# 代码库设计（codebase-design）

设计**深模块（deep module）**：把大量行为放在一个小接口后面，安置在干净的接缝（seam）上，并能通过这个接口来测试。凡是涉及设计或重构代码的地方，都用这套语言和这些原则。目标是：给调用方带来杠杆（leverage），给维护者带来局部性（locality），给所有人带来可测试性。

## 词汇表

严格使用这些术语：不要用「组件（component）」「服务（service）」「API」「边界（boundary）」来替代。用词一致本身就是重点。

**模块（module）**：任何拥有接口和实现的东西。刻意做到与规模无关：可以是一个函数、一个类、一个包，或者一段横跨多层的切片。_避免_：unit、component、service。

**接口（interface）**：调用方为了正确使用这个模块所必须知道的一切：类型签名，但也包括不变量、顺序约束、错误模式、必需配置和性能特征。_避免_：API、signature（太窄，它们只指类型层面的表面）。

**实现（implementation）**：模块内部的东西，它的代码本体。与**适配器（adapter）**不同：一个东西可以是一个小适配器配一个大实现（一个 Postgres 仓储），也可以是一个大适配器配一个小实现（一个内存里的假实现）。当话题是接缝时，用「适配器」；其他情况用「实现」。

**深度（depth）**：接口处的杠杆。调用方（或测试）每学习一单位接口，所能跑通的行为量。当一个模块把大量行为放在小接口后面时，它是**深**的；当接口几乎和实现一样复杂时，它是**浅**的。

**接缝（seam）** _（Michael Feathers）_：一个你无需就地编辑就能改变行为的地方；也就是模块接口所在的*位置*。接缝放在哪里本身就是一项设计决策，与它后面放什么无关。_避免_：boundary（跟 DDD 的限界上下文（bounded context）撞词了）。

**适配器（adapter）**：一个在某个接缝上满足某个接口的具体东西。它描述的是*角色*（填哪个槽），而不是实质（里面装什么）。

**杠杆（leverage）**：调用方从深度中得到的收益。每学习一单位接口，换来更多能力。一份实现能在 N 个调用点和 M 个测试上得到回报。

**局部性（locality）**：维护者从深度中得到的收益。变更、bug、知识、验证都集中在一处，而不是散落在各个调用方。改一处，处处都改好。

## 深 vs 浅

**深模块（deep module）** = 小接口 + 大量实现：

```
┌─────────────────────┐
│       小接口         │  ← 方法少、参数简单
├─────────────────────┤
│                     │
│      深层的实现      │  ← 复杂逻辑被隐藏
│                     │
└─────────────────────┘
```

**浅模块（shallow module）** = 大接口 + 少量实现（要避免）：

```
┌─────────────────────────────────┐
│             大接口               │  ← 方法多、参数复杂
├─────────────────────────────────┤
│            薄实现                │  ← 只是转手透传
└─────────────────────────────────┘
```

设计一个接口时，问：

- 我能减少方法的数量吗？
- 我能简化参数吗？
- 我能把更多复杂性藏到里面吗？

## 原则

- **深度是接口的属性，不是实现的属性。** 一个深模块内部可以由许多小、可 mock、可替换的部件组成；它们只是不属于接口。一个模块可以既有**内部接缝（internal seams）**（对它的实现私有，供它自己的测试使用），也有位于其接口处的**外部接缝（external seam）**。
- **删除测试（deletion test）。** 想象把这个模块删掉。如果复杂性随之消失，那它只是个透传；如果复杂性在 N 个调用方那里重新冒出来，那它是在创造价值。
- **接口就是测试面（test surface）。** 调用方和测试跨越的是同一道接缝。如果你想测试到接口*之外*去，那这个模块的形态多半是错的。
- **一个适配器意味着一个假想的接缝，两个适配器才意味着一个真实的接缝。** 除非确实有东西在接缝两边变化，否则不要引入接缝。

## 为可测试性而设计

好的接口让测试变得自然：

1. **接受依赖，而不是创建依赖。**

   ```typescript
   // 可测试
   function processOrder(order, paymentGateway) {}

   // 难测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，而不是产生副作用。**

   ```typescript
   // 可测试
   function calculateDiscount(cart): Discount {}

   // 难测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **更小的表面积。** 方法更少 = 需要的测试更少。参数更少 = 测试的搭建更简单。

## 关系

- 一个**模块（Module）**恰好拥有一个**接口（Interface）**（它呈现给调用方和测试的表面）。
- **深度（Depth）**是**模块**的属性，对照它的**接口**来衡量。
- **接缝（Seam）**是**模块**的**接口**所在之处。
- **适配器（Adapter）**坐落在**接缝**上，满足**接口**。
- **深度**为调用方产出**杠杆**，为维护者产出**局部性**。

## 被否定的表述

- **把深度定义为「实现行数 / 接口行数」的比值**（Ousterhout）：这会奖励给实现注水。我们改用「深度即杠杆」。
- **把「接口」理解为 TypeScript 的 `interface` 关键字或类的公开方法**：太窄了；这里的接口包含调用方必须知道的每一个事实。
- **「边界（boundary）」**：跟 DDD 的限界上下文撞词。请说**接缝**或**接口**。
