# 深化（Deepening）

在给定依赖的前提下，如何安全地深化一簇浅模块。假定你已掌握 [SKILL.md](../SKILL.md) 里的词汇：**模块（module）**、**接口（interface）**、**接缝（seam）**、**适配器（adapter）**。

## 依赖分类

在评估一个深化候选对象时，先给它的依赖分类。类别决定了深化后的模块如何跨越它的接缝来测试。

### 1. 进程内（In-process）

纯计算、内存状态、没有 I/O。永远可深化：把模块合并起来，直接通过新接口测试。不需要适配器。

### 2. 本地可替身（Local-substitutable）

有本地测试替身的依赖（Postgres 用 PGLite、内存文件系统）。只要替身存在就可深化。深化后的模块在测试套件里带着替身运行来测试。接缝是内部的；模块的外部接口上不开端口（port）。

### 3. 远程但自有（端口与适配器，Ports & Adapters）

你自己的、跨网络边界的服务（微服务、内部 API）。在接缝处定义一个**端口（port）**（即接口）。深模块拥有逻辑；传输层作为**适配器**注入。测试用内存适配器。生产用 HTTP / gRPC / 队列适配器。

建议的表述形态：*「在接缝处定义一个端口，为生产实现一个 HTTP 适配器，为测试实现一个内存适配器，这样即便它跨网络部署，逻辑也落在一个深模块里。」*

### 4. 真正的外部依赖（Mock）

你控制不了的第三方服务（Stripe、Twilio 等）。深化后的模块把外部依赖作为一个注入的端口来接收；测试提供一个 mock 适配器。

## 接缝纪律

- **一个适配器意味着一个假想的接缝，两个适配器才意味着一个真实的接缝。** 除非至少有两个适配器站得住脚（通常是生产 + 测试），否则不要引入端口。单适配器的接缝只是多绕一层。
- **内部接缝 vs 外部接缝。** 一个深模块可以既有内部接缝（对它的实现私有，供它自己的测试使用），也有位于其接口处的外部接缝。不要仅仅因为测试用到了内部接缝，就把它们暴露到接口上。

## 测试策略：替换，而不是叠加

- 一旦深化模块接口处的测试存在了，那些针对浅模块的旧单元测试就成了废料；删掉它们。
- 在深化模块的接口处写新测试。**接口就是测试面（test surface）**。
- 测试断言的是通过接口表现出的可观察结果，而不是内部状态。
- 测试应当能扛住内部重构，因为它们描述的是行为，不是实现。如果实现一变测试就必须改，那它就是在测试到接口之外去了。
