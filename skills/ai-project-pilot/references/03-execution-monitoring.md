# ③ 执行与监控：交付、反馈、纠偏

> 目标：让项目在跑的过程中**每一步都有产出、每次偏差都被发现**。监控不是阶段性的动作，它贯穿全过程。

**持续产出**：可用增量 · 状态报告 · 决策及变更记录
**管理提醒**：监控贯穿全过程

四个模块：小步迭代 → 沟通闭环 → 看板监控 → 偏差处理。

---

## 模块 1：小步迭代

循环：

```text
待办排序 → 开发验证 → 演示反馈 → 更新待办
```

要点：

- **每轮交付可验证成果**，并**记录实验结论**（这轮试了什么、结果如何、下一步做什么）
- 成果要「可验证」：能演示、能评测、能对比基线
- **固定评测集做回归**——每轮都跑同一套评测，防止改好一个坏一个
- **模型与提示词留版本**——每次变更记录版本，出问题能回滚定位

> 别憋大招。小步走、每步留痕，比一次交付一个大而全的东西可靠得多。

---

## 模块 2：沟通闭环

三个层次：

| 层次 | 频率 | 内容 |
|---|---|---|
| **日常同步** | 每天 | 进展、下一步、阻塞 |
| **周报汇总** | 每周 | 里程碑、指标、风险、待决策事项 |
| **关键决策** | 按需 | 责任人、截止日、结论留痕 |

闭环链条：

```text
发送 → 接收 → 理解 → 确认 → 跟进
```

要点：

- **「发送了」不等于「沟通了」**。必须走到「确认」和「跟进」，否则等于没说
- 阻塞项要当天抛出，不要留到周报
- 关键决策**必须留痕**（谁定的、什么时候、结论是什么），否则一周后没人记得

---

## 模块 3：看板监控

四个维度，用数据说话：

| 维度 | 看什么 |
|---|---|
| **进度** | 里程碑偏差、阻塞、关键依赖 |
| **质量** | 任务成功率、事实错误、缺陷 |
| **成本** | 预算消耗、单次调用成本 |
| **业务** | 真实使用、效率改善、用户反馈 |

要点：

- **进度**盯的是「偏差」不是「百分比」——偏离基准多少、为什么
- **质量**里的「事实错误」是 AI 项目专属指标，必须单独统计
- **成本**要同时看总量（预算消耗）与单价（单次调用成本），单价涨了往往意味着提示词或模型出了问题
- **业务**指标最容易漏——没人用，技术上再漂亮也是失败

> 用数据说话，及时发现问题，推动持续改进。

---

## 模块 4：偏差处理

流程：

```text
发现偏差 → 分析原因 → 制定措施
```

升级与变更规则：

- **超出授权范围** → 按约定路径升级（找项目经理或发起人）
- **涉及基准调整**（范围/进度/成本变了）→ 提交变更审批
- **跟踪措施效果** → 更新风险与问题记录

要点：

- 偏差**分两类**：能在授权内解决的就地解决；动到基准的必须走变更
- 措施要有**责任人和截止日**，否则等于没定
- 处理完要**回头验证措施是否真的有效**，无效就再循环

> 及时纠偏，把风险控制在可接受范围。

### 变更准入：工程三问（涉及代码时）

变更单上必须答出三问，**答不出来就不批**（见 [05-engineering-guardrails.md](05-engineering-guardrails.md) 原则 9）：

| 问 | 对应 |
|---|---|
| **怎么测？** | 行为可测试 |
| **怎么看到它坏了？** | 运行可观测、故障可定位 |
| **怎么退回去？** | 可回滚，且回滚路径演练过 |

同时确认变更性质：**内部路径**重构可直接删旧实现；**对外契约**（稳定 API、数据库迁移）的兼容性按协议契约单独评估，属合同义务。

---

## 阶段收尾：过推进关口

监控是**贯穿式**的，没有「监控阶段结束」这一说。但进入「④ 验收与上线」之前，确认：

- [ ] 每轮迭代都有可验证成果 + 实验结论记录
- [ ] 固定评测集在跑回归，模型与提示词有版本记录
- [ ] 沟通闭环走得通（有确认、有关键决策留痕）
- [ ] 看板四维度（进度/质量/成本/业务）都有数据
- [ ] 未关闭的偏差都有责任人和截止日
- [ ] 所有基准变更都有变更记录

**监控贯穿全过程。** 从第一轮迭代到上线后运营，看板都不能停。
