# ⑤ 工程护栏（可选）：把工程原则接进项目管理

> **这是可选章节**，不属于四阶段的强制关口。当项目进入「要开始写代码」或「有多个工程团队协作」时加载。
>
> 一句话说清关系：**项目管理管「做什么、值不值、过不过关口」，工程规范管「代码怎么写」。** 两者不是一回事，但接口在三处——**计划阶段的设计关口、执行阶段的变更准入、收尾阶段的决策归档**。本文件就是把工程规范接进这三处。

---

## 为什么要接

工程规范（`CLAUDE.md` / `AGENTS.md` / 团队编码规范）如果只躺在仓库根目录，会变成「写着好看、没人执行」。把它接进项目管理，它才有牙齿：**变成关口的判据、变更的准入条件、复盘的归档项。**

反过来，项目管理如果不接工程规范，会出现「进度正常、质量失控」——每个变更单看都没问题，攒起来架构就烂了。

---

## 可移植的工程护栏（10 条，方法层）

下面 10 条是**与具体技术栈无关**的工程原则，任何 AI 项目都适用。每条给出「原则 → 落在哪个阶段 → 怎么判过关」。

### 1. 架构与领域优先

**原则**：计划阶段就以理想架构为目标，先明确业务目标、领域边界、模块职责、依赖方向和数据流，形成可持续演进的设计后再进入编码。不得以短期实现便利牺牲整体设计。

**关键补充**：**设计必须完整，实现应当克制。** 不做推测性抽象——抽象延迟到第二个真实用例出现时才引入，单一场景直接实现。

**落在**：② 计划（WBS 的「需求与数据」工作包之前插入设计评审）

**判过关**：设计文档里有业务目标、领域边界、模块职责、依赖方向、数据流五样；且**没有**为单一场景提前抽的接口。

---

### 2. 高内聚、低耦合

**原则**：模块通过精简且稳定的接口封装内部复杂度，使职责、命名、依赖和扩展方式清晰自然；按单一职责拆分。

**落在**：② 计划（模块划分）、③ 执行（代码评审）

**判过关**：每个模块能用一句话说清职责；模块间依赖方向单一，无循环依赖。

> ⚠️ 具体的「单文件行数上限」「目录层级规则」属于**项目自定**，写进项目的 `CLAUDE.md` / `AGENTS.md`，不要写死在本技能里。

---

### 3. 边界与数据流清晰

**原则**：协议模型、领域模型、持久化模型、视图模型**不得相互泄漏**；数据必须在边界处完成校验和独立转换，避免跨层共享可变状态。

**落在**：② 计划（分层设计）

**判过关**：能画出数据从入口到落库的路径，且每一层用的是自己的模型，层与层之间有显式转换。

> ⚠️ 「哪四类模型」是项目自定。有的项目是 DTO / Entity / VO，有的项目根本没有持久层。

---

### 4. 安全与隔离默认开启

**原则**：所有功能按多租户、多用户场景设计，明确认证、授权和数据隔离边界；遵循最小权限原则；**任何外部输入均视为不可信**；敏感信息不得进入代码、日志或响应。

**落在**：① 立项（成功标准 + 初步风险）、② 计划（安全评审工作包）、③ 执行（安全评审关口）

**判过关**：认证/授权/数据隔离边界写明；敏感信息清单存在，且代码、日志、响应三处都检查过。

**与 AI 护栏的接口**：这条直接支撑「数据来源与使用权限」「数据泄露 / 合规」两条 AI 护栏。**提示词、RAG 检索结果、模型输出同样是「外部输入」，一律不可信。**

---

### 5. 面向并发与故障设计

**原则**：主动考虑幂等性、竞态、事务边界、超时、取消、重试、背压和资源释放；**不得通过无边界重试、吞错或隐式共享状态掩盖问题**。

**落在**：② 计划（可靠性设计）、③ 执行（稳定性监控）

**判过关**：每一处外部调用都定义了超时、重试上限与失败处理；幂等键明确。

**与 AI 护栏的接口**：AI 调用天然是高延迟、高失败率的**外部依赖**。这条是「工程稳定性」指标的具体化——尤其「不得无边界重试」，模型调用重试会**直接烧钱**。

---

### 6. 完整的前端 / 交互体验

**原则**：控制渲染成本、异步状态和并发请求，保持清晰的 UI 结构；用户流程必须覆盖**加载、空状态、错误、重试、反馈和可访问性**。

**落在**：② 计划（验收场景设计）

**判过关**：验收场景表里，每一个用户流程都覆盖了加载 / 空 / 错误 / 重试四个状态。

> 对 AI 产品尤其重要：**「模型正在思考」「模型答不出来」「模型答错了」是三个不同的状态**，不能只做一个转圈动画。

---

### 7. 复用稳定的业务语义

**原则**：优先复用已有模块和能力，但**不要仅因代码外形相似而过早抽象**；确需重复时，必须注释说明其独立演进或暂不抽象的原因。新增依赖前先核查项目已有依赖能否满足需求，**不得臆断已有库缺少功能——先查阅文档和类型定义**；确需引入时优先成熟且维护良好的库，不重复实现通用功能。

**落在**：② 计划（技术选型）、③ 执行（代码评审）

**判过关**：每个新增依赖都有「为什么现有依赖不行」的一句话说明。

> ⚠️ 「已有依赖去哪查」（根 `package.json` / `packages/` workspace / `pom.xml`…）是**项目自定**，写进项目的工程规范。

---

### 8. 为未来维护者保留上下文 ★

**原则**：代码、注释、测试和架构文档是**跨越时间的协作媒介**。非显然的设计决策、兼容约束、已知缺陷和临时方案，必须记录**原因、影响范围、潜在风险及移除条件**；技术债务应关联追踪任务；关键架构决策应同步到 **ADR**；**避免留下缺少上下文的 TODO**。

**落在**：③ 执行与监控（决策留痕）、④ 收尾与复盘（归档）

**判过关**：抽查三条 TODO / 技术债，每条都能答出「为什么这么写、什么时候能删」。

**这是本组里对项目管理增益最大的一条。** 它把「决策留痕」从一句口号变成了可检查的标准：

| 要留痕的东西 | 必须写清 |
|---|---|
| 非显然的设计决策 | 原因 · 影响范围 · 潜在风险 · 移除条件 |
| 兼容约束 | 约束来源 · 到期时间 |
| 已知缺陷 / 临时方案 | 为什么先这样 · 什么条件下必须修 |
| 技术债 | 关联的追踪任务 ID |
| 关键架构决策 | 同步到 ADR |

---

### 9. 变更可验证、可观测、可回滚 ★

**原则**：每项改动应**行为可测试、运行状态可观测、故障可定位**，并兼顾向后兼容和回滚路径；错误与日志必须保留**诊断上下文**，但**不得泄露敏感信息**。

**落在**：③ 执行（变更准入）、④ 发布（回滚演练）

**判过关**：变更单上三问都能答——**怎么测？怎么看到它坏了？怎么退回去？** 答不出来就不批。

**这是本组里对变更管理增益最大的一条。** 把它直接做成变更申请的**准入条件**（见 `templates/变更申请.md`）。

---

### 10. 删除优于兼容

**原则**：**内部路径**重构时直接删除过时实现，禁止新增兼容层、deprecated shim 或双写逻辑；**对外契约**（稳定 API、数据库迁移）的兼容性按协议契约**单独评估**——那属于合同义务，而非迁就旧代码。

**落在**：③ 偏差处理（变更申请）

**判过关**：变更单上明确标了「内部路径」还是「对外契约」，两者走不同审批强度。

> 这条最容易被忽略，也最容易被滥用：**「删除优于兼容」只适用于内部路径。** 对外 API 和已上线的数据库迁移，删之前先看合同。

---

## 项目自定部分（不要写死在本技能里）

上面 10 条是**方法层**。下面这些属于**实现层**，每个项目都不一样，必须由项目自己的 `CLAUDE.md` / `AGENTS.md` 定义。本技能只提供骨架（见 `templates/工程规范.md`）：

| 项目自定项 | 举例 |
|---|---|
| 具体命令 | 提交前跑什么、改了前端跑什么、改了 schema 跑什么 |
| 阈值 | 单文件行数上限、覆盖率下限、响应时间上限 |
| 分层与模型名 | 协议/领域/持久化/视图模型在本项目里叫什么 |
| 依赖清单位置 | 根 `package.json` / `packages/` workspace / 其它 |
| 目录与命名约定 | 模块怎么放、文件怎么命名 |
| 技术栈专属规则 | 前端框架、数据库、消息队列各自的坑 |

> **判断标准**：一条规则换个项目还成立吗？成立 → 属于本技能（方法层）；不成立 → 属于项目的工程规范（实现层）。

## 变更速查的「模式」

原 `CLAUDE.md` 末尾那张「变更速查」（改前端跑 A、改 schema 跑 B、数据迁移跑 C）**内容本身是本项目专属的，不能搬**；但**它的模式非常值得纳入**：

> **按「变更类型」列出「必须运行的校验」，并在变更申请里要求填写。**

本技能已把它落成两处：

1. `templates/工程规范.md` 里的「变更速查」表——项目自己填命令
2. `templates/变更申请.md` 里的「变更后需运行的校验」字段——每个变更单都要填

这样「提交前跑什么」不再是口口相传，而是**写在规范里、填在变更单上**。

## 怎么和四阶段串起来

```text
① 立项   → 安全与隔离（原则 4）写进成功标准与初步风险
② 计划   → 架构与领域优先（原则 1）、高内聚低耦合（原则 2）、
            边界与数据流（原则 3）、面向故障（原则 5）、
            交互完整性（原则 6）、复用（原则 7）
            ★ 并在这一步产出《工程规范》（templates/工程规范.md）
③ 执行   → 决策留痕（原则 8）、变更准入三问（原则 9）、
            删除优于兼容（原则 10）
④ 收尾   → 归档 ADR、技术债、被推翻的假设（原则 8 的延续）
```

**关键点：工程规范必须在 ② 计划阶段产出，不能等到 ③ 执行阶段再补。** 执行阶段没有判据，代码评审就没有标准，变更审批就只剩形式。
