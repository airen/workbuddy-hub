# ② 计划：把不确定性拆成可验证任务

> 目标：把「不知道能不能成」的大目标，拆成一串「每一步都能验证」的小任务，并给出范围、进度、成本基准与风险/沟通规则。

**本阶段交付**：范围、进度、成本基准 · 风险与沟通计划
**推进原则**：总体有基准，迭代做验证

四个模块：拆工作（WBS）→ 设关口（里程碑）→ 算资源（进度与成本）→ 定规则（风险与变更）。

---

## 模块 1：拆工作 | WBS

把项目拆成六个阶段的工作包：

```text
需求与数据 → 原型与评测 → 开发与集成
测试与安全 → 试点与上线 → 交接
```

要点：

- **每一项都要写清三件事**：负责人、完成条件、依赖
- **「完成条件」必须是可验证的**（能跑通、能通过评测、能签字），不是「基本完成」
- **依赖**要显式标出，尤其是「等数据」「等授权」「等上游接口」
- AI 项目特有的工作包别漏：**数据清洗与标注、评测集构建、提示词工程、成本测算、安全与合规评审**

**产出**：WBS 表（见模板）。

---

## 模块 2：设关口 | 里程碑

不要按时间设里程碑，要按**验证**设关口。四个标准关口：

| 关口 | 要回答的问题 |
|---|---|
| **可行性验证** | 数据和方案能否支撑目标？ |
| **原型验证** | 固定评测集是否达到门槛？ |
| **试点验证** | 真实用户是否获得价值？ |
| **上线准备** | 质量、监控与回滚是否就绪？ |

要点：

- 每个关口都要有**明确的通过标准**（例如「固定评测集准确率 ≥ 85%」）
- 关口没过，**不进入下一阶段**；要带病前进必须走变更
- 关口之间可以迭代多轮，但每轮都要记录结论

**产出**：里程碑与关口表（见模板）。

---

## 模块 3：算资源 | 进度与成本

要点：

- **评估工作量、关键依赖与资源可用性**：人力在不在、数据到没到、算力够不够
- **预算覆盖五块**：人力、数据、模型、算力、运维
- **为实验失败和返工预留缓冲**——AI 项目返工概率远高于普通软件，缓冲不是浪费
- 进度给**区间**而不是单点；标注关键路径

AI 项目成本特别注意：

- 模型调用按量计费，要算**单次调用成本 × 预估调用量**
- 评测与实验本身也烧钱，要单独列预算
- 上线后运维是**持续成本**，不是一次性投入

> 合理规划，让资源创造更大价值。

**产出**：进度与成本基准（见模板 WBS 与里程碑的配套表）。

---

## 模块 4：定规则 | 风险与变更

要点：

- **风险登记**：每条风险写清概率、影响、责任人、应对措施
- **AI 项目重点关注**：数据不足、幻觉、数据泄露、成本失控
- **变更流程**：先评估对范围、进度、成本和质量的影响，再由授权人审批，最后更新计划与基准
- 变更**必须留痕**（谁提的、为什么、批没批、影响是什么）

> 控制风险，拥抱变化。

**产出**：风险登记册（见模板）+ 沟通计划（谁、多久、通过什么渠道同步什么）。

---

## 阶段收尾：过推进关口

进入「③ 执行与监控」之前逐条确认：

- [ ] WBS 每一项都有负责人、完成条件、依赖
- [ ] 四个关口都有可量化的通过标准
- [ ] 预算覆盖人力/数据/模型/算力/运维五块，且含返工缓冲
- [ ] 风险登记册里四条 AI 重点风险（数据不足、幻觉、泄露、成本）都有应对
- [ ] 变更流程与授权人明确
- [ ] 沟通计划明确（日常同步、周报、关键决策的节奏与责任人）
- [ ] **设计评审已完成**：业务目标 / 领域边界 / 模块职责 / 依赖方向 / 数据流五样齐全，且没有为单一场景提前抽的接口（见 [05-engineering-guardrails.md](05-engineering-guardrails.md) 原则 1）
- [ ] **已产出《工程规范》**（[templates/工程规范.md](../templates/工程规范.md)），且「变更速查」表里填的是真实可执行的命令

**总体有基准，迭代做验证。** 基准是参照系，不是枷锁——变更要走流程。
