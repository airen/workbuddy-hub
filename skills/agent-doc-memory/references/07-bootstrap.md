# 07 · 落地路径

> 三种场景：全新项目、已有项目、团队协作。**共同原则：不要一次建全，不要另起一套。**

## 通用原则

1. **先盘点，再动手。** 建脑前先找现有文档（README、`docs/`、`AGENTS.md`、`CLAUDE.md`、wiki 导出、会议纪要、接口文档）。**把已有的登记进索引，不要另起一套并行体系。**
2. **从最小的可用开始。** 先建 `INDEX.md` + `conventions.md`，不要一次写 50 篇。
3. **让知识随任务生长。** 每次任务收尾自然补一篇，比一次性大扫除可靠得多。
4. **最后必须写硬指令。** 在 agent 的指令文件里钉死"先查后更新"，否则这套工作区下一轮就没人读。

---

## 场景 A：全新项目

最省事——从第一天就长成对的形状。

### 第 1 天

```bash
python3 scripts/init_doc_brain.py /path/to/new-project
```

生成骨架：

```text
docs/
├── INDEX.md          ← 空索引，带说明
├── conventions.md    ← 骨架 + 待填清单
├── glossary.md       ← 骨架
├── specs/
├── decisions/
└── research/
```

然后：

1. **填 `conventions.md`**：技术栈、目录结构、命名、分支 / 提交 / 评审约定。**不用写全，写你现在确定的。**
2. **在 `AGENTS.md` / `CLAUDE.md` 加硬指令**（模板见 [templates/conventions.md](../templates/conventions.md) 末尾）：

   ```markdown
   ## 项目记忆（必读）
   本项目使用文档工作区承载长期知识，位置 `docs/`。
   - 任何任务开工前，先读 `docs/INDEX.md`，按索引读出相关文档。
   - 任务收尾时更新对应文档，并同步 `docs/INDEX.md`。
   - 没有新知识就说"本次无文档更新"。
   ```

3. 第一个功能做完 → 写第一篇 `specs/` 和第一篇 `decisions/`。

### 前两周

每完成一个任务，问一次三问（见 [04-update-protocol.md](04-update-protocol.md)）。两周后你会有 5–10 篇真正有用的文档，而不是 50 篇模板。

## 场景 B：已有项目（最常见）

**难点**：项目已经跑了一段时间，知识散落在各处（甚至只在人的脑子里）。

### 第 1 步：盘点（30 分钟）

列出所有现有知识源：

| 来源 | 里面有什么 | 处理 |
|---|---|---|
| `README.md` | 项目简介、启动方式 | 保留；在索引里登记 |
| `docs/`（已有） | 各种文档 | 逐份登记进索引 |
| `AGENTS.md` / `CLAUDE.md` | agent 指令 | 保留 + 追加"先查后更新"硬指令 |
| `adr/` / `decisions/`（已有） | 决策记录 | 当 `decisions/` 用 |
| wiki / Notion / 飞书文档 | 可能很多 | 先登记**链接**，不急着搬 |
| 代码注释 / `CONTRIBUTING.md` | 工程约定 | 提炼进 `conventions.md`（只提炼"为什么"） |
| **人的脑子** | 大量"我们当时为什么……" | **最该抢救的**——见第 3 步 |

### 第 2 步：建索引，把现有文档登记进去

新建 `docs/INDEX.md`，把上一步盘到的每一份都登记一行。**先"指向"，不急着"搬入"**——把知识地图先建立起来。

> 如果已有文档在别处（wiki、Notion），索引里直接写外链即可。**地图比仓库更重要。**

### 第 3 步：抢救"脑子里的知识"（最高价值）

找 3–5 个"为什么"型问题，问项目里最老的人（或你自己回忆），写成决策记录：

- 「我们当初为什么选了这个数据库 / 框架？」
- 「这个奇怪的字段 / 表 / 接口是怎么来的？」
- 「有没有试过别的方案，为什么放弃了？」
- 「有哪些坑是新人一定会踩的？」

**这一步的产出，价值超过前面所有步骤的总和。** 因为这些知识：① 代码里读不出来；② 只存在于人的记忆里；③ 人一走就永久丢失。

### 第 4 步：从最痛的地方开始写

不要按目录顺序补。**按"最近踩的坑"补**：

- 最近一次返工 → 补对应的 `decisions/` 或 `research/`
- 最近一次"新人问同样的问题" → 补 `conventions.md`
- 最近一次"改了一处忘了另一处" → 补 `specs/` 的边界

### 第 5 步：写硬指令 + 跑一次审计

- 在 `AGENTS.md` / `CLAUDE.md` 加硬指令
- `python3 scripts/doc_audit.py /path/to/project` → 处理掉断链与孤儿

## 场景 C：团队协作

文档工作区的一大优势是**可分享**——这是向量库做不到的。

### 关键动作

1. **文档进 git**，和代码同一个仓库（或独立文档仓库）
2. **文档变更走 review**：改 `conventions.md`、新增 `decisions/` 都提 PR
3. **决策记录在评审时引用**：PR 描述里写「遵循 `decisions/0003`」或「本 PR 引入 `decisions/0007`，请评审」
4. **新人 onboarding 第一站是 `INDEX.md`**，不是代码
5. **约定变更要广播**：改 `conventions.md` 时 @ 相关人

### 团队特有的约定

- **谁能改什么**：`conventions.md` / `decisions/` 通常需要 owner review；`research/` 相对自由
- **决策记录的编号冲突**：多人同时写会撞号 → 约定"先到先得 + 提交时检查"，或用 PR 号当编号
- **谁的 agent 写**：每个成员用自己的 agent，但**写进同一份文档工作区**——这正是它比"每人一个私有记忆库"强的地方

### 团队审计节奏

- **每季度**：跑 `doc_audit.py --stale-days 90`，在例会上过一遍过期文档
- **每次架构评审**：顺手检查相关决策记录是否还现行

## 迁移已有"记忆插件"的方案

如果项目已经接了向量库记忆，想换过来：

1. **不要把向量库里的片段导出成文档。** 它们是切片，没有上下文，搬过来就是制造噪音。
2. **把向量库当"线索"用**：扫一遍有哪些主题，然后**按主题重新写**成完整的文档。
3. **保留 RAG 用于外部语料**（如果有），把项目自身的知识迁到文档工作区。两者可以共存，边界见 [01-why-not-recall.md](01-why-not-recall.md)。
4. **在硬指令里移除"先搜记忆"**，改成"先读 INDEX.md"。

## 落地自检

- [ ] 项目里有一份能查到**全部**文档的索引吗？
- [ ] 现有文档都登记进索引了吗？（跑了 `doc_audit.py` 确认没有孤儿）
- [ ] `conventions.md` 写了吗？（哪怕只有几条）
- [ ] agent 的指令文件里写了"先查后更新"的硬指令吗？
- [ ] 有没有至少一篇"从人脑里抢救出来"的决策记录？
- [ ] 下次任务开工时，agent 真的会去读索引吗？（拿一次任务验证）

## 常见落地失败

| 失败 | 原因 | 纠正 |
|---|---|---|
| 建了目录，一周后没人用 | 没写硬指令，agent 不知道该读 | 补 `AGENTS.md` 硬指令 |
| 写了 30 篇模板，全是空的 | 一次建全 | 删到只剩 3 篇，按需长 |
| 文档和代码两套说法 | 发现冲突不修 | 以现实为准，当场修 |
| 只有一个人写 | 没进 git / 没走 review | 文档进仓库，变更走 PR |
| 半年后全过期 | 没审计节奏 | 设成里程碑动作，跑 `doc_audit.py` |
| 又变成"什么都往里塞" | 忘了"没有就不写" | 回到三问，守住信噪比 |
