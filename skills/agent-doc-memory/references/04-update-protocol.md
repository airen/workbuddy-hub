# 04 · 更新协议

> 每个任务收尾执行。**这一步不做，整个文档工作区就退化成"一次性写过的说明"，下一轮没人会读它。**

## 为什么必须"趁热"

更新文档的唯一时机，是**整幅图还在你上下文里的时候**。

一旦会话结束、上下文清空，你就只剩下一份代码，和"当时好像想过点什么"的模糊印象——而**模糊印象恰恰是最不该被写下来的东西**。等下次新会话再来写，你写的就不再是"当时的决策"，而是"对代码的逆向猜测"，价值低一个数量级。

所以：**干完立刻写，不要攒着。**

---

## 三问（收尾必做）

趁上下文还在，问自己三句话：

### 问 1：这次有没有产生"下次还需要知道"的东西？

- 定了一条约定 / 改了一条约定？
- 做了一个有取舍的决策？
- 搞清了一个第三方库 / API / 坑？
- 写了规格或计划？需求变了？
- 澄清了一个术语？

**任一为"是" → 写。**

### 问 2：有没有推翻或修正已有文档？

- 我这次的实现，和某份决策记录冲突了吗？（冲突了 → 要么改实现，要么更新决策，**必须显式处理，不能默默绕过**）
- 我发现某份文档过期了吗？（过期了 → 就地改对或标 `已废弃`）
- 某份规格的边界被突破了吗？（突破了 → 更新规格）

**任一为"是" → 改。**

### 问 3：有没有出现该新建文档的新领域？

- 我处理了一个索引里完全没有的领域？
- 我搞清楚了一个之前没人调研过的技术点？

**任一为"是" → 新建（并同步索引）。**

---

## 三问全"否"怎么办

**明确说「本次无文档更新」。**

这不是偷懒，这是纪律。记忆插件最大的病是"捕获一切"——把噪音也塞进库里，导致信噪比崩塌、正确的东西反而浮不上来。**文档工作区必须守住信噪比：只写"下次还需要知道"的。**

> 一句判据：**如果这条信息三个月后会被当成"过期的废话"，就不要写。**

## 更新触发事件表（逐条对照）

| 触发事件 | 写到哪 | 至少包含 | 不该包含 |
|---|---|---|---|
| 定下 / 改变一条**约定** | `conventions.md` | 规则 + 为什么 + 例外 | 泛泛的"最佳实践" |
| 做了一个**有取舍的决策** | `decisions/NNNN-*.md` | 备选、选了谁、**放弃了什么代价**、何时该重估 | 只写结论不写代价 |
| 搞清楚**第三方库 / API / 工具**的用法或坑 | `research/<topic>.md` | 结论先行、最小可用示例、坑与规避 | 复制官方文档全文 |
| 写了**规格 / 计划**，或需求变更 | `specs/<feature>.md` | 目标、**不做清单**、验收标准 | 实现细节（那是代码的事） |
| **澄清术语**歧义 | `glossary.md` | 词 + 本项目定义 + **不指什么** | 通用词典释义 |
| 发现**文档过期** | 原文档 | 就地改对，或标 `已废弃` + 被谁取代 | 追加"补充说明（二）" |
| 踩坑并找到**根因** | `research/` 或 `decisions/` | 现象、根因、怎么避免复发 | 只记现象不记根因 |
| 引入了**新的依赖 / 服务 / 环境要求** | `conventions.md` 或 `research/` | 是什么、为什么引入、代价 | 依赖清单本身（看 lockfile） |

## 怎么写（写作纪律）

### 1. 就地修改，不要追加

**改已有文档时直接改原文**，不要写"补充说明（二）：关于上面第 3 点，现在改成……"。

- ✅ 把"我们用 session"直接改成"我们用 JWT（2026-10 改，原因见下）"
- ❌ 在文末追加一段"更新：现在改用 JWT 了"

**为什么**：追加式会让文档变成考古现场，读者要读完所有历史才知道现状。**演变交给 git 历史承载**——`git log -p docs/decisions/0002-*.md` 比一堆"补充说明"清楚得多。

### 2. 写"为什么"，不只写"是什么"

| ❌ 只写是什么 | ✅ 加上为什么 |
|---|---|
| 用 pnpm | 用 pnpm：npm 的扁平化 node_modules 让我们踩了幽灵依赖的坑，pnpm 的严格链接避免了它 |
| 接口超时设 3s | 接口超时设 3s：下游 P99 是 1.8s，3s 留了余量又不至于拖垮上游线程池 |
| 订单表按 user_id 分片 | 订单表按 user_id 分片：查询几乎都带用户维度；代价是跨用户统计要聚合 16 片 |

代码已经写了"是什么"。**你写"为什么"才是增量。**

### 3. 更新完必须同步索引

**新建 / 删除 / 改状态 → 回 `INDEX.md` 改对应行。**

忘了这一步，等于没写：下次 agent 读索引时根本不知道有这份文档，它就永远不会被查到。**这是最常见的"文档写了没人看"的成因。**

### 4. 一次任务只写必要的量

不要在一次收尾里写 5 份文档。**只写本次真正产生的那 1–2 份。** 宁可少写、持续写，不要一次写爆然后烂尾。

---

## 更新时的自检

- [ ] 我写的是**为什么**，不是代码里已有的**是什么**吗？
- [ ] 我是**就地修改**，还是错误地追加了"补充说明"？
- [ ] 我**同步更新了 `INDEX.md`** 吗？
- [ ] 我的文档开头有 `状态` 和 `最后更新` 吗？
- [ ] 我有没有把**代码**抄进文档？（抄了 → 改成指路径）
- [ ] 这份文档三个月后还有人愿意读吗？（不愿读 → 别写）

---

## 反面：更新时的常见错误

| 错误 | 后果 |
|---|---|
| 攒着等"以后统一整理" | 永远不整理；或者整理时靠逆向猜测 |
| 追加"补充说明（二）（三）" | 文档变考古现场，读者读不出现状 |
| 只写结论不写代价 | 下次无法判断这个决策是否还成立 |
| 把代码粘进文档 | 第二天就过期，且开始说谎 |
| 写了不同步索引 | 下次等于没写 |
| 为写而写（没新知识也硬写） | 信噪比崩塌，重蹈记忆插件的覆辙 |
| 发现和已有决策冲突却默默绕过 | 项目里出现两套互相矛盾的"真相" |
