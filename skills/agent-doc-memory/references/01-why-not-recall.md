# 01 · 为什么召回式记忆是错题

> 这一篇讲"为什么不能那么做"。**不需要在每次任务里读它**，但当你（或用户）想给项目接一个记忆插件、向量库、或者"让 agent 搜历史对话"的方案时，先读这一篇。

## 记忆插件的全部架构

市面上每一个记忆插件，剥掉包装后都是同一套：

1. 遍历会话记录
2. 生成"记忆"片段（一段摘要、一个事实、一条偏好）
3. 插进 RAG 数据库（向量库）
4. 每次提示检索 top 5，注入上下文
5. 还不够？给 agent 一个在数据库里搜的工具

更花哨的版本在往上堆功能：逐字搜历史记录、多级记忆（短期 / 长期）、后台守护进程去审阅合并去重、整夜重写记忆的"做梦者"、连续上下文压缩、重排器……

**每个插件都在用新的烧 token 的功能，去补底下同一个有缺陷的架构。** 这就是为什么它们没有一个真正可靠。

## 五类失败

### 1. 记忆靠相似度浮出，而相似度 ≠ 正确性

向量检索排的是**两个片段在嵌入空间里的距离**。就这些。

它不告诉你：哪条是**正确的**、哪条是**当前的**、以及**缺了什么**。一段三个月前写的、当时就对但现在已经过期的描述，和一段昨天刚更新的描述，在嵌入空间里可能挨得一样近。

### 2. 记忆被存储时没有上下文

一个 RAG 片段只能装那么多。**其余全部丢失**：语境、动机、当时为什么这么选、踩过什么教训、环境有什么特殊约束。

你得到一句「认证用 JWT」，丢掉了「我们试过 session，因为移动端跨域 cookie 不可靠才换的 JWT，且 token 有效期设短是因为风控要求」。

后者才是你下次真正需要的东西。

### 3. 过去被当成真相

这些插件全都依赖**召回**——不管是搜历史记录还是查向量库。但代码库天天在变。

那 500 条关于认证的片段，**各自有多准？** 没有人知道。它们带着当时的语气、当时的确定感被检索出来，然后被当成现在的事实使用。

### 4. Agent 搜不到它不知道自己不知道的东西

就算你给 agent 一个搜索工具，**它怎么知道什么时候该用？**

- 它不知道项目里有一份关于"分库方案"的决策记录 → 它不会去搜"分库"
- 它不知道自己缺一条"命名约定" → 它不会去搜"命名"

**这是最致命的一条**：召回的前提是"知道要找什么"。而 agent 最大的问题恰恰是**不知道自己不知道什么**。

### 5. 这个存储无法审计

SQLite 里躺着 10,000 个嵌入。请回答：

- 哪些记忆存在？
- 哪些过期了？
- 哪些从来没被取用过？
- 哪些是**错的**、正在偷偷影响 agent 的行为？

**答不上来。** 它是黑箱。你没法 diff 它、review 它、也没法把一个错误的记忆精准地改掉——你只能删掉整条，或者再加一条去"覆盖"它（然后两条可能同时被召回，互相打架）。

## 根因：整套架构建立在同一个错误假设上

> **假设**：agent 会遗忘，这就是问题。所以修复方式就是**记住**。为了记得更好，我们应该捕获得更多、索引得更好、检索得更聪明。

于是整套论点都围绕**"捕获并召回过去"**打转。

但没有任何其他领域是这么处理知识的。**没有人会为了回忆某个功能的约束条件，去重看三年前的一场团队会议。** 人们把事情写下来，然后用那些记录。

解决方案不是给 agent 一个搜索工具，让它在过去一千万 token 的对话里翻找、把发生的事情重新拼成碎片。

**解决方案是基于文档的记忆。**

## 五类失败 → 文档工作区怎么解

| 召回式记忆的失败 | 文档工作区的解法 |
|---|---|
| 相似度 ≠ 正确性 | 文档有 **状态字段**（现行 / 过期 / 已废弃），正确性是**被声明**的，不是被猜的 |
| 片段没有上下文 | 文档**整篇读**，动机、代价、边界、教训都在里面 |
| 过去被当成真相 | 文档**就地更新**，改完就是当前真相；git 历史记录演变，不需要"召回" |
| 不知道自己不知道 | **`INDEX.md` 是唯一入口**，一眼看到全部文档，不需要先猜关键词 |
| 无法审计 | **纯 Markdown**，可 grep、可 diff、可 review，孤儿 / 断链 / 过期一键查 |

## 什么时候召回（RAG）仍然是对的

**不要一棒子打死。** 本技能的边界很清晰：

**用 RAG**：

- 语料是**外部的、海量的、非结构化的**：产品手册、法规全文、论文库、客服知识库
- 你**没有能力或权限**把它整理成一份份文档（几万页法规，你不可能"写下来"）
- 任务是**一次性的问答型检索**，不需要"当前真相"的强保证

**用文档工作区（本技能）**：

- 知识是**项目自身的**：约定、规格、决策、调研、术语
- 你**有能力也有责任**把它写清楚（通常几十到几百份文档，不是几十万页）
- 知识会**随项目演进**，且"哪条是当前的"至关重要

> 一句话判据：**能写下来的，就写下来；写不下来的（海量外部语料），才去检索。**

## 给用户讲清楚这件事的话术

当用户说"给我接个记忆插件吧"，不要直接照做，先讲清三件事：

1. **你想让 agent 理解你的项目** —— 知道某个功能在哪、当初为什么这么做、你们约定过什么、你在意什么。
2. **而记忆插件给你的是** —— 每一条提示上都注入一次 RAG 片段的抽奖，然后祈祷正确的那几条能浮上来。**即便它偶尔奏效，agent 仍然不理解你的项目。**
3. **替代方案** —— 把知识写进一个文档工作区，agent 干活前先查、干完再更新。你得到的不是一个黑箱，而是一个**你能读、能改、能提交、能分享**的东西。

## 反面清单：不要做的事

- ❌ 建向量库 / 嵌入 / 摘要器 / 后台守护进程（这是回到老路）
- ❌ 把历史对话原样切片入库
- ❌ 给 agent 一个"搜历史"工具就以为解决了
- ❌ 用"多级记忆 / 短期长期 / 做梦者"这类堆功能的方式打补丁
- ❌ 追求"捕获一切"——捕获越多，信噪比越差
