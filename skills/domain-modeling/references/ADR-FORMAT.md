# ADR 格式

ADR 放在 `docs/adr/` 里，采用顺序编号：`0001-slug.md`、`0002-slug.md`，依此类推。

惰性创建 `docs/adr/` 目录：只在需要第一个 ADR 时才建。

## 模板

```md
# {决策的简短标题}

{1-3 句话：上下文是什么，我们决定了什么，以及为什么。}
```

就这样。一个 ADR 可以只有一段。它的价值在于记录下*做出过*某个决策以及*为什么*，而不在于把各个小节填满。

## 可选小节

只在它们能带来真正价值时才包含这些。大多数 ADR 都不需要。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：当决策会被重新审视时有用
- **Considered Options**：只在被否掉的备选方案值得记住时才写
- **Consequences**：只在有非显而易见的下游影响需要点明时才写

## 编号

扫描 `docs/adr/`，找出已有的最大编号，加一。

## 什么时候提议写 ADR

以下三条必须全部成立：

1. **难以逆转**：以后改主意要付出的代价是实打实的
2. **脱离上下文会让人意外**：未来的读者看着代码会纳闷「他们到底为什么要这么做？」
3. **是一次真正取舍的结果**：确实存在备选方案，而你出于特定理由选了其中一个

如果一个决策很容易逆转，就跳过它：你到时候直接逆转就行了。如果它不让人意外，没人会纳闷为什么。如果根本没有真正的备选方案，那除了「我们做了显而易见的事」之外没什么可记的。

### 什么才算数

- **架构形态。** 「我们用 monorepo。」「写模型是事件溯源（event-sourced）的，读模型投影进 Postgres。」
- **上下文之间的集成模式。** 「Ordering 和 Billing 通过领域事件通信，而不是同步 HTTP。」
- **带锁定效应的技术选型。** 数据库、消息总线、鉴权提供方、部署目标。不是每个库都要记：只记那些换掉要花一个季度的。
- **边界与范围决策。** 「Customer 数据归 Customer 上下文所有；其他上下文只通过 ID 引用它。」明确说「不」和明确说「是」一样有价值。
- **对显而易见路径的刻意偏离。** 「我们用手写 SQL 而不是 ORM，因为 X。」凡是理性读者会假设成反面的事。这些记录能拦住下一个工程师去「修好」一个本就刻意为之的东西。
- **代码里看不见的约束。** 「因为合规要求，我们不能用 AWS。」「因为合作方 API 的合约，响应时间必须低于 200ms。」
- **在否决理由非显而易见时，记下被否掉的备选方案。** 如果你考虑过 GraphQL，却因为一些微妙的理由选了 REST，就把它记下来；否则六个月后会有人又提议 GraphQL。
