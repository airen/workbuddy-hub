# 分流（Triage）

把项目 issue tracker 上的 issue 推进一个由 triage 角色构成的小型状态机。

如果这个仓库把外部 pull request 也当作一种请求面（见 issue-tracker 配置），triage 同样覆盖它们：**一个 PR 就是一个附带了代码的 issue**，使用相同的角色、相同的状态、相同的状态机，只是有几处差异，下面标为「对 PR 而言」。把裸的 `#42` 按 tracker 配置解析成 issue 或 PR。

triage 期间发到 issue tracker 的每一条评论或 issue **必须**以这段免责声明开头：

```
> *This was generated by AI during triage.*
```

## 角色（Roles）

两个**类别（category）**角色：

- `bug`：某个东西坏了
- `enhancement`：新功能或改进

五个**状态（state）**角色：

- `needs-triage`：维护者需要评估
- `needs-info`：等待报告者补充信息
- `ready-for-agent`：已完整规格化，可供 AFK agent 接手
- `ready-for-human`：需要人类实现
- `wontfix`：不会被处理

对一个 PR，同样的状态是针对其附带的代码而言的：`ready-for-agent` 表示已附上简报、agent 应在 diff 上推进下一步；`ready-for-human` 表示已可由人类合并。

每个完成 triage 的 issue 都应当恰好带一个类别角色和一个状态角色。如果状态角色互相冲突，先标记出来并询问维护者，再做别的事。

这些是规范的角色名。issue tracker 里实际使用的标签字符串可能不同。这个映射本应已经提供给你。如果没有，就提示用户运行 `setup-matt-pocock-skills` 技能。

状态转移：一个没有标签的 issue 通常先进入 `needs-triage`；从那里它可以转到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 回到 `needs-triage`。维护者可以随时覆盖；对看起来不寻常的转移，先标记出来并询问再继续。

## 调用方式（Invocation）

维护者调用 `triage` 技能，用自然语言描述想要什么。理解这个请求并执行。例如：

- 「给我看看有什么需要我处理的」
- 「看看 #42」（issue 或 PR）
- 「把 #42 移到 ready-for-agent」
- 「有什么可以让 agent 接手了？」

## 展示需要注意的东西

查询 issue tracker，按从旧到新呈现三个分桶：

1. **无标签**：从未 triage 过。
2. **`needs-triage`**：评估进行中。
3. **`needs-info` 且自上次 triage 记录以来报告者有活动**：需要重新评估。

当 PR 在范围内时，把这些外部 PR 也纳入这些分桶，并给每一行打上 `[PR]` 或 `[issue]` 标签。发现环节只暴露_外部_ PR（tracker 配置定义了谁算外部），所以协作者的进行中 PR 不属于 triage 工作。这个过滤只用于发现；被明确点名的 PR 无论作者是谁都始终 triage。

展示计数和每个条目的一行摘要。让维护者来挑。

## triage 一个具体的 issue 或 PR

1. **收集上下文。** 完整读这个 issue 或 PR（正文、评论、标签、作者、日期；对 PR 还要读 diff）。解析任何先前的 triage 记录，免得重复问已经解决过的问题。用项目的领域术语表（glossary）探索代码库，遵守该区域的 ADR。对代码库跑两项检查：(a) **冗余（redundancy）**：按领域概念（而不只是请求的措辞）搜索所请求行为是否已有实现，并报告你在哪里找过。如果找到，就是一个「已实现」的 `wontfix`（第 5 步）。(b) **先前拒绝（prior rejection）**：读 `.out-of-scope/*.md`，把任何与本次请求相似的都挑出来。

2. **给出建议。** 把你的类别和状态建议连同理由告诉维护者，再附上一段与该请求相关的简短代码库摘要（包括它是否已经实现）。等待指示。

3. **核验这个说法。** 在任何拷问之前，先检查这个说法站不站得住。对 bug，按报告者的步骤复现它。对 PR，确认这个 diff 做了它声称的事：checkout，跑相关测试或命令。报告结果：已确认（附代码路径）、失败，或细节不足（这是很强的 `needs-info` 信号）。一次已确认的核验会让 agent 简报强得多。

4. **拷问（如需要）。** 如果这个请求需要补充成形，依次调用 Skill 工具加载 `grilling` 和 `domain-modeling` 两个技能，一轮问题一轮问题地把它拷问成形，顺手打磨领域术语，并在决策落定时就地更新 `GLOSSARY.md`/ADR。

5. **应用结果：**
   - `ready-for-agent`：发一条 agent 简报评论（[AGENT-BRIEF.md](references/AGENT-BRIEF.md)）。
   - `ready-for-human`：结构与 agent 简报相同，但注明为什么不能委派（需要判断取舍、需要外部访问、涉及设计决策、需要手工测试）。
   - `needs-info`：发 triage 记录（模板见下）。
   - `wontfix` 时关闭这个 issue，评论取决于_为什么_：
     - **已实现**：这个改动已经在代码库里存在了。指出它在哪里；**不要**写入 `.out-of-scope/`（那个知识库是给_被拒绝的_请求用的，不是给已建成的）。
     - **拒绝（bug）**：给一段礼貌的解释，然后关闭。
     - **拒绝（enhancement）**：写入 `.out-of-scope/`，从一条评论链接过去，然后关闭（[OUT-OF-SCOPE.md](references/OUT-OF-SCOPE.md)）。
   - `needs-triage`：应用这个角色。如果有部分进展，可选地留一条评论。

## 快速覆盖状态

如果维护者说「把 #42 移到 ready-for-agent」，相信他们，直接应用这个角色。先确认你将要做什么（角色变更、评论、关闭），再动手。跳过拷问。如果在没有拷问环节的情况下移到 `ready-for-agent`，问一下他们是否想写一份 agent 简报。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- 要点 1
- 要点 2

**What we still need from you (@reporter):**

- 问题 1
- 问题 2
```

把拷问期间解决的一切都记在「established so far」下面，这样工作不会丢。问题必须具体、可执行，而不是「请提供更多信息」。

## 恢复之前的会话

如果这个 issue 或 PR 上已有先前的 triage 记录，读一下它们，检查报告者是否已回答了任何悬而未决的问题，并在继续之前呈现一幅更新后的图景。不要重问已经解决的问题。
