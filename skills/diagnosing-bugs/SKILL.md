# 疑难 bug 诊断（diagnosing-bugs）

一套对付疑难 bug 的纪律。除非有明确正当的理由，否则不得跳过任何阶段。

探索代码库时，读一下 `GLOSSARY.md`（如果存在），以建立相关模块的清晰心智模型，并查看你要触碰那块区域里的 ADR。

## 脱敏（redact）

本技能会让你展示命令、输出和抓取到的产物。**先把所有机密信息脱敏**：在原处写成 `<REDACTED>`。反馈回路要基于环境变量来搭，这样凭据留在环境里，而不是出现在你展示的内容里。抓取到的产物会带着鉴权头：只引用承载信号的那几行。

如果脱敏后的输出不足以诊断这个 bug，就明说，并去问用户。

## 阶段 1：构造反馈回路（feedback loop）

**这才是本技能的核心。** 其余步骤都是机械劳动。只要你能为这个 bug 拿到一个**紧**（tight）的通过/失败信号（一个会在 _这个_ bug 上变红的信号），你就一定能找到根因；二分、假设验证、埋点全都只是在消费这个信号。拿不到它，盯着代码看多久都救不了你。

在这里投入不成比例的精力。**要凶猛，要有创意，不许放弃。**

### 构造反馈回路的方式，大致按这个顺序

1. **失败的测试**，用任何能触达这个 bug 的接缝（seam）：单元、集成、端到端。
2. **curl / HTTP 脚本**，打向一个跑起来的 dev server。
3. **命令行调用**，喂一份固定输入（fixture），把 stdout 跟一份已知正确的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer），驱动 UI 并对 DOM / console / network 做断言。
5. **重放抓取到的 trace。** 把一次真实的网络请求 / 载荷 / 事件日志存到磁盘，隔离地把它在代码路径里重放一遍。
6. **一次性测试台（harness）。** 拉起系统的一个最小子集（单个服务、mock 掉依赖），用一次函数调用就走完出 bug 的那段代码路径。
7. **属性 / 模糊测试回路（property / fuzz loop）。** 如果 bug 是「输出偶尔出错」，就跑 1000 组随机输入，去找那个失败模式。
8. **二分测试台（bisection harness）。** 如果这个 bug 出现在两个已知状态之间（commit、数据集、版本），把「在状态 X 启动、检查、重复」自动化，好让你能 `git bisect run` 它。
9. **差分回路（differential loop）。** 把同一份输入分别跑过旧版本和新版本（或两套配置），diff 输出。
10. **人机协同（HITL）bash 脚本。** 最后手段。如果必须有人来点，就用 `scripts/hitl-loop.template.sh` 去驱动 _他_，这样回路依然是结构化的。抓取到的输出会回喂给你。

把对的反馈回路搭出来，这个 bug 就已经修好 90% 了。

### 把回路收得更紧

把回路当成一个产品来打磨。一旦你有了 _一个_ 回路，就**收紧**它：

- 能更快吗？（缓存初始化、跳过无关的启动、缩小测试范围。）
- 能让信号更锐利吗？（断言具体的症状，而不是「没崩」。）
- 能更确定吗？（固定时间、给 RNG 设种子、隔离文件系统、冻结网络。）

一个 30 秒还时灵时不灵的回路，比没有回路好不了多少；一个 2 秒且确定的回路才算紧，是一把调试超能力。

### 非确定性 bug

目标不是拿到一份干净的复现，而是**更高的复现率**。把触发动作循环 100 次、并行化、加压、收窄时间窗口、注入 sleep。一个 50% 概率 flaky 的 bug 是可调试的；1% 的不是，所以持续抬高复现率，直到它变得可调试。

### 当你确实构造不出回路时

停下来，明确说明。列出你试过什么。向用户要：(a) 能复现它的那个环境的访问权限，(b) 一份脱敏后的抓取产物（HAR 文件、日志转储、core dump、带时间戳的录屏），或 (c) 允许你临时加生产环境埋点。**没有回路，不许**进入假设阶段。

### 完成标准：一个能变红的紧回路

当回路既**紧**又**能变红**时，阶段 1 才算完成：你能说出**一条命令**（一个脚本路径、一次测试调用、一条 curl），而且你**已经至少跑过它一次**（展示这次调用和它的输出，脱敏后），并且它满足：

- [ ] **能变红**：它走的是真正出 bug 的那段代码路径，断言的是**用户描述的确切症状**，所以它能在这个 bug 上变红、在修复后变绿。不是「能跑不报错」；它必须能 _抓住这个特定的 bug_。
- [ ] **确定**：每次运行结论一致（flaky bug：按上文，固定一个高复现率）。
- [ ] **快**：秒级，不是分钟级。
- [ ] **代理可运行**：你能无人值守地跑它；只有在用 `scripts/hitl-loop.template.sh` 时才需要人介入。

如果你发现自己在命令还不存在时就已经在读代码构建理论，**停下：直接跳到假设，正是本技能要防的那种失败。** 没有能变红的命令，就没有阶段 2。

## 阶段 2：复现 + 最小化

运行回路。看着它随着 bug 出现而变红。

确认：

- [ ] 回路产生的失败模式就是**用户**描述的那个，而不是碰巧挨着的另一个失败。搞错 bug = 修错东西。
- [ ] 这个失败在多次运行中可复现（或者，对非确定性 bug，复现率高到足以据以调试）。
- [ ] 你已经抓下了确切的症状（报错信息、错误输出、慢下来的耗时），好让后续阶段能验证修复确实解决了它。

### 最小化

一旦它变红，就把复现缩小到**仍会变红的最小场景**。**一次砍一个**输入、调用方、配置、数据、步骤，每砍一刀就重跑回路，只留下对这个失败真正承重的部分。

为什么要费这个劲：最小复现会缩小阶段 3 的假设空间（剩下可怀疑的活动部件更少），并成为阶段 5 里那份干净的回归测试。

当**剩下的每一个元素都承重**时才算完成：去掉其中任何一个，回路都会变绿。

在既完成复现**又**完成最小化之前，不得继续。

## 阶段 3：假设

在验证任何一个之前，先产出 **3–5 个排好序的假设**。只生成一个假设，会让你锚定在第一个看起来合理的点子上。

每个假设都必须**可证伪**：说清它作出的预测。

> 格式：「如果 <X> 是原因，那么 <改动 Y> 会让 bug 消失 / <改动 Z> 会让它更糟。」

如果你说不出这个预测，那这个假设就是一种感觉：丢掉它，或者把它磨利。

**在验证之前，把排好序的清单给用户看。** 他们往往带着领域知识，能瞬间重排（「我们刚给第 3 个上线了一个改动」），或者知道哪些假设已经被排除。这是个便宜的检查点，能省大把时间。但不要卡在这里；如果用户不在（AFK），就按你自己的排序往下走。

## 阶段 4：埋点（instrument）

每个探针都必须对应阶段 3 里某个具体的预测。**一次只改一个变量。**

工具偏好：

1. **调试器 / REPL 检查**，如果环境支持。一个断点胜过十条日志。
2. **定点日志**，打在能区分各个假设的边界上。
3. 绝不要「把所有东西都打日志然后 grep」。

**给每条调试日志打上标签**，用唯一前缀，例如 `[DEBUG-a4f2]`。这样最后的清理就变成一次 grep。没打标签的日志会留在代码里；打了标签的都会死掉。

**性能分支。** 对性能回退，日志通常是错的工具。改用：先建立一个基线测量（计时测试台、`performance.now()`、profiler、查询计划），再做二分。先测量，后修复。

## 阶段 5：修复 + 回归测试

**在修复之前**写回归测试，但前提是存在一个**正确的接缝（seam）**。

正确的接缝是指：测试能在这个接缝上跑出**真正的 bug 模式**，就像它在调用点发生的那样。如果唯一可用的接缝太浅（bug 需要多个调用方，你却在单调用方上测；单元测试复现不了触发 bug 的那条链路），在那上面写回归测试只会带来虚假的信心。

**如果不存在正确的接缝，这本身就是发现。** 把它记下来。是代码库的架构在阻止这个 bug 被锁定。为下一阶段标记出这一点。

如果存在正确的接缝：

1. 把最小化后的复现变成该接缝上一个失败的测试。
2. 看着它失败。
3. 应用修复。
4. 看着它通过。
5. 针对原始的（未最小化的）场景重跑阶段 1 的反馈回路。

## 阶段 6：清理

宣布完成之前必须做到：

- [ ] 原始复现不再复现（重跑阶段 1 的回路）
- [ ] 回归测试通过（或者已记录「没有接缝」这一事实）
- [ ] 所有 `[DEBUG-...]` 埋点都已移除（`grep` 那个前缀）
- [ ] 一次性原型已删除（或移到一个明确标记的调试位置）
- [ ] 最终证明正确的那个假设写进了 commit / PR 信息里，好让下一个调试的人学到东西
