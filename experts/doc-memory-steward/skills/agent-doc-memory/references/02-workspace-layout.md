# 02 · 文档工作区的结构

> 这一篇定义"脑"长什么样：六类文档各是什么、放在哪、什么判据算合格。建脑（第 1 步）和查脑（第 2 步）时读它。

## 全景

```text
<project>/
└── docs/                      ← 优先跟随项目既有文档目录；没有才用 docs/
    ├── INDEX.md               ← ① 索引：唯一入口
    ├── conventions.md         ← ② 指令：项目怎么干活
    ├── glossary.md            ← ③ 术语：这个词指什么
    ├── specs/                 ← ④ 规格：要做什么
    │   ├── <feature-a>.md
    │   └── <feature-b>.md
    ├── decisions/             ← ⑤ 决策：为什么这么做
    │   ├── 0001-<slug>.md
    │   └── 0002-<slug>.md
    └── research/              ← ⑥ 调研：学到什么
        ├── <library>.md
        └── <api>.md
```

**目录名可以变，六类不能缺。** 项目已有 `docs/`、`doc/`、`documentation/`、`.github/` 就跟着走；已有 `adr/` 就把它当 `decisions/` 用，不要另建一份。**唯一的硬要求是有一个能查到全部文档的索引。**

---

## ① INDEX.md — 索引

**唯一入口。** Agent 每轮任务的第一件事就是读它。它解决的是"不知道自己不知道"：不读它，agent 就只能凭运气猜项目里有什么知识。

**必须包含**：每份文档的**路径**、**一句话说明**、**状态**、**最后更新**。

```markdown
# 项目文档索引

> 干活前先读本文件。新建 / 删除文档后必须回来更新。

## 约定与术语
| 文档 | 说明 | 状态 | 更新 |
|---|---|---|---|
| [conventions.md](conventions.md) | 代码风格、分支、提交、评审流程 | 现行 | 2026-10-06 |
| [glossary.md](glossary.md) | 项目术语表 | 现行 | 2026-10-01 |

## 规格
| 文档 | 说明 | 状态 | 更新 |
|---|---|---|---|
| [specs/order-export.md](specs/order-export.md) | 订单导出：目标、边界、验收 | 现行 | 2026-10-05 |

## 决策
| 文档 | 说明 | 状态 | 更新 |
|---|---|---|---|
| [decisions/0001-postgres-over-mongo.md](decisions/0001-postgres-over-mongo.md) | 选 PostgreSQL 而非 MongoDB | 现行 | 2026-09-20 |
| [decisions/0002-jwt-session.md](decisions/0002-jwt-session.md) | 移动端改用 JWT | 已废弃 | 2026-10-02 |

## 调研
| 文档 | 说明 | 状态 | 更新 |
|---|---|---|---|
| [research/stripe-webhook.md](research/stripe-webhook.md) | Stripe Webhook 验签与重试 | 现行 | 2026-09-28 |
```

**判据**：

- 每条链接**都指向存在的文件**（用 `scripts/doc_audit.py` 查断链）
- 项目里**没有**不在索引里的 `.md` 文档（除了代码注释性的 README；用脚本查孤儿）
- 状态列用固定三个词：`现行` / `过期` / `已废弃`

## ② conventions.md — 指令

**在这个项目里活该怎么干。** 这是见效最快的一份文档——写一次，之后每个任务都省一轮解释。

**内容范围**：

- 代码风格与结构约定（目录怎么分、命名怎么起、模块边界）
- 工作流约定（分支模型、提交信息、评审流程、发布节奏）
- 技术约束（必须用的 / 禁止用的、兼容性要求）
- 边界与红线（哪些文件不许动、哪些操作要先问）
- 常见任务的"标准动作"（加一个接口要动哪几个文件）

**每条都要有"为什么"**，否则它只是一堆命令，下次遇到例外情况 agent 不知道怎么变通。

```markdown
## 目录约定
- 业务逻辑只放 `src/domain/`，HTTP 层只做参数校验与序列化。
  **为什么**：之前逻辑散在 controller 里，改一个规则要翻 5 个文件。
  **例外**：一次性脚本可以内联。
```

详见 [templates/conventions.md](../templates/conventions.md)。

## ③ glossary.md — 术语

**这个词在本项目里指什么。** 项目里的黑话、被重载的通用词、领域专有名词——不定义，agent 就会按"通用含义"理解，然后做错。

**每条要写"不指什么"**，这是它区别于字典的地方：

```markdown
### 订单（Order）
- **指**：用户提交的一次购买意图，含多个商品行。
- **不指**：`order` 表里的一行（那是 `OrderItem` 的聚合根，命名有历史遗留）。
- **别称**：老代码里叫 `Purchase`，看到就按 Order 理解。
```

详见 [templates/glossary.md](../templates/glossary.md)。

---

## ④ specs/ — 规格

**要做什么、不做什么、怎么算完成。** 一份规格 = 一个功能 / 一次改动。

**三要素**（缺一个就不算规格）：

1. **目标**：解决什么问题、给谁用、成功长什么样
2. **边界（不做清单）**：明确写清**这次不做什么**——这是防止范围蔓延最有效的一行字
3. **验收标准**：可判定的完成条件（不是"体验流畅"，是"导出 1 万行在 10 秒内完成"）

详见 [templates/spec.md](../templates/spec.md)。

## ⑤ decisions/ — 决策

**为什么这么做、放弃了什么。** 这是**代码里永远读不出来**的部分，也是三个月后最值钱的部分。

**编号 + 一页一决策。** 文件名 `NNNN-短横线-slug.md`（`0001-postgres-over-mongo.md`）。

**必写四项**：

1. **背景**：什么情况逼着我们要做这个决定
2. **备选**：至少 2 个（含"什么都不做"），各自代价
3. **决定**：选了谁 + 理由
4. **代价与重估触发点**：失去了什么、出现什么信号就该回头改

第 4 项是决策记录的灵魂。**说不出代价的决策记录，等于没写。**

详见 [templates/decision.md](../templates/decision.md)。

## ⑥ research/ — 调研

**某个库 / API / 第三方怎么用、坑在哪。** 一次调研，下次直接复用，不用重新踩坑。

**结论先行**——因为下次读者是带着具体问题来的：

```markdown
# Stripe Webhook 接入

**结论**：用 `stripe.webhooks.constructEvent` 验签；必须用 **raw body**，
Express 的 `express.json()` 会破坏签名（这是最常见的坑）。
**最小示例**：……
**坑**：① 重试是 at-least-once，业务要幂等；② 测试环境的签名密钥和线上不同。
```

详见 [templates/research.md](../templates/research.md)。

## 可选：log/ — 工作日志

**按天的追加式笔记**，只记"有跨会话价值"的东西，不记流水账。

**什么时候需要**：项目很长、任务很碎、你希望保留"这段时间在忙什么"的粗粒度线索。

**什么时候不需要**：任务本身有规格 / 决策文档承载，日志只会变成噪音。**默认不建**，需要时再建。

> 注意：日志是**追加**的（append-only），永远不改历史；其余五类都是**就地更新**的。别把日志当主力。

## 命名与编号约定

| 类型 | 命名 | 例 |
|---|---|---|
| 索引 / 约定 / 术语 | 固定名 | `INDEX.md`、`conventions.md`、`glossary.md` |
| 规格 | 功能名，短横线 | `specs/order-export.md` |
| 决策 | 四位编号 + slug | `decisions/0007-drop-legacy-auth.md` |
| 调研 | 主题名 | `research/stripe-webhook.md` |

**决策编号只增不减**。废弃一个决策就把它状态改成 `已废弃`，**不要删文件、不要复用编号**——历史记录的价值就在于它没被抹掉。

## 和项目既有文档的关系

**不要另起一套并行的体系。** 建脑时按这个顺序处理现有文档：

| 现状 | 做法 |
|---|---|
| 已有 `docs/` 且有索引 | 直接用，缺哪类补哪类 |
| 已有 `docs/` 但没索引 | 建 `INDEX.md` 把现有文档登记进去 |
| 已有 `AGENTS.md` / `CLAUDE.md` | 保留，把"先查后更新"的硬指令写进去；它不属于六类，是 agent 的行为约束 |
| 已有 `adr/` | 当 `decisions/` 用 |
| 文档散落在各处（README、wiki 导出、Notion 导出） | 先登记进索引（可指向外部链接），不急着搬 |
| 只有代码注释 | 别搬注释。只写代码里读不出来的东西（为什么、边界、教训） |

**索引可以先"指向"而不是"搬入"**——先把知识地图建立起来，搬迁是后来的事。
