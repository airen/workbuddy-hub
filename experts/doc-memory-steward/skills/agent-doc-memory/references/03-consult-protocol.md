# 03 · 查脑协议

> 每个任务开工前执行。**这是本技能与"凭记忆干活"的分界线。**

## 五步

### 1. 读索引（永远第一步）

读 `INDEX.md`（或项目等价的文档清单）。**不是搜索，是通读。** 索引通常只有几十行，读完它你就知道这个项目里有哪些知识。

> 如果项目没有索引 → 走建脑流程（见 [07-bootstrap.md](07-bootstrap.md)），不要跳过直接干。

### 2. 挑相关文档，读全文

从索引里挑出与本次任务相关的 **1–3 份**，**读全文**。

**这是与 RAG 的根本差别**：你拿到的是完整语境（动机、代价、边界、例外），不是"最相似的五个片段"。一份决策记录里的"我们放弃了 X，因为 Y"，比十条相关片段加起来都有用。

挑选优先级：

1. `conventions.md` —— 几乎总是要读（它约束你怎么干活）
2. `decisions/` 里与本次改动相关的决策 —— **尤其是你没参与过的那些**
3. `specs/` 里对应的规格 —— 确认边界与验收标准
4. `research/` 里相关的调研 —— 别重复踩坑
5. `glossary.md` —— 任务涉及项目黑话时

### 3. 查不到 → 记录"新领域"

索引里没有相关文档，**不要硬找**，也不要停下任务。做两件事：

- 记一句：**「未找到相关文档，按代码现状与常识处理」**（建议写进回复）
- 收尾时把这次产生的新知识**补成文档**（第 4 步更新协议会提醒你）

**"查不到"本身就是有价值的信息**：它告诉你这个项目有一块知识是空的。**这个洞，就是下次别人（或你）会再次踩的地方。**

### 4. 文档与现实不符 → 以现实为准，顺手修

读文档时发现它和代码 / 现状不一致（描述的功能已经删了、约定已经改了、决策已经被推翻）：

- **不要"将就着用"**，也不要两边都信
- **以现实为准**：按代码 / 现状干活
- **顺手把文档改对**，或把它状态改成 `已废弃` 并写清被谁取代

> 留着错的文档比没有文档更糟——它会被当成真相。**修文档的成本此刻最低**（你正好在读它、上下文正好在）。

### 5. 声明依据

在回复里用一句话说明你查了什么、依据是什么：

- ✅「按 `decisions/0003-分库方案.md`，我们约定按用户 ID 分片，所以这次我按 16 片实现。」
- ✅「未找到相关文档，我按现有 `src/auth/` 的写法保持一致。」
- ❌（什么都没说，直接开始写代码）

**这一句让"查了"从不可验证的自称，变成可验证的行为。** 用户看到你能引用具体文档，就知道你没在瞎猜；如果你引错了，用户也能立刻纠正。

---

## 反面：不要这样做

| 不要 | 为什么 |
|---|---|
| 凭"我记得项目里好像是……"就动手 | 记忆会过期，而且你无法区分"记得"和"猜" |
| 用关键词搜索代替读文档 | 搜到的是片段，丢掉的是动机与边界 |
| 索引里有相关文档但没读 | 你等于在重新发明一个已经定过的决定 |
| 发现文档过期却照旧用 | 你在复制一个已知的错误 |
| 发现文档过期却不管 | 下一个人还会踩 |
| 查不到就停下来问用户"有没有文档" | 先按现状干，收尾补文档；不要用这个当借口阻塞任务 |

---

## 什么时候可以跳过查脑

- **一次性小任务**：改 typo、跑个脚本、问个概念 —— 没有跨会话价值，跳过
- **项目还没有文档工作区，且本次任务很小** —— 跳过；但任务不小的话，先花五分钟建最小索引

**判据**：这次任务会不会有"下次还要知道"的东西？会 → 查（并收尾更新）；不会 → 可以直接干。

## 给 agent 的自我检查（开工前默问）

1. 我读过这个项目的 `INDEX.md` 了吗？
2. 有没有一份决策记录，会让我现在这个做法变成"重复讨论"或"违反约定"？
3. 我这次要用到的那个第三方库 / API，项目里有没有人调研过？
4. 我用到的术语，在本项目里和通用含义一样吗？
5. 我能不能用一句话说出"我依据的是哪份文档"？

任何一条答"没有 / 不能" → 回去补。
