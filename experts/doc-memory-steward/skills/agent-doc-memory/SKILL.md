# 文档即记忆

**核心判断**：Agent 记不住你的项目，不是"记忆容量"问题，是**知识没有落在可读、可改、可提交的地方**。

市面上的记忆插件都在解同一道错题：把对话切成片段塞进向量库，每次提示检索最相似的几条注入，再给 agent 一个搜索工具去翻旧账。这套架构建立在"agent 会遗忘，所以要帮它记住过去"的假设上——于是它捕获得更多、索引得更好、检索得更聪明，却始终回答不了一个问题：**哪一条是对的、是当前的、是完整的？**

没有任何其他领域是这么处理知识的。没人会为了回忆某个功能的约束，去重看三年前的一场会议录像。人们**把事情写下来，然后用那些记录**。

所以正确做法不是给 agent 一个检索工具，而是给它一个**文档工作区**——一个 Markdown 大脑：干活前先查，干完再更新。

> 工作循环从 `prompt → build → forget` 变成 `prompt → consult → build → update`。
> 记忆从一个硬接到 agent 上的向量数据库，变成一个**你可以读、可以改、可以提交、可以和团队分享**的工作区。

## 什么时候用

出现下面任何信号，主动加载本技能，**不要等用户说"帮我建个知识库"**：

- 用户抱怨 agent 的记忆：「记不住项目」「每次都要重新解释一遍」「上次说好的又忘了」「同一个坑踩三次」「换个会话就失忆」「它不知道我们之前定过什么」
- 用户要建立**长期上下文**：AGENTS.md、CLAUDE.md、项目文档、知识库、团队共享上下文、跨会话记忆
- 用户明确提到**记忆方案**：「记忆插件」「RAG 记忆」「向量库记忆」「Embedding」「记忆系统」「Operator Memory」「Agent 不需要记忆，它们需要文档」
- 用户要**接手 / 交接一个项目**，或要新人（或新 agent）能读懂项目为什么是现在这样
- **你自己**出现下面情形时（最主要触发点）：
  - 即将在一个项目里开始**跨会话的长期工作**（改一处、下次还要改）
  - 你**做了一个有取舍的决策**（选了 A 放弃 B），或**定下/改了一条约定**
  - 你**搞清楚了一个第三方库 / API / 工具**的用法或坑
  - 你**写了规格或计划**，或需求发生了变更
  - 你**澄清了一个术语**在本项目里的确切含义
  - 你**发现文档与代码 / 现实不一致**（顺手修掉）
  - 你要动手时发现**不知道该问谁**（说明该有文档）

## 不适用

- **一次性的、无后续的小任务**（问个概念、跑个脚本、改个 typo）→ 不需要建工作区，直接干
- **外部海量非结构化语料**（产品手册、法规全文、论文库）→ 这类**该用 RAG**，见 [references/01-why-not-recall.md](references/01-why-not-recall.md) 的「什么时候召回仍然是对的」
- **只读的、没有写权限的场景** → 本技能的立足点是"能改"，不能写就没有意义
- 用户只是想要一段"记忆方案科普" → 直接回答即可，不要强行建目录

## 四条铁律

1. **先查后干。** 任何任务开工前，先读 `INDEX.md`，按索引读出相关文档。**不许凭记忆猜项目约定**——猜错一次，代价比读三份文档高得多。
2. **干完就更新，趁热。** 整幅图还在上下文里的时候更新：过期就改、缺了就补、新增就登记。**更新完必须同步索引**，否则下次等于没写。
3. **文档是给人看的。** 纯 Markdown、进 git、能 diff、能 review、能分享。**不能读、不能改、不能提交的"记忆"不算记忆。** 同事（和下一个 agent）都该读得懂。
4. **写"为什么"，不写"是什么"。** 代码已经记录了"是什么"。文档的价值在**动机、代价、边界、教训**——这些代码里读不出来。

> 第 5 条藏在上面的反面：**没有就不写。** 一次任务没产生新知识，就明确说「本次无文档更新」。**为写而写是另一种噪音**，和"什么都往向量库里塞"是同一个病。

## 工作流（五步）

### 第 0 步：判断有没有"脑"

先找项目里有没有**文档索引**（`INDEX.md`，或已有的 `docs/README.md`、`AGENTS.md` 里的文档清单）。

- **有** → 直接进第 2 步查脑
- **没有** → 进第 1 步建脑（**只做一次**）

> 判断依据是"有没有一个能查到全部文档的入口"，不是"有没有 md 文件"。散落的十几个 README 不构成一个脑。

### 第 1 步：建脑（没有时才做）

**第一步不是新建目录，是先找现有文档**：README、`docs/`、`AGENTS.md`、`CLAUDE.md`、wiki 导出、接口文档、会议纪要。**把已有的登记进索引，不要另起一套。**

按下面六类补齐（结构与判据见 [references/02-workspace-layout.md](references/02-workspace-layout.md)）：

```text
<project>/
└── docs/                      ← 优先跟随项目既有文档目录；没有才用 docs/
    ├── INDEX.md               ← ① 索引：唯一入口，列全部文档 + 一句话 + 状态 + 最后更新
    ├── conventions.md         ← ② 指令：项目怎么干活（风格 / 流程 / 边界 / 禁止项）
    ├── glossary.md            ← ③ 术语：这个词在本项目里指什么
    ├── specs/                 ← ④ 规格：要做什么、边界在哪、怎么算完成
    │   └── <feature>.md
    ├── decisions/             ← ⑤ 决策：为什么这么做、放弃了什么、何时该重估
    │   └── 0001-<slug>.md
    └── research/              ← ⑥ 调研：某个库 / API / 第三方怎么用、坑在哪（可复用）
        └── <topic>.md
```

**起步顺序**（不要一次建全，会烂尾）：① 先建 `INDEX.md` 把现有文档登记进去 → ② 写 `conventions.md`（最容易见效）→ ③ 补最近一次重大决策 → ④ 之后每次任务自然生长。

可以直接用脚本脚手架：

```bash
python3 scripts/init_doc_brain.py <项目根目录>          # 建骨架（已存在的文件不覆盖）
```

**最后一步必须做**：在 `AGENTS.md` / `CLAUDE.md`（或等效的 agent 指令文件）里写一条**硬指令**，把"先查后更新"钉死。否则这套工作区下一轮就没人读了。模板见 [templates/conventions.md](templates/conventions.md) 末尾。

### 第 2 步：查脑（每个任务开工前）

1. **读 `INDEX.md`**——永远第一步。它告诉你这个项目里有哪些文档、各自状态如何。
2. **按索引挑出与本次任务相关的 1–3 份，读全文**。不是搜关键词，是**读文档**——这正是它与 RAG 的根本差别：你拿到的是完整语境，不是最相似的五个片段。
3. **索引里没有相关文档** → 明确记下「这是新领域，干完补文档」，然后按常识 + 代码现状干。
4. **文档与代码 / 现实不符** → **以现实为准**，顺手把文档改对。文档过期不是"将就着用"的理由，是"现在就修"的信号。
5. **声明你查了什么**：在回复里用一句话说明依据（「按 `decisions/0003-分库方案.md`，我们约定……」）。这让"查了"变成可验证的行为。

详见 [references/03-consult-protocol.md](references/03-consult-protocol.md)。

### 第 3 步：干活

查到的约束就是**硬约束**。如果这次任务需要突破某条已记录的约定或决策，**不能默默突破**——要显式提出：「这违反 `decisions/0003`，要么改做法，要么我们更新那条决策」，让用户裁决。

### 第 4 步：更新脑（收尾必做）

趁整幅图还在上下文里，做**三问**：

1. 这次有没有产生**下次还需要知道**的东西？
2. 有没有**推翻或修正**了已有文档？
3. 有没有出现**该新建文档的新领域**？

任一为"有" → 更新 / 新建对应文档，**并同步 `INDEX.md`**。
三问全为"否" → **明确说「本次无文档更新」**。不要为写而写。

**什么时候必须写**（这是 agent 最缺的判据，逐条对照）：

| 触发事件 | 写到哪 | 至少包含 |
|---|---|---|
| 定下 / 改变一条**约定**（命名、目录、分支、评审、测试策略） | `conventions.md` | 规则 + 为什么 + 例外 |
| 做了一个**有取舍的决策** | `decisions/NNNN-*.md` | 备选、选了谁、**放弃了什么代价**、何时该重估 |
| 搞清楚**第三方库 / API / 工具**的用法或坑 | `research/<topic>.md` | 结论先行、最小可用示例、坑与规避 |
| 写了**规格 / 计划**，或需求变更 | `specs/<feature>.md` | 目标、边界（不做什么）、验收标准 |
| **澄清了一个术语**的歧义 | `glossary.md` | 词 + 本项目定义 + 不指什么 |
| 发现**文档过期** | 原文档 | 就地改对（或标 `已废弃`） |
| 踩了一个**坑并找到根因** | `research/` 或 `decisions/` | 现象、根因、怎么避免复发 |

**不写**：流水账、每次运行的日志、能从代码直接读出来的东西、临时的调试过程、还没定论的想法（除非显式标 `草稿`）。

详见 [references/04-update-protocol.md](references/04-update-protocol.md)。

### 第 5 步：审计（有信号时）

因为全是 Markdown，**它天然可审计**——这是召回式记忆做不到的。出现下列信号就跑一次：

- 感觉"文档越来越乱、没人看" → 查**孤儿文档**（不在索引里的）和**断链**
- 隔了很久回来接手 → 查**过期文档**（长时间未动且领域变动频繁）
- 文档与代码打架 → 查**冲突**（以现实为准，改文档）

```bash
python3 scripts/doc_audit.py <项目根目录>        # 孤儿 / 断链 / 过期 三类问题一次报出
```

详见 [references/06-audit-and-maintenance.md](references/06-audit-and-maintenance.md)。

## 六类文档速查

| # | 文档 | 回答的问题 | 状态判据 |
|---|---|---|---|
| ① | `INDEX.md` | 这个项目有哪些文档、先读哪个？ | 每条都指向存在的文件 |
| ② | `conventions.md` | 在这个项目里活该怎么干？ | 每条都有"为什么"，不是命令堆砌 |
| ③ | `glossary.md` | 这个词在本项目里指什么？ | 有"不指什么"的反面定义 |
| ④ | `specs/` | 要做什么、不做什么、怎么算完成？ | 有明确的不做清单与验收标准 |
| ⑤ | `decisions/` | 为什么这么做、放弃了什么？ | 有备选方案与重估触发点 |
| ⑥ | `research/` | 这个库 / API 怎么用、坑在哪？ | 结论先行，可被下次直接复用 |

## 好文档的四条判据

1. **为什么 > 是什么。** 只写"是什么"的文档，代码里已经有了，没人会读第二遍。
2. **一份文档一个主题，标题即结论。** 能被一句话引用（「见 `decisions/0003`」），才算有用。
3. **开头写清状态**：`状态: 现行 | 过期 | 已废弃` + `最后更新: YYYY-MM-DD` + `适用范围`。**留着错的文档比没有文档更糟**——它会被当成真相。
4. **不抄代码，只指位置。** 写 `src/auth/session.ts` 的 `refresh()`，不要粘贴实现。抄来的代码第二天就过期了。

## 反模式（出现任一条，说明你走回了老路）

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 建向量库 / 嵌入 / 摘要器 / 后台守护进程 | 这正是本技能要替代的东西 | 就是 Markdown 文件 |
| 把对话日志原样倒进文档 | 噪音，没人读 | 只写提炼后的结论与动机 |
| 追求"捕获一切" | 捕获越多，信噪比越差 | 只写"下次还需要知道"的 |
| 文档里复制代码 | 第二天就过期，且开始说谎 | 指路径与符号名 |
| 一次建 50 篇文档 | 必然烂尾，没人维护 | 从 INDEX + conventions 起步，按需生长 |
| 只写"是什么" | 与代码重复，无增量价值 | 写动机、代价、边界、教训 |
| 文档和代码各说各话 | 错的文档比没有更危险 | 发现不一致立即以现实为准修文档 |
| 写完全不同步 INDEX | 下次等于没写 | 每次更新都同步索引 |

## 输出规范

- **建脑时先盘点再动手**：先列出找到的现有文档，再决定登记与新建，**不要另起一套并行体系**
- **落盘到项目里**：默认 `docs/`（项目已有文档目录就跟随），**不要写到工作区外的临时位置**
- **每次任务开头声明依据**：一句话说明查了哪几份文档；没有相关文档也要说「未找到相关文档，按现状处理」
- **每次任务收尾声明更新**：一句话说明更新了什么、或明确说「本次无文档更新」
- **更新要能 diff**：改已有文档时**就地修改**，不要追加"补充说明（二）"；让 git 历史承载演变
- **索引是唯一入口**：新建 / 删除文档必须同步 `INDEX.md`，否则视为未完成
- **语言跟随用户**；用户用中文就用中文

- 本技能是**面向 agent 的可执行化封装**：把原文的判断转成可触发的行为约束、六类文档的结构判据、查 / 更新两份协议、审计脚本与可填空模板。**内容按本技能自己的口径重写与扩充，无第三方代码依赖、无原文照抄**。
- 「六类文档」「五步工作流」「三问」「更新触发事件表」「反模式表」「审计脚本」为本技能原创补充。
