# 07 · 分布式系统

> 本模块解决：**CAP 到底怎么用？一致性模型怎么选？故障了怎么办？共识是什么？**

## 0. 先记住：分布式系统是**权衡机器**，不是"更强的单机"

**分布式的唯一理由是：单机做不到的事。** 比如：
- 超出单机容量（存储/吞吐）
- 需要地理分布（低延迟、合规）
- 需要高可用（单机故障不影响整体）

**而它带来的代价是全部的新问题**：网络不可靠、时钟不同步、部分失败、一致性难题、排障困难。

> **判据**：**"如果单机能做，就不要分布式。"** 这是最重要的分布式架构决策。

## 1. CAP 定理的正确理解

### 1.1 定义

在一个分布式系统中，以下三者**最多同时满足两个**：

| 字母 | 含义 |
|------|------|
| **C** Consistency（一致性） | **线性一致性**（Linearizability）：所有节点看到同一份最新数据 |
| **A** Availability（可用性） | **每个非故障节点**都必须在**有限时间**内响应（不保证是最新数据） |
| **P** Partition Tolerance（分区容忍） | 网络分区（节点间消息丢失/延迟）时系统仍能工作 |

### 1.2 ⚠️ 最常见的误读

**误读 1**："三选二"。**实际上 P 不是可选项。**

> **网络分区是客观事实，不是设计选择。** 你无法"选择不要 P"。所以真正的选择是：**当分区发生时，你要 C 还是 A？**
> → 正确的表述是 **"CP 或 AP"**，而不是"三选二"。

**误读 2**："CAP 的 C 是 ACID 的 C"。**不是。** CAP 的 C 是**线性一致性**（最强的分布式一致性），ACID 的 C 是**约束不被违反**。两者完全不同的概念。

**误读 3**："分区很罕见，可以忽略"。**分区比你想象的频繁**：GC 停顿、网络抖动、交换机重启都会造成短暂分区。**在分区期间的行为，决定了系统的性质。**

### 1.3 CP vs AP 的实际含义

| | CP（保一致，牺牲可用） | AP（保可用，牺牲一致） |
|---|---------------------|---------------------|
| 分区时 | 拒绝服务或阻塞（保证不返回旧数据） | 继续服务（可能返回旧数据） |
| 例子 | ZooKeeper、etcd、Consul、HBase、MongoDB(默认) | Cassandra、DynamoDB、Riak、Eureka |
| 适合 | 配置管理、选主、金融账本 | 购物车、社交 Feed、库存展示 |

**注意**：**很多系统是可调的**（如 Cassandra 的 Quorum 级别）。CAP 是**系统在分区时的行为描述**，不是永久的标签。

### 1.4 PACELC —— 比 CAP 更实用的模型

**CAP 只描述分区时（P）的选择。但分区是少数时间，正常运行时（E = Else）也有取舍：**

```
PACELC:
  当 Partition 发生时 → 在 A 和 C 之间选（PAC）
  Else（正常运行时） → 在 Latency 和 C 之间选（ELC）
```

| 系统 | PAC | ELC |
|------|-----|-----|
| DynamoDB / Cassandra | PA（保可用） | EL（保延迟，牺牲一致） |
| BigTable / HBase | PC（保一致） | EC（保一致，牺牲延迟） |
| MongoDB | PC | EC |
| 多数 SQL 主从 | PC | EC（同步复制时） |

**PACELC 的价值**：**它提醒你，即使没有分区，强一致也要付出延迟代价。** 大多数时候你在做的是 **延迟 vs 一致性**的取舍，而不是可用性。

## 2. 一致性模型与 Quorum

### 2.1 一致性谱系（从强到弱）

| 模型 | 含义 | 例子 |
|------|------|------|
| **线性一致 Linearizability** | 所有操作看起来像在单一时间点原子发生（最强） | etcd、ZooKeeper |
| **顺序一致 Sequential** | 所有节点看到相同的操作顺序，但不要求实时 | — |
| **因果一致 Causal** | 有因果关系的操作保持顺序，无因果的可乱序 | MongoDB 会话因果一致性 |
| **读己之写 Read-Your-Writes** | 能读到自己写的数据 | 会话粘性 |
| **单调读 Monotonic Reads** | 不会读到比之前更旧的数据 | 会话绑定同一副本 |
| **最终一致 Eventual** | 停止写入后，最终所有副本一致 | DNS、Cassandra、S3 |

**关键洞察**：
- **大多数业务其实不需要线性一致**，只需要"读己之写"或"因果一致"
- **用户能感知的不一致**主要是：读不到自己刚写的、数据倒退、看到别人的顺序错乱
- **会话级一致性（Session Guarantees）** 往往就够用了，且成本远低于全局强一致

### 2.2 Quorum（法定人数）

**在有 N 个副本的系统中，读写需要满足一定数量的副本确认。**

```
W = 写入需要确认的副本数
R = 读取需要查询的副本数
N = 副本总数

若 W + R > N  → 读写集合必有交集 → 强一致（读到最新写入）
```

| 配置 | 效果 |
|------|------|
| W=N, R=1 | 写慢读快，强一致但写可用性差 |
| W=1, R=N | 写快读慢 |
| W=多数, R=多数 | 平衡（N=3 时 W=2,R=2） |
| W=1, R=1 | 最快，但可能读到旧数据（最终一致） |

**可调一致性（Tunable Consistency）**：Cassandra/DynamoDB 允许**每次操作**指定一致性级别（ONE / QUORUM / ALL），从而**按操作**权衡。

**Quorum 的陷阱**：
- **W + R > N 不等于线性一致**（还需要处理并发写冲突、时钟、读修复）
- **多数派写**（W > N/2）防止脑裂时两边都能写
- **读修复（Read Repair）**：读时发现副本不一致就修复
- **反熵（Anti-Entropy）**：后台 Merkle 树比对修复

### 2.3 冲突解决（多主/无主场景）

| 策略 | 说明 |
|------|------|
| **Last Write Wins (LWW)** | 按时间戳取最新 → **会丢数据**，依赖时钟 |
| **版本向量（Version Vector）** | 检测并发写（真并发时需应用层解决） |
| **CRDT** | 可自动合并的数据结构（计数器、集合、序列）→ 无需协调 |
| **应用层合并** | 交给业务逻辑（如购物车取并集） |

**时钟问题**：**分布式系统中的物理时钟不可信**（见 §5）。LWW 在时钟偏移时会静默丢数据。**优先用逻辑时钟（Lamport / 版本向量）或 CRDT。**

## 3. 故障模式、重试与幂等

### 3.1 分布式故障的现实

**部分失败（Partial Failure）**：**一部分组件挂了，另一部分正常——这是分布式系统区别于单机的本质。**

| 故障模式 | 说明 |
|---------|------|
| **崩溃失败 Crash** | 进程/节点停止（最容易处理） |
| **遗漏失败 Omission** | 消息丢失 |
| **时序失败 Timing** | 响应过慢（超时） |
| **拜占庭失败 Byzantine** | 节点返回错误/恶意结果（区块链场景） |
| **网络分区 Partition** | 节点间无法通信 |
| **灰故障 Gray Failure** | 部分降级（如磁盘慢、GC 停顿）——**最难排查** |

### 3.2 超时（Timeout）—— 最基础的弹性手段

**没有超时的调用 = 迟早耗尽线程/连接池。**

| 要点 | 说明 |
|------|------|
| **必须有超时** | 所有网络调用（HTTP、DB、MQ、RPC）都要设超时 |
| **超时预算** | 端到端延迟预算分配到各跳（如总 2s → 各服务 200ms） |
| **超时不是错误** | 超时后请求可能**仍然成功**（结果未知）→ 必须幂等 |
| **级联超时** | 上游超时应**小于**下游，避免上游先超时下游还在跑 |

### 3.3 重试（Retry）—— 必须配套的三件事

**重试是"用流量换可靠性"，但用错会放大故障。**

| 配套 | 说明 |
|------|------|
| **1. 幂等** | 重试会重复执行 → 操作必须幂等（见 `06`） |
| **2. 指数退避 + 抖动（Jitter）** | 避免"重试风暴"同时打过去。`delay = min(cap, base * 2^attempt) * random(0,1)` |
| **3. 重试预算/熔断** | 限制重试次数；配合熔断器，避免对已挂服务持续重试 |

**⚠️ 重试风暴（Retry Storm）**：服务变慢 → 客户端重试 → 流量翻倍 → 服务更慢 → 雪崩。**这是最常见的级联故障原因。**

**只对"可重试"的错误重试**：
- ✅ 超时、连接失败、503、429（配合退避）
- ❌ 400、401、403、404、422（重试无意义，只会浪费）
- ❌ **非幂等操作**（如"创建订单"没有幂等键时）

### 3.4 幂等的实现（再强调）

| 方式 | 说明 |
|------|------|
| 幂等键 + 去重表 | 客户端提供唯一键；服务端记录并返回相同结果 |
| 乐观锁 / 版本号 | `UPDATE ... WHERE version = N` |
| 状态机 | 状态单向流转，重复转换被拒绝 |
| 天然幂等 | 覆盖式写（`SET x = v`）而非增量写（`SET x = x + 1`） |

### 3.5 幂等 + 至少一次 = 实际语义

| 投递语义 | 说明 |
|---------|------|
| **至多一次 At-most-once** | 可能丢，不重复（不可靠） |
| **至少一次 At-least-once** | 不丢，可能重复 → **最常用** |
| **恰好一次 Exactly-once** | 理论上有代价；实际是"至少一次 + 幂等消费" |

> **架构师观点**：**"恰好一次"在业务层面靠"至少一次 + 幂等"实现**，而不是靠基础设施保证。

## 4. 共识机制（Raft 直觉理解）

### 4.1 为什么需要共识

**共识 = 多个节点就某个值达成一致。** 用于：
- **选主（Leader Election）**
- **复制状态机**（所有节点按相同顺序应用相同操作 → 状态一致）
- **分布式配置/元数据**（etcd、ZooKeeper、Consul）

### 4.2 Raft 的三个子问题（直觉版）

| 子问题 | 解决方式 |
|--------|---------|
| **选主 Leader Election** | 节点有随机的选举超时；超时未收到心跳 → 变成候选人 → 拉票；获多数票 → 成为 leader |
| **日志复制 Log Replication** | Leader 接收写请求 → 追加到本地日志 → 复制给 follower → 多数确认后提交 → 通知 follower 提交 |
| **安全性 Safety** | 日志匹配、只允许日志最新的节点当选、提交的条目永不回滚 |

**Raft 的关键机制**：

| 机制 | 说明 |
|------|------|
| **任期 Term** | 逻辑时钟，每次选举 +1；用于拒绝过期 leader |
| **多数派 Majority** | 任何决策需多数节点同意 → 保证只有一个 leader 能提交 |
| **日志索引 + 任期号** | 判断日志新旧；解决冲突时用 leader 的日志覆盖 follower |
| **心跳 Heartbeat** | Leader 定期发心跳维持权威 |

**理解要点**：
- **共识算法保证了"多数派一致"，但代价是"少数派不可用"** → CP 系统
- **N 个节点容忍 (N-1)/2 个故障**（3 节点容忍 1 个，5 节点容忍 2 个）
- **节点数通常是奇数**（3、5、7）——偶数不增加容错能力，只增加延迟
- **跨数据中心共识 = 高延迟**（需要跨地域往返）→ 因此全局强一致系统的写延迟下限是**地理距离**

### 4.3 什么时候**不要**用共识

- **不要把共识用在数据平面**（每次读写都过 Raft = 吞吐灾难）
- **共识用于控制平面**（选主、配置、元数据），数据平面用复制 + Quorum
- **跨地域全局共识会拖慢一切**；考虑**分区自治 + 异步同步**

## 5. 分布式计算的误区（Fallacies of Distributed Computing）

**Sun 的工程师（Peter Deutsch 等）总结的 8 条错误假设：**

| # | 错误假设 | 现实 |
|---|---------|------|
| 1 | 网络是可靠的 | 会丢包、会断、会分区 |
| 2 | 延迟为零 | 跨机房几十 ms，跨洲 100ms+ |
| 3 | 带宽是无限的 | 有限，且传输大数据会阻塞 |
| 4 | 网络是安全的 | 内网也会被入侵（零信任） |
| 5 | 拓扑不会变 | 节点增减、扩缩容、迁移是常态 |
| 6 | 只有一个管理员 | 多团队、多供应商 |
| 7 | 传输成本为零 | 跨区流量要钱、要时间 |
| 8 | 网络是同质的 | 混合云、多厂商、不同 MTU/协议 |

**架构含义**：
- 每一条都对应一类必须处理的失败模式
- **"网络调用 = 可能失败 + 有延迟 + 有成本"** 应成为肌肉记忆
- **本地调用和远程调用的语义不同** → 不要用"透明远程调用"（RPC 假装本地）来掩盖这一点

### 5.1 时钟不可信

| 问题 | 说明 |
|------|------|
| **时钟偏移（Clock Skew）** | 不同机器的时钟有偏差（即使 NTP 也有毫秒~秒级） |
| **时钟漂移（Drift）** | 时钟走得快慢不同 |
| **NTP 跳变** | 时钟可能**向后跳** → 时间戳排序失效 |
| **无法确定全局顺序** | 只有逻辑时钟（Lamport、向量时钟）能给出可靠的因果顺序 |

**实践**：
- **不要用物理时间戳做分布式排序/冲突解决**（LWW 会静默丢数据）
- 用**逻辑时钟**表达因果
- 物理时间只用于**近似**（监控、日志展示）

### 5.2 分布式系统的隐性成本

| 成本 | 说明 |
|------|------|
| 网络往返（RTT） | 每次跨服务调用至少 1 个 RTT |
| 序列化/反序列化 | 每次调用都有 CPU 开销 |
| 连接管理 | 连接池、keep-alive、TLS 握手 |
| 排障成本 | 跨服务追踪、日志聚合 |
| 部署协调 | 版本兼容、滚动升级 |
| 认知成本 | 团队需要理解分布式语义 |

> **"微服务比单体快"通常不成立**——它把函数调用换成了网络调用。**微服务优化的是"交付速度和组织扩展"，不是"延迟"。**

## 6. 分布式系统检查清单

- [ ] **为什么必须分布式？** 单机瓶颈被量化了吗？
- [ ] 分区发生时，**选 CP 还是 AP**？（明确写出）
- [ ] 正常运行时，**延迟 vs 一致性**怎么权衡？（PACELC 的 ELC）
- [ ] 需要什么**级别的一致性**？（线性 / 因果 / 读己之写 / 最终）
- [ ] **所有**网络调用都设了**超时**吗？
- [ ] 超时预算是否**逐跳递减**？
- [ ] 重试有**指数退避 + 抖动 + 预算**吗？只对可重试错误重试吗？
- [ ] 所有跨进程写操作**幂等**吗？
- [ ] **消息重复**（至少一次）被处理了吗？
- [ ] **时钟**是否被用于关键排序？（不应该）
- [ ] 共识用在**控制平面**而非数据平面吗？
- [ ] 是否用"透明 RPC"掩盖了远程调用的语义差异？
- [ ] **故障演练**（混沌工程）做过吗？
- [ ] 有没有**级联故障**的防护（熔断、隔板、限流，见 `09`）？

## 常见误区

| 误区 | 纠正 |
|------|------|
| CAP "三选二" | P 不可选；实际是分区时选 C 或 A |
| CAP 的 C = ACID 的 C | 完全不同：线性一致 vs 约束 |
| 忽略 PACELC | 正常运行时的延迟 vs 一致性同样重要 |
| 认为"恰好一次"靠基础设施保证 | 实际是"至少一次 + 幂等" |
| 用物理时间戳解决冲突 | 时钟不可信；用逻辑时钟/CRDT |
| 无超时的网络调用 | 必然耗尽资源 |
| 无退避的重试 | 重试风暴 → 雪崩 |
| 把共识用在数据平面 | 吞吐灾难；共识属于控制平面 |
| 认为微服务更快 | 把函数调用换成网络调用 |
| 忽略部分失败 | 部分失败是分布式系统的本质 |
