# 06 · 数据与持久化

> 本模块解决：**数据归谁？选 SQL 还是 NoSQL？怎么复制分区？跨服务的一致性怎么办？**

## 0. 第一原则：数据归属

**在讨论任何数据库技术之前，先回答：这份数据归谁所有？**

### 0.1 数据所有权（Data Ownership）

**每条数据有且只有一个"所有者"（writer）。** 其他人只能通过所有者的接口读取（或读副本）。

| 反模式 | 问题 |
|--------|------|
| 多个服务直连同一个库 | schema 变更互相牵连；无法独立部署；故障域重叠 |
| 服务 A 直接读服务 B 的表 | 绕过 B 的业务规则；B 改 schema 就崩 |
| 共享的"公共库" | 最终变成大泥球的数据中心 |

**判据**：**"这份数据的写入方有几个？"** > 1 → 要么合并（同一上下文），要么重新划边界。

### 0.2 数据建模的两个层次

| 层次 | 关注 | 说明 |
|------|------|------|
| **领域数据模型** | 业务概念（聚合、实体、值对象） | 来自 DDD（见 `05-domain-modeling.md`） |
| **持久化模型** | 存储结构（表/schema/索引/分区） | 服务于**访问模式**与**一致性需求** |

> ⚠️ **两者不应强制一致。** 用 ORM 把领域模型直接映射成表，会导致数据库结构被领域模型绑架（或反过来）。**读写模式差异大时，考虑 CQRS 分离读写模型。**

### 0.3 访问模式优先（Access-Pattern-First）

**选存储前先列出访问模式**：

| 要问的 | 例子 |
|--------|------|
| 主要查询是什么？ | 按用户查订单、按时间范围查日志、按地理位置找附近 |
| 读写比例？ | 100:1 读多写少 / 1:1 / 写多读少 |
| 查询的维度（key）？ | 主键、二级索引、全文、地理、图遍历 |
| 一致性要求？ | 强一致 / 最终一致 / 无所谓 |
| 数据量级与增长？ | 当前 1TB，年增 10TB |
| 数据保留期？ | 永久 / 5 年 / 30 天 |
| 事务范围？ | 单行 / 多表 / 跨服务 |

**结论**：**先有访问模式，再选存储。** 反过来（先选 MongoDB 再想怎么查）是失败的主因。

## 1. SQL vs NoSQL 的驱动因素

### 1.1 不要问"哪个更好"，问"哪个约束更匹配"

| 驱动因素 | 倾向 SQL | 倾向 NoSQL |
|---------|---------|-----------|
| **数据模型** | 结构化、关系多、需要 join | 文档/宽列/图/时序；嵌套聚合 |
| **一致性** | 需要 ACID 强一致 | 可接受最终一致 |
| **schema** | 相对稳定 | 频繁变化 / 异构 |
| **扩展方向** | 垂直扩展为主（水平较难） | 原生水平扩展 |
| **数据量** | 单机可承载（TB 级） | PB 级 |
| **事务范围** | 多行多表事务 | 单文档/单分区事务 |
| **查询灵活度** | 任意 join、ad-hoc 查询 | 需按设计好的访问路径查 |
| **团队熟悉度** | 普遍熟悉 | 需专门经验 |

### 1.2 NoSQL 的四大类

| 类型 | 数据模型 | 典型产品 | 适合 |
|------|---------|---------|------|
| **文档** | JSON 文档 | MongoDB、Couchbase | 内容管理、目录、半结构化 |
| **键值** | key → value | Redis、DynamoDB | 缓存、会话、计数器 |
| **宽列** | 行键 + 列族 | Cassandra、HBase、ScyllaDB | 时序、写密集、海量数据 |
| **图** | 节点 + 边 | Neo4j、JanusGraph | 社交关系、推荐、知识图谱 |

（另有**时序**（InfluxDB、TimescaleDB）、**搜索**（Elasticsearch、OpenSearch）、**向量**（pgvector、Milvus）等专用类型。）

### 1.3 现实中的常见答案

> **大多数系统的最佳答案是"PostgreSQL + 一个缓存"，而不是"五种数据库"。**

理由：
- PostgreSQL 支持 JSON（jsonb）、全文检索、地理（PostGIS）、时序（TimescaleDB）、向量（pgvector）
- **每引入一个存储都在支出复杂度预算**（备份、运维、一致性、团队学习）
- **多语言持久化（§5）是有成本的，不是免费的**

**升级路径**：先用 PostgreSQL 扛住，遇到**明确的、被量化的瓶颈**（如写吞吐超过单机上限、需要 PB 级存储、需要原生图遍历）再引入专用存储。

## 2. 复制与分区

### 2.1 复制（Replication）

**目的**：高可用（故障切换）、读扩展（读副本）、降低延迟（就近读）。

| 模式 | 说明 | 一致性 | 写延迟 | 故障时数据丢失风险 |
|------|------|--------|--------|------------------|
| **主从（单主）** | 一主多从，写主读从 | 异步：可能读到旧数据；同步：写延迟高 | 中 | 异步：可能丢未同步数据 |
| **多主（Multi-master）** | 多个节点可写 | 需冲突解决 | 低（就近写） | 冲突处理复杂 |
| **无主（Leaderless）** | 任意节点可读写，Quorum 决定 | 可调（见 `07`） | 低 | 依赖 Quorum |

**关键概念**：

| 术语 | 含义 |
|------|------|
| **RPO**（Recovery Point Objective） | 能容忍丢多少数据（时间维度） |
| **RTO**（Recovery Time Objective） | 能容忍停多久 |
| **同步复制** | 主等从确认后才返回 → 强一致，但延迟高、可用性降低 |
| **半同步** | 等至少一个从确认 |
| **异步复制** | 主立即返回 → 延迟低，但故障时可能丢数据 |
| **复制延迟（Replication Lag）** | 从库落后主库的时间 → 导致"读己之写"问题 |

**读己之写（Read-Your-Writes）问题**：用户写完立刻读从库，读不到自己的写入。
解决：写后一段时间内读主库 / 会话粘性 / 客户端记录版本号。

### 2.2 分区（Partitioning / Sharding）

**目的**：突破单机存储与吞吐上限。

| 策略 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **范围分区** | 按 key 范围（如时间、ID 段） | 范围查询高效 | 热点（如按时间 → 最新分区最热） |
| **哈希分区** | `hash(key) % N` | 分布均匀 | 范围查询要扫所有分区 |
| **一致性哈希** | 哈希环，节点增减只影响邻近 | 扩缩容影响小 | 实现复杂 |
| **目录分区** | 单独的映射服务决定路由 | 灵活 | 映射服务是单点 |
| **地理分区** | 按区域 | 合规（数据主权）、低延迟 | 跨区域查询难 |

**分区键的选择是最关键的决策**（且难以更改——**单向门**）：

| 判据 | 说明 |
|------|------|
| **基数够高** | 避免热点（如按"性别"分区是灾难） |
| **访问均匀** | 每个分区的负载相近 |
| **与查询模式匹配** | 常见查询应命中单个分区（避免跨分区扫描） |
| **不会频繁变更** | 分区键变更 = 数据搬迁 |

**跨分区的代价**：跨分区查询慢、跨分区事务难、跨分区 join 几乎不可行。**因此分区键要尽量让"常用查询"落在单分区内。**

### 2.3 分区的常见陷阱

| 陷阱 | 说明 |
|------|------|
| **热点分区** | 某个 key 特别热（如大 V 用户、爆款商品）→ 需要二次拆分或加缓存 |
| **跨分区事务** | 需要两阶段提交或 Saga（性能差） |
| **重分区成本** | 加节点需要重新分布数据（一致性哈希缓解但仍有成本） |
| **分区键选错** | 最难回退的错误之一（单向门） |

## 3. 事务、Saga 与 Outbox

### 3.1 本地事务（ACID）—— 单体时代的舒适区

```
BEGIN → 扣库存 → 创建订单 → 扣余额 → COMMIT / ROLLBACK
```

**在一个数据库内，ACID 帮你解决一切。** 这也是模块化单体的巨大优势（见 `04-architecture-styles.md`）。

### 3.2 分布式事务的选项

| 方案 | 一致性 | 性能 | 复杂度 | 适用 |
|------|--------|------|--------|------|
| **两阶段提交 2PC/XA** | 强一致 | 差（同步阻塞、协调者单点） | 中 | 极少；跨库强一致场景 |
| **Saga** | 最终一致 | 好 | 高 | **主流选择**（微服务） |
| **TCC（Try-Confirm-Cancel）** | 最终一致 | 中 | 很高 | 金融级强约束场景 |
| **本地消息表 / Outbox** | 最终一致 | 好 | 中 | 保证"业务写入 + 事件发布"原子性 |
| **事件溯源** | 最终一致 | 好 | 很高 | 审计/回放是核心需求时 |

> **架构师建议**：**避免分布式事务。** 优先通过**重新划边界**（把需要强一致的东西放进同一个聚合/服务）来消灭分布式事务，而不是用技术手段硬解。

### 3.3 Saga 模式

**把一个跨服务的业务流程，拆成一串本地事务；每个本地事务有一个补偿操作（compensating action）。**

```
订单服务:  创建订单(待支付) ──────┐
支付服务:           扣款 ────────┤ 全部成功 → 完成
库存服务:              锁库存 ────┘
                    ↓ 任一步失败
                 反向补偿：解锁库存 → 退款 → 取消订单
```

| 编排方式 | 说明 | 优点 | 缺点 |
|---------|------|------|------|
| **编排式（Choreography）** | 各服务通过事件自发响应 | 松耦合、无中心 | 流程分散难追踪、易循环依赖 |
| **协调式（Orchestration）** | 中心协调器指挥各服务 | 流程集中可见、易调试 | 协调器是中心（可能成为瓶颈/单点） |

**Saga 的关键设计点**：
1. **补偿操作必须幂等**（可能被重试多次）
2. **补偿操作可能失败** → 需要重试 + 人工介入兜底（**没有完美的自动补偿**）
3. **必须处理"语义锁"**：Saga 执行中，其他流程不得修改相关数据（用状态标记，如"待支付"）
4. **Saga 只保证最终一致**，中间状态对外可见 → 需要产品设计配合（如"订单处理中"）

> ⚠️ **Saga 不是免费的**：它把"事务"换成了"业务流程 + 补偿 + 幂等 + 状态机"。**这是复杂度预算的重大支出。** 能用单库事务解决的，不要用 Saga。

### 3.4 Outbox 模式（事务性发件箱）

**问题**：如何保证"写数据库"和"发消息"**原子地**发生？

```
❌ 天真做法（会不一致）
BEGIN; INSERT order; COMMIT;
sendMessage(orderEvent);   ← 如果这里挂了，订单存在但没有事件
```

```
✅ Outbox 模式
BEGIN;
  INSERT order;
  INSERT outbox(order_id, payload, status='PENDING');   ← 同一个事务
COMMIT;
                                          ↓
后台 relay 进程轮询 outbox → 发消息 → 标记 SENT（幂等）
```

**关键点**：
- outbox 表与业务表在**同一个数据库、同一个事务**里写入 → 保证原子性
- relay 进程（或 CDC，如 Debezium）负责投递，**至少一次**投递
- 消费端必须**幂等**（因为可能重复投递）
- **权衡**：牺牲即时性（轮询延迟）换取一致性

**变体**：
- **事务日志挖掘（CDC）**：直接读 binlog/WAL 发布事件（Debezium），无轮询延迟
- **发件箱 + 事件溯源**：事件本身就是事实源

### 3.5 幂等（Idempotency）—— 分布式数据的生命线

**因为"至少一次投递"是常态，所以"重复处理"是常态。**

| 实现方式 | 说明 |
|---------|------|
| **幂等键（Idempotency Key）** | 客户端提供唯一键，服务端记录已处理的键，重复请求返回同一结果 |
| **去重表** | 记录已处理的消息 ID |
| **状态机** | 状态只能单向流转（已支付 → 不能再支付） |
| **条件更新** | `UPDATE ... WHERE version = ?`（乐观锁） |
| **天然幂等操作** | `SET status = 'PAID'`（覆盖式）比 `SET balance = balance - 100` 幂等 |

> **架构师必做**：任何跨服务/跨进程的写操作，都要问"**这个操作重复执行会怎样？**" 答不上来就是隐患。

## 4. 多语言持久化（Polyglot Persistence）

### 4.1 定义

**同一个系统里使用多种数据存储技术，各取所长。**

```
PostgreSQL  → 交易数据（ACID、关系）
Redis       → 缓存、会话、限流计数
Elasticsearch → 全文搜索、日志分析
ClickHouse  → OLAP 分析、报表
Kafka       → 事件流
S3/OSS      → 对象/文件存储
```

### 4.2 收益 vs 成本

| 收益 | 成本（**持续支出**） |
|------|-------------------|
| 每种数据用最合适的引擎 | 运维：多套备份/监控/告警/升级 |
| 性能与成本优化 | 一致性：多存储之间的同步 |
| 可独立扩缩容 | 团队学习成本、招聘要求 |
| 故障隔离 | 排障链路变长 |
| | 事务跨存储更难 |

> **判据**：**每引入一种存储，都要能说清"它解决了哪个被量化的瓶颈"。** 说不出具体数字的，就是在支出复杂度预算买"架构师觉得很酷"。

### 4.3 数据同步模式

| 模式 | 说明 |
|------|------|
| **双写（Dual Write）** | 应用同时写两个存储 | ⚠️ 危险：无法保证原子性，会不一致 |
| **CDC（变更数据捕获）** | 从数据库日志同步到下游 | ✅ 推荐：不侵入应用，可靠 |
| **事件驱动** | 通过消息同步 | ✅ 推荐：解耦，但需幂等 |
| **定时批处理** | 定期全量/增量同步 | 简单但延迟高，适合分析场景 |
| **应用层 Outbox** | 见 §3.4 | ✅ 保证原子性 |

> ⚠️ **双写是反模式**：两个写操作无法原子化，一个成功一个失败就会不一致。**用 CDC 或 Outbox 替代。**

### 4.4 CQRS 与多存储

CQRS 的高级形态：**写模型用 PostgreSQL，读模型用 Elasticsearch/Redis/ClickHouse**，通过事件或 CDC 同步。适合读写负载差异巨大、读模型需深度优化的场景（见 `04-architecture-styles.md`）。

## 5. 数据架构检查清单

**设计数据层时，逐条回答**：

- [ ] 每份数据的**所有者**是谁？（唯一 writer）
- [ ] 主要**访问模式**是什么？（查询维度、读写比、量级）
- [ ] **一致性要求**是强一致还是最终一致？
- [ ] 需要**事务**的范围有多大？能否通过重划边界消除跨服务事务？
- [ ] **分区键**选什么？（高基数、访问均匀、与查询匹配、不变）
- [ ] **复制策略**：RPO/RTO 是多少？同步还是异步？
- [ ] 跨服务的写操作是否**幂等**？
- [ ] 是否需要 **Outbox/Saga**？补偿逻辑设计了吗？
- [ ] **数据增长**预测：1 年后多大？3 年后？
- [ ] **数据保留/归档/合规**要求？（删除权、数据主权、留存期）
- [ ] **备份与恢复**演练过吗？（没演练过的备份等于没有备份）
- [ ] 引入的每种存储，解决的是**哪个被量化的瓶颈**？

## 常见误区

| 误区 | 纠正 |
|------|------|
| 先选数据库再想查询 | 访问模式优先 |
| 多个服务共享一个库 | 数据必须有唯一所有者 |
| 用分布式事务硬解跨服务一致性 | 优先重划边界，消除分布式事务 |
| 双写两个存储 | 用 CDC / Outbox |
| 天真地"写库 + 发消息" | Outbox 保证原子性 |
| 假设消息只投递一次 | 至少一次是常态；必须幂等 |
| 分区键选低基数字段 | 会造成热点，且难回退 |
| 引入多种存储但不量化收益 | 每种存储都是持续复杂度支出 |
| 认为 Saga 能完美补偿 | 补偿也会失败；需要人工兜底 |
| 备份了但没演练恢复 | 没验证过的备份不算备份 |
