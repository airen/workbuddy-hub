# 01 · 基础与角色

> 本模块解决：**什么是架构？架构师到底做什么？怎么把模糊的"非功能需求"变成架构能用的东西？**

## 1. 究竟什么是架构

**定义（实用版）**：架构是**一组关于系统结构的决策**，这些决策**难以在事后更改**，且**决定了系统满足哪些质量属性**。

判断一个决策是不是"架构决策"，用两个筛子：

| 筛子 | 问题 | 是 → |
|------|------|------|
| **变更成本** | 改它要动多少地方、多少团队、多少数据？ | 变更成本高的决策是架构决策 |
| **质量属性影响** | 它决定了性能/可用性/可修改性/安全性中的哪些？ | 决定质量属性的是架构决策 |

> 常见误区：把"用了什么框架/中间件"当架构。技术选型是**架构决策的产物**，不是架构本身。架构的核心是**边界、依赖方向、数据归属、交互契约**。

**架构的三个层次**（别混为一谈）：

| 层次 | 关注 | 典型产物 |
|------|------|---------|
| **系统架构（System）** | 系统与外部世界、系统间的边界 | C4 Context 图、集成契约 |
| **应用架构（Application）** | 应用内的模块/服务划分与依赖 | C4 Container/Component 图、模块图 |
| **代码/组件架构（Code）** | 类/包/函数的组织 | 依赖图、分层规则 |

**架构 vs 设计**：没有清晰的界线，通常按"变更成本"和"影响范围"划分。影响多个团队、跨系统、难回退的是架构；影响单模块内部的是设计。

## 2. 架构师 vs 高工 vs 技术主管

这三者**不是职级高低，而是职责不同**，可以重叠但重心不同：

| 维度 | 软件架构师 | 高级工程师 | 技术主管 / Tech Lead |
|------|-----------|-----------|---------------------|
| **核心产出** | 决策与约束（边界、契约、质量标准） | 可运行的高质量代码与模块 | 团队的交付节奏与人的成长 |
| **时间尺度** | 1–3 年（系统演化） | 数周–数月（功能迭代） | 数周–季度（版本与团队目标） |
| **作用范围** | 跨系统、跨团队 | 单个模块/子系统 | 一个团队 |
| **主要对象** | 利益相关者、其他团队、未来维护者 | 代码、测试、性能 | 人、流程、排期 |
| **失败模式** | 设计无人能落地的"空中楼阁" | 局部最优、缺乏全局视角 | 只盯交付、技术债失控 |

**架构师最容易犯的错**：
- **象牙塔架构师**：脱离代码和团队，产出无人执行的设计。**架构师必须持续接触代码与生产环境。**
- **不做决策的架构师**：只罗列选项，不拍板。架构师的价值在于**在信息不完整时做出可辩护的决策**。
- **全栈微观管理**：什么都管，结果是团队的瓶颈。

**健康的架构师画像**：技术判断力 + 沟通力 + 组织感知力。技术只占三分之一。

## 3. 质量属性与各种 "-ility"

**质量属性（Quality Attribute, QA）** 是架构的真正目标。功能性需求决定系统**做什么**，质量属性决定系统**做得多好**。

### 3.1 质量属性分类

**运行期（Runtime）**——系统跑起来时能观测到的：

| 属性 | 含义 | 常见度量 |
|------|------|---------|
| 性能 Performance | 单位时间处理量与响应延迟 | 吞吐量（QPS/TPS）、P50/P95/P99 延迟、延迟预算 |
| 可用性 Availability | 系统可服务的时间比例 | 可用性百分比（99.9% = 年停 8.76h）、MTBF/MTTR |
| 可靠性 Reliability | 无故障持续运行的能力 | 故障率、数据丢失率 |
| 可伸缩性 Scalability | 增加资源时性能的改善程度 | 水平扩展效率、线性度 |
| 安全性 Security | 抵御攻击与保护数据的能力 | 认证强度、加密覆盖、漏洞数 |
| 互操作性 Interoperability | 与外部系统交换信息的能力 | 协议覆盖率、集成成功率 |
| 可观测性 Observability | 从外部推断内部状态的能力 | 追踪覆盖率、MTTD |

**开发期（Development）**——影响团队怎么干活：

| 属性 | 含义 | 常见度量 |
|------|------|---------|
| 可修改性 Modifiability | 变更的成本与风险 | 改一个需求的平均人天、变更影响面 |
| 可测试性 Testability | 验证正确性的难易 | 覆盖率、测试执行时间、可独立部署性 |
| 可部署性 Deployability | 发布到生产的难易与风险 | 部署频率、前置时间、回滚时间 |
| 可维护性 Maintainability | 理解与修复代码的难易 | 认知复杂度、重复率、文档完整度 |
| 可复用性 Reusability | 组件在别的场景被复用的能力 | 复用率 |

**业务/组织期**：

| 属性 | 含义 |
|------|------|
| 上市时间 Time to Market | 从想法到上线的速度 |
| 成本 Cost | 基础设施 + 人力 + 迁移成本 |
| 合规性 Compliance | 法律、行业标准、数据主权 |

### 3.2 ⚠️ 质量属性之间几乎总是**冲突**的

这是架构的本质：**你无法同时最大化所有质量属性。**

| 提升 | 通常牺牲 |
|------|---------|
| 性能（本地缓存/数据冗余） | 一致性、可修改性 |
| 可用性（多副本/异步） | 一致性、成本 |
| 安全性（多层校验/加密） | 性能、开发速度 |
| 可修改性（抽象/解耦） | 性能、初始复杂度、理解成本 |
| 可伸缩性（分片） | 运维复杂度、事务能力 |
| 上市时间（走捷径） | 长期可维护性（技术债） |

**因此架构师的工作 = 在这些冲突中，按业务优先级排序并明确取舍。** 这就是为什么"没有免费的午餐"是本技能的第一信条。

### 3.3 质量属性怎么才"可用"——用场景描述

"高可用""高性能"这类词**无法验证、无法设计、无法验收**。必须转成**质量属性场景（Quality Attribute Scenario）**：

```
刺激源(Source) → 刺激(Stimulus) → 制品(Artifact) → 环境(Environment)
                                        ↓
                        响应(Response) ← 响应度量(Response Measure)
```

**六要素示例**：

| 要素 | 内容 |
|------|------|
| 刺激源 | 外部用户 |
| 刺激 | 发起下单请求 |
| 制品 | 订单服务 |
| 环境 | 促销峰值（10 倍日常流量） |
| 响应 | 正常创建订单并返回订单号 |
| 响应度量 | P99 延迟 < 2s，成功率 ≥ 99.9% |

> 完整工作表见 `templates/quality-attribute-scenario.md`。

**通用场景 vs 具体场景**：通用场景是模板（"任意用户在任何时候…"），具体场景带具体数字（"促销峰值时 10 万并发用户…"）。**架构设计用具体场景，因为它可度量。**

## 4. 功能性需求 vs 非功能性需求

| 维度 | 功能性需求 (FR) | 非功能性需求 (NFR) |
|------|----------------|-------------------|
| 描述 | 系统**做什么** | 系统**做得多好 / 受什么约束** |
| 例子 | "用户可以下单""支持退款" | "下单 P99 < 2s""可用性 99.9%""数据留存 5 年" |
| 谁提出 | 业务方 / 产品 | 业务方 + 运维 + 安全 + 合规 + 用户 |
| 验证方式 | 功能测试（通过/不通过） | 度量、压测、监控、审计 |
| 对架构的影响 | 决定**模块划分** | 决定**架构风格与拓扑** |

**关键洞察**：**架构主要由 NFR 驱动，而不是 FR。** 两个需求完全相同的系统，因为 NFR 不同（一个 100 QPS 一个 10 万 QPS），架构可以完全不同。所以：

> 讨论架构时，如果对方只给了功能列表，**先要 NFR**。没有 NFR 就没有架构讨论。

**NFR 的分类骨架（便于提问）**：
- **性能**：延迟、吞吐、并发、数据规模、增长速率
- **可用性**：SLA、允许停机窗口、容灾等级（同城/异地）
- **可伸缩性**：峰值倍数、扩展方向（读多/写多）
- **安全与合规**：等保、隐私（个人信息保护法/GDPR）、审计、数据主权
- **可维护性**：团队规模、迭代频率、人员流动率
- **成本**：预算上限、单位成本目标
- **运维**：现有运维能力、可接受的运维复杂度

## 5. 利益相关者、约束与驱动因素

### 5.1 利益相关者（Stakeholders）

**每个利益相关者关心的质量属性不同，且常常互相冲突。**

| 利益相关者 | 主要关心 |
|-----------|---------|
| 最终用户 | 性能、可用性、易用性 |
| 产品/业务方 | 上市时间、成本、功能覆盖 |
| 开发团队 | 可修改性、可测试性、技术栈匹配度 |
| 运维/SRE | 可观测性、可部署性、可恢复性、值班负担 |
| 安全/合规 | 安全性、合规性、审计能力 |
| 财务/管理层 | 成本、ROI、风险 |
| 未来维护者（常被遗忘） | 可理解性、文档、可修改性 |

> **架构师的关键动作**：识别出**关键利益相关者**（能一票否决的人），在决策早期就让他们参与，而不是最后才"通知"。ADR 的一个重要价值就是让决策**可被这些人事后追溯**。

### 5.2 约束（Constraints）

约束是**不可协商的限制**，它缩小了解空间。分三类：

| 类型 | 例子 |
|------|------|
| **技术约束** | 必须用某云厂商、必须复用某存量系统、团队只会 Java、必须支持 IE（历史遗留） |
| **组织约束** | 团队规模与地理分布、外包边界、审批流程、预算周期 |
| **业务/合规约束** | 上线死线、等保三级、数据不得出境、必须审计留痕、行业监管 |

**约束 ≠ 借口**。好的架构师会**质疑约束**：哪些是真正的硬约束，哪些只是"我们一直这么做"？——但要**在决策前质疑，而不是在失败后抱怨**。

### 5.3 架构驱动因素（Architecture Drivers）

**驱动因素 = 约束 + 关键质量属性。**

流程：

```
所有需求（FR + NFR）
        ↓ 用具体场景描述
候选质量属性场景（可能几十条）
        ↓ 按业务价值 + 冲突程度排序
关键质量属性（通常 2–3 条）  ← 这些才真正决定架构形状
        ↓ 叠加不可协商约束
架构驱动因素  ← 架构设计围绕它们展开
```

**实操建议**：一份系统架构文档的开头，应该明确写出**驱动因素表**：

| # | 驱动因素 | 类型 | 说明 | 优先级 |
|---|---------|------|------|--------|
| D1 | 促销峰值 10 万并发下单，P99 < 2s | 性能 | 大促是核心营收场景 | 高 |
| D2 | 可用性 99.95%，同城双活 | 可用性 | 停机直接影响收入 | 高 |
| D3 | 3 个团队独立发布 | 可部署性 | 组织现状（康威定律） | 中 |
| D4 | 必须复用现有支付网关 | 约束 | 与银行直连，短期不可替换 | 硬约束 |
| D5 | 6 个月内上线 | 约束 | 董事会承诺 | 硬约束 |

> **没写驱动因素的架构文档，等于没写架构。** 因为读的人无法判断"这个设计在什么前提下是对的"。

## 常见误区

| 误区 | 纠正 |
|------|------|
| 把技术栈当架构 | 架构是边界/依赖/数据/契约的决策 |
| 追求"高内聚低耦合"这类口号 | 口号无法度量；要落到具体质量属性场景 |
| 试图同时最大化所有质量属性 | 必然失败；必须排序取舍 |
| 用形容词写 NFR（"高性能"） | 转成六要素场景，带数字 |
| 忽略运维/安全/合规利益相关者 | 他们的需求常在后期变成"架构返工" |
| 把约束当不可讨论的天条 | 决策前质疑，决策后遵守 |

## 速查：架构师开工前的 5 问

1. **业务目标是什么？**（成功长什么样）
2. **量级是多少？**（QPS、数据量、增长速度、延迟要求）
3. **团队与组织是什么样？**（人数、分布、能力、发布节奏）
4. **硬约束有哪些？**（技术、合规、时间、预算、存量系统）
5. **当前最疼的是什么？**（性能 / 交付速度 / 稳定性 / 成本 / 招人）

> 五问答不全，就不要开始设计。答不全就先声明假设，并标注"待确认"。
