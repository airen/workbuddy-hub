# 10 · 实践与沟通

> 本模块解决：**怎么把架构讲清楚？怎么评审？怎么练习？经典系统怎么拆？怎么从开发者成长为架构师？**

## 1. C4 模型与图表

### 1.1 为什么需要 C4

**架构图最大的问题是"没有统一的抽象层次"**——一张图里混着系统、服务、类、表，读者不知道该关注什么。

**C4 模型（Simon Brown）** 用**四个层次的抽象**解决这个问题，**每层只画一种东西**。

### 1.2 四个层次

| 层次 | 画什么 | 给谁看 | 元素 |
|------|--------|--------|------|
| **L1 Context（系统上下文）** | 系统与外部世界的关系 | 非技术人员、管理者 | 人（Person）、软件系统（System）、外部系统 |
| **L2 Container（容器）** | 系统内部的可部署单元 | 技术管理者、架构师 | Web 应用、移动 App、API、数据库、消息队列 |
| **L3 Component（组件）** | 容器内部的主要模块 | 架构师、开发者 | 控制器、服务、仓储、网关 |
| **L4 Code（代码）** | 类/接口级细节 | 开发者 | 类、接口（**通常不画**，用 IDE 生成） |

**关键概念辨析**：

| C4 术语 | 含义 | 注意 |
|---------|------|------|
| **System** | 最高层，交付价值的整体 | 不是"系统"这个词的泛用 |
| **Container** | **可独立部署/运行的单元** | **不是 Docker 容器！** 是"部署单元"（应用、服务、数据库、前端应用） |
| **Component** | 容器内的模块 | 有明确定义的职责 |
| **Person** | 使用者（角色，非具体人） | 内部用户、外部用户 |

### 1.3 画 C4 的实用建议

| 建议 | 说明 |
|------|------|
| **Context + Container 是主力** | 90% 的场景只需这两层；Component 按需画 |
| **一个图一个故事** | 不要在一张图里塞下所有细节 |
| **标注技术选型** | Container 图上写清"PostgreSQL""Kafka" |
| **标注交互协议** | 箭头写清是 HTTP/gRPC/异步消息 |
| **保持一致** | 所有图用同一套符号与命名 |
| **图和代码同源** | 用 Mermaid/PlantUML 写在版本库里，而不是画图工具（会过期） |

### 1.4 补充视图（C4 之外）

C4 只覆盖**静态结构**。实际架构文档还需要：

| 视图 | 回答 |
|------|------|
| **时序图 Sequence** | 关键流程如何交互（下单流程、支付流程） |
| **部署图 Deployment** | 物理/云上如何部署（机房、可用区、K8s） |
| **动态图 Dynamic** | 运行时的对象协作 |
| **数据流图** | 数据从哪来、到哪去、存哪 |
| **状态机图 State** | 关键实体的状态流转（订单状态） |

> 模板见 `templates/c4-diagram.md`（含 Mermaid 骨架）。

## 2. 文档化视图与决策

### 2.1 文档化架构视图（Views & Beyond, Rozanski & Woods）

除了 C4，另一种组织方式是**按关注点分视图**：

| 视图 | 关注 | 受众 |
|------|------|------|
| **上下文 Context** | 系统与外部的关系 | 全部 |
| **功能 Functional** | 功能元素与职责 | 开发、产品 |
| **信息 Information** | 数据模型、存储、流转 | 数据、开发 |
| **并发 Concurrency** | 并发、异步、并行 | 开发、运维 |
| **开发 Development** | 代码组织、构建、依赖 | 开发 |
| **部署 Deployment** | 部署拓扑、环境 | 运维 |
| **运维 Operational** | 运维、监控、备份、恢复 | 运维、SRE |

**观点（Perspectives）**：安全、性能、可用性、可演化性等**横切关注点**要贯穿所有视图。

### 2.2 架构文档的核心原则

| 原则 | 说明 |
|------|------|
| **文档是给未来的人看的** | 假设读者不知道任何背景 |
| **只写"不明显的"** | 代码能说清的不要写文档 |
| **重点写"为什么"** | 写 ADR（决策），而不是写"是什么"（代码已有） |
| **与代码同仓** | `docs/architecture/`，随代码评审、随代码演进 |
| **有明确的所有者** | 谁负责维护（否则必然过期） |
| **过期即删除** | 错误的文档比没有文档更糟 |
| **图表用文本格式** | Mermaid/PlantUML，可 diff、可评审 |

### 2.3 架构文档的最小集（务实版）

不是每个项目都需要全套。**最小可用集**：

```
docs/
├── README.md              # 系统是什么、给谁、怎么跑
├── architecture/
│   ├── context.md         # C4 L1：系统与外部
│   ├── containers.md      # C4 L2：部署单元
│   ├── quality-attributes.md  # 驱动因素 + 质量属性场景
│   ├── data.md            # 数据模型与归属
│   └── diagrams/          # Mermaid 源文件
└── adr/
    ├── 0001-record-architecture-decisions.md
    ├── 0002-xxx.md
    └── ...
```

**加一份 `CONTRIBUTING` 说明边界规则**（哪些模块能依赖哪些），比画十张图有用。

## 3. 架构 Kata 与设计评审

### 3.1 架构 Kata（Architecture Kata）

**定义**：**限时（通常 45–90 分钟）的架构设计演练**，给定一个需求场景，团队一起产出设计并互相评审。

**目的**：**练习架构决策能力**（不是练习画图），在低风险环境里暴露思维盲区。

**标准流程**：

| 阶段 | 时长 | 内容 |
|------|------|------|
| 1. 读题 | 5 min | 阅读需求（含驱动因素与约束） |
| 2. 澄清 | 5 min | 向"出题人"提问，补齐缺失信息 |
| 3. 设计 | 30–45 min | 团队协作产出 C4 图 + 关键决策 + ADR |
| 4. 展示 | 5 min/组 | 各组讲解设计（重点是**取舍**） |
| 5. 评审 | 15–30 min | 互相提问、挑刺（**这是最有价值的部分**） |
| 6. 复盘 | 10 min | 总结：哪些决策是敏感点？哪些是取舍点？ |

**评分维度**（比"图漂不漂亮"重要）：
- 驱动因素识别是否准确？
- 是否列出多个备选并做了权衡？
- 边界划分是否合理？理由是什么？
- 是否考虑了失败模式与运维？
- 取舍是否被明确表达？

> 工作表见 `templates/architecture-kata.md`。

### 3.2 设计评审（Design Review）

**评审的目标不是"批准/否决"，而是"发现风险"和"传播知识"。**

**评审清单（简化版，完整见 `templates/architecture-review.md`）**：

| 维度 | 要问的问题 |
|------|-----------|
| **驱动因素** | 驱动因素写清楚了吗？优先级明确吗？ |
| **质量属性** | 关键质量属性有可度量场景吗？ |
| **边界** | 边界基于什么划的？跨边界交互是否最小化？ |
| **数据** | 数据归属清晰吗？一致性策略是什么？ |
| **集成** | 同步/异步选择有理由吗？失败怎么处理？ |
| **失败模式** | 依赖挂了会怎样？有降级吗？ |
| **运维** | 怎么部署、怎么监控、怎么回滚？ |
| **安全** | 认证/授权/密钥/数据保护怎么做？ |
| **演化** | 未来怎么改？哪些是单向门？ |
| **成本** | 复杂度预算支出多少？团队扛得住吗？ |

**评审反模式**：

| 反模式 | 问题 |
|--------|------|
| 变成"设计汇报" | 只讲不讲评，没人提问 |
| 只挑技术细节 | 忽略了驱动因素与取舍 |
| 评审者不懂业务 | 提不出关键问题 |
| 没有决策记录 | 评完了没结论，下次再吵一遍 |
| 评审太晚 | 设计已固化，改动成本高 |
| 用"最佳实践"压人 | 忽略具体约束 |

**有效评审的做法**：
- **提前发材料**，让评审者带着问题来
- **明确主持人**（防止跑题）
- **强制提问**（每人至少问一个"如果 X 失败会怎样？"）
- **现场产出 ADR**（把决策固化）
- **记录待办与责任人**

### 3.3 ATAM 轻量版

ATAM（Architecture Tradeoff Analysis Method）是重量级的架构评估方法。**轻量版流程**：

1. **呈现驱动因素**（业务目标 + 关键质量属性）
2. **呈现架构**（C4 Context + Container）
3. **识别架构方法**（用了哪些模式/策略）
4. **生成质量属性效用树**（把质量属性分解为可度量的场景，按优先级排序）
5. **分析架构方法**（对每个高优先级场景，找出**敏感点**与**取舍点**）
6. **识别风险与非风险**
7. **形成风险主题**（跨决策的系统性风险）

> 详见 `decision-frameworks.md` 的 ATAM-lite 部分。

## 4. 经典案例

> 以下是**常见题型的拆解思路**，不是标准答案。真实设计必须基于具体驱动因素。

### 4.1 电商系统

**核心子域与限界上下文**：

| 上下文 | 核心职责 | 关键数据 |
|--------|---------|---------|
| 商品 Catalog | 商品信息、类目、搜索 | 商品、类目、SKU |
| 库存 Inventory | 库存扣减、预占 | 库存、预占记录 |
| 订单 Order | 订单生命周期 | 订单、订单项 |
| 支付 Payment | 支付、退款、对账 | 支付单、流水 |
| 履约 Fulfillment | 发货、物流 | 发货单、物流轨迹 |
| 会员 User | 账户、等级、地址 | 用户、地址 |
| 营销 Promotion | 优惠券、活动 | 券、活动规则 |

**关键架构决策**：

| 决策点 | 常见取舍 |
|--------|---------|
| **库存扣减时机** | 下单扣（超卖风险低但占用库存）/ 支付扣（库存利用率高但需防超卖）→ 通常"下单预占 + 支付确认 + 超时释放" |
| **库存一致性** | 强一致（分布式锁/单库）vs 最终一致（Redis 预扣 + DB 对账）→ **高并发下通常选后者 + 补偿** |
| **订单与支付边界** | 独立上下文，通过事件（OrderPlaced → PaymentRequested → PaymentCompleted）协调 |
| **搜索** | 独立读模型（Elasticsearch），通过 CDC/事件同步 |
| **大促削峰** | 排队（MQ）、限流、预扣库存、降级非核心功能 |

**必答的失败场景**：
- 支付成功但订单状态未更新 → Outbox + 对账
- 库存扣了但订单创建失败 → 补偿/超时释放
- 支付回调重复 → 幂等
- 大促流量 10 倍 → 削峰 + 限流 + 降级

### 4.2 Feed 流（信息流）

**核心挑战**：**读多写少（可能 1000:1），且需要低延迟。**

**三种推模式**：

| 模式 | 做法 | 优点 | 缺点 | 适合 |
|------|------|------|------|------|
| **推（Push / Fan-out on Write）** | 发布时写入所有粉丝的收件箱 | 读极快（直接读收件箱） | 写放大（大 V 发一条写百万次） | 粉丝少、活跃用户 |
| **拉（Pull / Fan-out on Read）** | 读时聚合所有关注者的内容 | 写简单 | 读慢（要聚合 N 个来源） | 大 V、不活跃用户 |
| **推拉结合（Hybrid）** | 普通用户推、大 V 拉 | 平衡 | 实现复杂 | **主流方案** |

**关键设计**：

| 关注点 | 做法 |
|--------|------|
| **收件箱存储** | Redis List/ZSet（按时间排序），热数据在内存 |
| **Feed 排序** | 时间序 → 算法排序（需要特征与模型，复杂度大增） |
| **分页** | 游标（cursor）分页，避免 offset 深分页 |
| **大 V 问题** | 推拉结合；大 V 内容单独存储，读时合并 |
| **冷启动/回填** | 新用户关注后要回填历史内容 |
| **内容删除** | 推模式下删除要级联（难）→ 常做"墓碑标记 + 读时过滤" |

### 4.3 支付系统

**核心特征**：**正确性 > 可用性 > 性能。** 钱不能错。

| 设计要点 | 说明 |
|---------|------|
| **幂等** | 每笔支付有唯一业务单号；重复请求返回同一结果（**生命线**） |
| **账务模型** | **复式记账**（借贷平衡），每笔交易产生多条分录 |
| **对账（Reconciliation）** | 与银行/渠道定期对账，发现差异 |
| **状态机** | 支付单状态严格流转，不允许非法跳转 |
| **最终一致 + 补偿** | 与渠道交互必然异步 → 状态轮询 + 回调 + 对账兜底 |
| **审计** | 所有操作留痕，不可篡改（事件溯源的价值场景） |
| **隔离** | 支付域独立部署、独立数据库、独立审计（合规要求） |
| **幂等键与去重** | 防止重复扣款 |
| **限额与风控** | 交易限额、频次限制、风控规则 |

**必答场景**：
- 用户支付成功但系统超时 → 主动查询渠道状态（不能假设失败）
- 渠道回调重复/乱序 → 幂等 + 状态机 + 版本号
- 退款与支付并发 → 加锁或状态校验
- 对账发现差异 → 人工介入流程

### 4.4 案例拆解的通用方法

面对任何"设计 X 系统"的题目：

```
1. 澄清：用户量、QPS、数据量、读写比、延迟要求、一致性要求、团队规模
2. 识别核心子域（DDD 战略）
3. 定关键质量属性（2-3 条）
4. 画 C4 Context + Container
5. 逐个关键决策做权衡（至少 3 个备选）
6. 走一遍失败场景（依赖挂、重复、并发、超时）
7. 说清数据流与一致性策略
8. 给出演化路径（第一版做什么，什么时候扩展）
```

> ⚠️ **面试/评审中最加分的不是"你用了什么高级技术"，而是"你识别出了什么约束、做了什么取舍、为什么"。**

## 5. 开发者 → 架构师进阶之路

### 5.1 能力跃迁的四个维度

| 维度 | 开发者 | 架构师 |
|------|--------|--------|
| **范围** | 一个模块/服务 | 跨系统、跨团队 |
| **时间** | 当前迭代 | 1–3 年 |
| **产出** | 可运行的代码 | 可辩护的决策 + 约束 |
| **成功标准** | 功能正确、质量达标 | 系统能演化、团队能交付 |

**核心转变**：**从"把事情做对"到"决定做什么事"。** 从"解决问题"到"定义问题"。

### 5.2 必备能力（按重要性排序）

| 能力 | 说明 |
|------|------|
| **1. 判断力（Judgment）** | 在信息不完整时做出可辩护的决策。**这是架构师的核心能力。** |
| **2. 沟通与说服** | 让不同利益相关者理解并接受决策。**技术好但说不清 = 无效架构师。** |
| **3. 广度（Breadth）** | 知道有哪些方案（不需要样样精通） |
| **4. 深度（Depth）** | 至少在 1–2 个领域有真正的深度（否则判断力没有根基） |
| **5. 组织感知** | 理解康威定律、团队拓扑、权力结构 |
| **6. 写作** | ADR、设计文档、评审意见——**写作即思考** |
| **7. 持续编码** | 保持技术手感，避免"象牙塔" |
| **8. 商业理解** | 理解成本、收益、优先级、上市时间 |

### 5.3 成长路径（务实版）

| 阶段 | 做什么 |
|------|--------|
| **1. 打好技术深度** | 在一个领域做到"团队里最懂的几个人之一" |
| **2. 扩展广度** | 系统学习架构知识体系（本技能库的 10 个模块就是路线图） |
| **3. 开始记录决策** | 主动写 ADR；参与设计评审；练习表达取舍 |
| **4. 做小型设计** | 主导一个模块/子系统的设计，完整走一遍流程 |
| **5. 跨边界协作** | 参与跨团队设计；理解组织约束 |
| **6. 承担系统级设计** | 主导系统架构；对质量属性负责 |
| **7. 影响组织** | 推动架构治理、平台建设、团队拓扑调整 |

**刻意练习的方法**：
- **架构 Kata**：每周/每月一次限时设计演练
- **案例复盘**：分析经典系统的公开架构（Netflix、Uber、微信、淘宝的技术博客）
- **决策复盘**：回头看你做过的决策，哪些判断错了？为什么？
- **写出来**：把你的设计写成文档并请人评审——**写作会暴露思维的漏洞**
- **教别人**：能讲清楚才是真懂

### 5.4 架构师的常见陷阱

| 陷阱 | 表现 | 解法 |
|------|------|------|
| **象牙塔** | 脱离代码与团队 | 持续参与实现与值班 |
| **银弹崇拜** | 追新技术，忽视约束 | 先问"它解决什么被量化的问题" |
| **过度设计** | 为假想未来付出复杂度 | YAGNI；单向门才留余地 |
| **不做决策** | 只列选项不拍板 | 决策是职责；不决策也是决策 |
| **只会画图** | 图很漂亮，落地不了 | 图只是产物；重点是取舍与约束 |
| **忽视组织** | 设计超出团队能力 | 康威定律是约束 |
| **沟通失败** | 技术正确但没人执行 | 学会讲故事、对齐利益 |
| ** burnout** | 所有事都找你 | 培养他人；建立可扩展的决策机制（ADR + 评审 + 适应度函数） |

### 5.5 一句话总结

> **架构师的价值 = 在不确定性中做出可辩护的取舍，并让它被团队理解、执行、演化。**

## 常见误区

| 误区 | 纠正 |
|------|------|
| 一张图混所有抽象层次 | 用 C4 分层 |
| 把 C4 的 Container 当 Docker 容器 | 是可部署单元 |
| 架构文档写"是什么" | 重点是"为什么"（ADR） |
| 文档写在 Confluence 无人维护 | 与代码同仓、有所有者、过期即删 |
| 评审变成汇报 | 强制提问、现场出 ADR |
| 只画图不讲取舍 | 取舍才是重点 |
| 案例题追求"高级技术" | 约束识别与取舍更值钱 |
| 认为架构师=技术最强 | 判断力 + 沟通力占大头 |
| 脱离代码做架构 | 持续编码保持手感 |
