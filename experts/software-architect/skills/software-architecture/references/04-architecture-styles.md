# 04 · 架构风格与模式

> 本模块解决：**系统整体该长成什么形状？单体还是微服务？事件驱动值不值得？**

## 0. 选择架构风格的第一原则

**不要从风格出发，从驱动因素出发。**

每种风格都是一组**特定的取舍**。选风格 = 在"你最重要的 2–3 个质量属性"上做取舍。所以流程永远是：

```
驱动因素 → 风格候选（≥3） → 权衡矩阵 → 决策 → ADR
```

**没有"最好的风格"，只有"在当前约束下最合适的风格"。** 本模块的每种风格都会明确写出**它的代价**。

## 1. 分层 / N 层架构

### 1.1 结构

```
表现层 (Presentation)  →  业务层 (Business)  →  持久层 (Persistence)  →  数据库
```

**N 层**是分层的物理化：每一层可以部署在**不同的进程/机器**上（如：前端服务器 / 应用服务器 / 数据库服务器）。

| | 逻辑分层 (Layered) | 物理 N 层 (N-Tier) |
|---|-------------------|-------------------|
| 部署 | 同一进程内的模块 | 分布在多个进程/机器 |
| 成本 | 低（函数调用） | 高（网络调用、序列化） |
| 适用 | 绝大多数系统 | 需要独立扩缩容/安全隔离时 |

### 1.2 关键规则

**严格分层（Strict Layering）**：只能调用**相邻的下一层**。
**宽松分层（Relaxed Layering）**：可以调用**任意下层**。

**核心纪律**：**依赖只能向下，不能向上，不能跨层回环。**

### 1.3 代价与陷阱

| 代价 | 说明 |
|------|------|
| **变化传染** | 加一个字段要改所有层（DTO 地狱、样板代码） |
| **数据库驱动设计** | 分层容易退化为"围绕数据库表设计业务" |
| **层数膨胀** | 常见 6 层：Controller → Service → Manager → DAO → Entity → DTO，一半是纯转发（浅模块） |
| **业务逻辑泄漏** | 逻辑散落在 Service 和 Controller 里，领域层被架空 |

**最常见的反模式：把分层切成微服务**（前端服务 / 业务服务 / 数据服务）——这会导致**每次业务变更都要跨三个服务**，是分布式单体的一种。

> ✅ **适用**：团队小、业务简单、边界未稳定。**分层是一个很好的起点。**
> ❌ **不适用**：领域复杂、需要长期演化、多团队并行。

## 2. 模块化单体（Modular Monolith）

### 2.1 定义

**单一部署单元，但内部有严格的模块边界。** 模块之间通过**明确的接口**通信，不允许跨模块直接访问内部（包括数据库表）。

```
┌──────────────── 单体进程 ────────────────┐
│  订单模块  ←→  支付模块  ←→  库存模块      │
│     │            │            │          │
│   订单表        支付表        库存表       │
└──────────────────────────────────────────┘
   一个进程、一次部署、一套数据库（可按模块分 schema）
```

### 2.2 为什么它是**大多数团队的正确答案**

| 优势 | 说明 |
|------|------|
| **保留事务** | 单库事务，无需 Saga/Outbox |
| **本地开发简单** | 一个进程跑起来，调试无跨服务障碍 |
| **重构成本低** | 改边界 = 改包结构，而不是拆服务 |
| **部署简单** | 一条流水线 |
| **性能好** | 进程内调用，无网络开销 |
| **边界可以演进** | 边界错了随时调整，不用做服务拆分 |
| **未来可拆** | 边界清晰后，按模块拆服务是**机械操作** |

### 2.3 代价

| 代价 | 说明 |
|------|------|
| 无法独立扩缩容 | 订单模块的高负载会拖累整个进程 |
| 无法异构技术栈 | 全系统一个运行时 |
| 单点故障域 | 一个模块 OOM 影响全局 |
| 需要纪律 | 边界靠**适应度函数**守护，否则会腐化成大泥球 |
| 团队协调 | 多团队改同一代码库需要流程（如 CODEOWNERS） |

### 2.4 关键：边界必须有强制力

模块化单体最大的风险是**边界形同虚设**。必须用适应度函数强制：

- 用 ArchUnit / dependency-cruiser 断言"模块 A 不得 import 模块 B 的内部包"
- 断言"不得跨模块直连对方的表"
- 每个模块通过 `module-api` 包暴露接口，内部实现在 `module-internal`
- 语言级支持：Java 的 JPMS、.NET 的 internal、TS 的 `exports` 字段 / eslint 规则

> **判据**：如果你的模块化单体里，模块边界只靠"大家自觉遵守"，它就不是模块化单体，而是一个**还没腐化完的大泥球**。

### 2.5 什么时候该拆

模块化单体是**起点**，不是终点。拆分的触发信号：

| 信号 | 说明 |
|------|------|
| 独立扩缩容成为刚需 | 某模块负载是其他的 10 倍 |
| 独立部署成为刚需 | 某模块每天发布，其他每周发布 |
| 团队规模超过一个团队的协调能力 | 多个团队互相阻塞（康威定律） |
| 技术栈异构需求 | 需要 Python 做 ML、Go 做高并发 |
| 合规/隔离要求 | 支付模块需独立审计域 |
| 故障隔离要求 | 一个模块崩溃不得影响核心交易 |

> ⚠️ **不要因为"微服务是趋势"而拆。** 拆分是**付出分布式复杂度**换取**独立性与自治**的交易。先确认你真的需要那个交换。

## 3. 微服务 vs 单体

### 3.1 微服务的定义（容易混淆）

**微服务 ≠ 多个服务。** 关键特征：

| 特征 | 说明 |
|------|------|
| **围绕业务能力组织** | 按限界上下文切，不是按技术层 |
| **独立部署** | 可以单独发布，不影响其他服务 |
| **数据私有** | 每个服务拥有自己的数据，**禁止跨服务直连数据库** |
| **去中心化治理** | 技术栈可以异构，团队自治 |
| **轻量通信** | 通过 API/消息，而非共享内存 |
| **为失败设计** | 假设依赖一定会挂 |

> ⚠️ **不符合"数据私有 + 独立部署"的，只是"分布式的分层单体"（distributed monolith）**——它拿到了微服务的所有代价，却没有拿到任何好处。

### 3.2 分布式单体（反模式）

**症状**：
- 服务 A 改一个字段，服务 B、C 必须同步改、同步上线
- 服务之间直连对方的数据库
- 一个业务请求要同步串行调用 5 个服务
- 必须一起部署才能工作

**结果**：**你付出了微服务的全部复杂度，却保留了大泥球的全部耦合。**

### 3.3 决策表

| 维度 | 单体 | 微服务 |
|------|------|--------|
| 团队规模 | < 10 人合适 | 多个自治团队 |
| 边界成熟度 | 未稳定 → 单体 | 已稳定 → 可拆 |
| 事务需求 | 强一致事务多 → 单体 | 可接受最终一致 |
| 运维能力 | 有限 → 单体 | 有平台/SRE 能力 |
| 交付节奏 | 统一发布可接受 | 需独立发布 |
| 初始速度 | 快 | 慢（基础设施成本） |
| 长期复杂度 | 集中在代码 | 分散到运维与分布式 |
| 故障域 | 全局 | 可隔离 |

> **结论**：**微服务是一种组织规模化的手段，不是一种技术先进性标志。**
> **推荐路径**：模块化单体 → 边界稳定 → 按需拆分 → 微服务。**跳过前两步是大多数失败案例的原因。**

### 3.4 微服务的必备配套（拆之前先确认）

- [ ] 服务边界基于限界上下文（见 `05-domain-modeling.md`）
- [ ] 每个服务有独立的数据存储（或独立 schema + 无跨库访问）
- [ ] 有服务发现与配置中心
- [ ] 有分布式追踪（否则无法排障）
- [ ] 有熔断/重试/超时/限流（见 `09-evolution-and-production.md`）
- [ ] 有 CI/CD 流水线（每服务独立）
- [ ] 有契约测试（消费者驱动）
- [ ] 团队有分布式系统经验或愿意投入学习
- [ ] 有处理最终一致性的方案（Saga/Outbox，见 `06-data-and-persistence.md`）

**没配齐就拆 = 生产事故的温床。**

## 4. 六边形、洋葱与整洁架构

这三种风格**本质上是同一件事的三个变体**：**把领域逻辑放在中心，把技术细节推到边缘，依赖方向指向中心。**

### 4.1 六边形架构（Ports & Adapters, Cockburn）

```
         ┌──────── 驱动适配器 ────────┐
         │  REST / CLI / 定时任务      │
         └───────────┬───────────────┘
                     ↓ 驱动端口 (inbound port)
        ┌────────────领域模型────────────┐
        │   （业务逻辑，不依赖任何框架）    │
        └───────────┬───────────────┘
                     ↑ 被驱动端口 (outbound port)
         ┌───────────┴───────────────┐
         │  DB / MQ / 外部 API 适配器   │
         └──────── 被驱动适配器 ────────┘
```

| 概念 | 说明 |
|------|------|
| **端口 Port** | 定义在**领域侧**的接口（由领域定义，不是由实现定义） |
| **驱动端口 Inbound** | 外部如何调用领域（用例接口） |
| **被驱动端口 Outbound** | 领域如何调用外部（仓储/网关接口） |
| **适配器 Adapter** | 端口的具体技术实现（HTTP controller、JPA repository） |

**关键收益**：**领域逻辑可以脱离框架独立测试**。测试时用内存实现替换适配器，不需要启动数据库。

### 4.2 洋葱架构（Onion, Palermo）

同心圆，依赖方向从外向内：

```
基础设施 / 框架 / 驱动  （最外）
    ↑
应用服务 / 用例
    ↑
领域服务
    ↑
领域模型（实体、值对象、领域事件）  （最内，零依赖）
```

**规则：内层不知道外层的存在。**

### 4.3 整洁架构（Clean, Martin）

同样是同心圆，层次为：Entities → Use Cases → Interface Adapters → Frameworks & Drivers。

**核心规则（Dependency Rule）**：**源代码依赖只能指向内层。**

### 4.4 三者对比

| | 六边形 | 洋葱 | 整洁 |
|---|-------|------|------|
| 核心概念 | 端口与适配器 | 同心圆层次 | 依赖规则 |
| 强调 | 内外对称（驱动/被驱动） | 领域服务层次 | 用例（Use Case）为中心 |
| 实质 | **相同**：领域居中、依赖向内、技术细节在边缘 | | |

> **选哪个不重要，重要的是理解同一个原理**：**依赖倒置 + 关注点分离 → 领域独立于技术。**
> 实践中最常用的是**六边形（端口与适配器）**的术语，因为它最清楚地表达了"谁调用谁"。

### 4.5 代价与陷阱

| 代价 | 说明 |
|------|------|
| 样板代码多 | 每层一个 DTO、一个 Mapper（浅模块风险） |
| 学习曲线 | 团队不熟悉时容易画成"三层的马甲" |
| 小项目过度设计 | CRUD 应用不需要六边形 |
| 容易形式化 | 有了 `domain/` 包但逻辑还在 service 里 |

> ✅ **适用**：领域复杂、生命周期长、需要可测试性、需要替换基础设施（如换数据库/换消息中间件）。
> ❌ **不适用**：简单的 CRUD、一次性脚本、原型。

**判据**：**如果换成另一个框架/数据库需要改动领域代码，说明你的依赖方向错了。**

## 5. 事件驱动、CQRS 与事件溯源

### 5.1 事件驱动架构（EDA）

**组件之间通过"事件"通信，而不是直接调用。**

| 概念 | 说明 |
|------|------|
| **事件 Event** | 已发生事实的不可变记录（"OrderPlaced"） |
| **命令 Command** | 请求做某事（"PlaceOrder"）——**可以有多个消费者拒绝执行** |
| **事件通知** | 事件只携带 ID，消费者回来查详情（耦合低，但多一次调用） |
| **事件携带状态转移** | 事件带完整数据，消费者无需回查（耦合稍高，但更健壮） |

**拓扑**：
- **中介者拓扑（Broker）**：事件 → 消息代理 → 多个消费者（无中心编排，简单）
- **代理者拓扑（Mediator）**：事件 → 编排器 → 命令 → 各服务（有中心，可编排复杂流程）

**优势**：松耦合、异步削峰、可扩展、天然支持多消费者、容错性好
**代价**：最终一致性、调试困难、消息顺序与重复处理、运维复杂度、**很难做"整体状态"查询**

### 5.2 CQRS（命令查询职责分离）

**读写分离为两个模型。**

```
命令侧 (Write)              查询侧 (Read)
  ↓ 处理业务规则               ↓ 为查询优化
写模型（规范化）  ──事件──→  读模型（反规范化/物化视图）
   强一致                       最终一致
```

| 级别 | 说明 | 复杂度 |
|------|------|--------|
| **基础级** | 同一个数据库，读写用不同的 Repository/Service | 低 |
| **中级** | 读模型是独立的表/视图，通过事件同步 | 中 |
| **高级** | 读写用不同的存储（写 PostgreSQL，读 Elasticsearch） | 高 |

**什么时候值得**：
- ✅ 读写负载差异极大（如 100:1）
- ✅ 读模型需要复杂的反规范化/聚合
- ✅ 读和写的性能优化方向冲突
- ❌ **读写负载相近的 CRUD —— 不要用 CQRS**，纯属增加复杂度

### 5.3 事件溯源（Event Sourcing）

**不存储当前状态，存储导致状态变化的事件序列。** 当前状态 = 重放所有事件。

```
传统：Account { balance: 150 }
事件溯源：AccountCreated(100) → MoneyDeposited(80) → MoneyWithdrawn(30)  ⇒ 重放得 150
```

| 优势 | 说明 |
|------|------|
| **完整审计** | 每一次变化都有记录（天然满足审计要求） |
| **时态查询** | 可以问"上周三的余额是多少" |
| **可回放** | 修复 bug 后重放事件得到正确状态 |
| **天然事件驱动** | 事件就是集成契约 |

| 代价 | 说明 |
|------|------|
| **复杂度高** | 快照、版本演进、事件 schema 变更都是硬问题 |
| **查询困难** | 需要配合 CQRS 才能高效查询 |
| **最终一致** | 读模型滞后 |
| **事件不可变** | 写错了只能补偿，不能改 |
| **团队门槛高** | 需要领域事件建模能力 |

**事件版本演进**的常见手法：事件升级（upcasting）、弱 schema（只加字段）、事件重写（重放时转换）。

> ⚠️ **事件溯源是重型武器。** 只在**审计/回放/时态**是核心需求时使用（金融账本、合规系统、协作编辑）。**不要为了"优雅"而用。**

### 5.4 三者关系

```
事件驱动（通信风格）
   ├── CQRS（读写分离）—— 可独立使用
   └── 事件溯源（存储风格）—— 通常配合 CQRS 使用
```

**它们可以独立采用**，但组合使用（EDA + CQRS + ES）会带来**叠加的复杂度**。逐项评估是否真的需要。

## 6. 风格选型速查

| 你的首要驱动因素 | 起点建议 | 主要代价 |
|----------------|---------|---------|
| 快速交付、边界未定、团队小 | 分层单体 → 模块化单体 | 后期拆分开销 |
| 多团队独立交付、边界清晰 | 微服务（按限界上下文） | 分布式复杂度、运维成本 |
| 领域复杂、长生命周期 | 六边形 + 模块化单体 | 样板代码、学习曲线 |
| 读写负载严重不对称 | CQRS | 最终一致、复杂度 |
| 审计/回放/时态是核心 | 事件溯源 + CQRS | 高复杂度、团队门槛 |
| 大量异步、削峰、多消费者 | 事件驱动 + 消息队列 | 调试难、最终一致 |
| 遗留系统渐进替换 | 绞杀者模式（见模块 09） | 双系统并行期成本 |

> **再次强调**：上表是**起点**，不是结论。任何一格都要走 `decision-frameworks.md` 的权衡流程，并把结论写成 ADR。

## 常见误区

| 误区 | 纠正 |
|------|------|
| 微服务 = 多个服务 | 核心是**独立部署 + 数据私有 + 业务边界** |
| 按技术层切服务 | 按业务能力/限界上下文切 |
| 先拆微服务再想边界 | 先模块化单体把边界磨稳 |
| 分布式单体 | 检查是否"必须一起部署" |
| CRUD 应用上 CQRS/ES | 复杂度远超收益 |
| 为"优雅"用事件溯源 | 只在审计/回放/时态是核心需求时 |
| 六边形只画包结构 | 关键是**依赖方向**，不是目录名 |
| 认为分层没有价值 | 分层是很好的起点；问题在于**切服务**时按层切 |
