# 决策框架（横向工具）

> **任何架构决策类问题，先读本文件。** 这里是把"感觉"变成"可辩护的决策"的工具箱。

## 1. 权衡分析（Tradeoff Analysis）

### 1.1 六步法

```
1. 明确驱动因素
2. 列备选（≥3，含"什么都不做"）
3. 定评价维度（3–6 个关键质量属性）
4. 逐项打分（+ / 0 / −，能定量就定量）
5. 标出敏感点与取舍点
6. 判断可逆性 → 拍板 → 写 ADR
```

### 1.2 权衡矩阵模板

| 评价维度（权重） | 方案 A | 方案 B | 方案 C（什么都不做） |
|----------------|--------|--------|-------------------|
| 属性 1（高） | + | 0 | − |
| 属性 2（高） | − | + | + |
| 属性 3（中） | 0 | + | 0 |
| **初始成本** | 中 | 高 | 低 |
| **持续成本** | 低 | **高** | 低 |
| **可逆性** | 双向门 | 单向门 | — |
| **总分** | ? | ? | ? |

**打分规则**：
- `+` 优于基线；`0` 与基线相当；`−` 劣于基线
- **权重必须显式**：不能"各项都好"——那就说明维度选错了
- **区分初始成本与持续成本**：持续成本才是长期负担

### 1.3 常见评价维度清单

**技术维度**：性能、可用性、一致性、可伸缩性、可修改性、可测试性、可部署性、安全性、可观测性
**组织维度**：团队认知负荷、运维负担、招聘难度、学习曲线、交付速度
**经济维度**：初始成本、持续成本（基础设施 + 人力）、迁移成本、锁定风险
**时间维度**：上线时间、演化灵活性、可逆性

## 2. 敏感点与取舍点

| 术语 | 定义 | 你要做什么 |
|------|------|-----------|
| **敏感点 Sensitivity Point** | 某决策对某属性高度敏感（改一点，属性大幅变化） | 重点验证；可能是性能/可用性的"承重墙" |
| **取舍点 Tradeoff Point** | 某决策同时影响两个以上属性且方向相反 | **这是真正需要拍板的地方**；写进 ADR |
| **风险 Risk** | 可能危及驱动因素的决策 | 制定缓解措施 |
| **非风险 Non-risk** | 已验证安全的关键决策 | 可以放心 |
| **风险主题 Risk Theme** | 跨决策的系统性风险（如"团队缺分布式经验"） | 组织层面应对（培训、招人、缩范围） |

**实操**：评审时对每个关键决策标注"它是敏感点还是取舍点？"——**标不出来的，说明还没想透。**

## 3. 质量属性场景（Quality Attribute Scenario）

### 3.1 六要素模板

| 要素 | 含义 | 示例 |
|------|------|------|
| **刺激源 Source** | 谁/什么触发 | 外部用户、定时任务、另一个系统 |
| **刺激 Stimulus** | 发生了什么 | 发起下单请求 |
| **制品 Artifact** | 作用于什么 | 订单服务 |
| **环境 Environment** | 什么条件下 | 促销峰值（10 倍日常流量） |
| **响应 Response** | 系统应如何反应 | 创建订单并返回订单号 |
| **响应度量 Measure** | 怎么判断成功 | P99 < 2s，成功率 ≥ 99.9% |

### 3.2 各质量属性的场景模板

| 属性 | 刺激 | 响应度量 |
|------|------|---------|
| **性能** | 并发用户发起请求 | 延迟分位数、吞吐量 |
| **可用性** | 某组件故障 | 故障期间可用性百分比、恢复时间 |
| **可修改性** | 提出一个变更 | 完成变更的工时、影响文件数 |
| **可测试性** | 提交一个变更 | 验证所需时间、可独立测试的单元比例 |
| **安全性** | 发起攻击 | 检测/抵御率、暴露窗口 |
| **可部署性** | 发布新版本 | 部署时长、失败率、回滚时间 |
| **可伸缩性** | 负载增加 N 倍 | 资源增加比例、性能保持度 |

### 3.3 好场景 vs 坏场景

| | 坏 | 好 |
|---|----|----|
| 性能 | "系统要快" | "10 万并发下单，P99 < 2s" |
| 可用性 | "要高可用" | "单机房故障时，30s 内切换，RPO = 0" |
| 可修改性 | "代码要好改" | "新增一种支付方式，改动 ≤ 2 人天，不影响其他支付" |

> **判据**：**能不能被测量/验证？** 不能 → 不是场景，是口号。

## 4. 复杂度预算

### 4.1 心智模型

```
复杂度预算 = 团队能持续承受的复杂度上限
支出 = 服务数 + 部署单元 + 存储种类 + 技术栈 + 抽象层 + 异步链路
偿还能力 = 团队的交付速度与运维能力
透支信号 = 交付变慢 / 故障变多 / 新人上手难 / 无人敢改
```

### 4.2 复杂度支出速查（每项都是**持续**成本）

| 引入 | 持续成本 |
|------|---------|
| 一个微服务 | 流水线、监控、告警、日志、契约、本地环境、跨服务调试 |
| 一种数据存储 | 备份恢复、运维、驱动升级、一致性、团队学习 |
| 服务网格 | Sidecar 开销、配置复杂度、排障难度 |
| 事件链路 | 最终一致、幂等、顺序、死信、可观测性 |
| 一层抽象 | 理解成本、调试穿透、样板代码 |
| 一个新语言/框架 | 招聘、培训、工具链、生态 |

### 4.3 复杂度体检问题

- 新人多久能独立提交第一个生产变更？（> 2 周 → 偏高）
- 本地能跑起完整系统吗？
- 一次需求变更平均涉及几个部署单元？（> 3 → 偏高）
- 有几个人能解释整体架构？（< 2 → 知识集中风险）
- 有多少个"没人敢动"的模块？
- 部署需要几步人工操作？（> 0 → 偏高）

## 5. 可逆性判断（单向门 / 双向门）

| | 单向门 One-way Door | 双向门 Two-way Door |
|---|-------------------|-------------------|
| 特征 | 难回退、成本高、影响面大 | 易回退、成本低、局部 |
| 例子 | 数据模型、数据库选型、服务边界、公共 API 契约、领域模型、云厂商锁定、分区键 | UI 布局、内部实现、缓存策略、日志格式、模块内部结构、类设计 |
| 投入 | 充分论证、多方案、写 ADR、找反例 | 快速决定、快速试错 |
| 错误 | 草率决定 | 反复论证（浪费） |

**判断问题**：
1. 回退要多久、多少钱、影响多少数据？
2. 有多少外部方依赖它？
3. 回退会造成数据丢失或不一致吗？

> **最高杠杆的思维工具。** 先分类，再决定投入多少论证成本。

## 6. ATAM-lite（轻量架构评估）

**ATAM（Architecture Tradeoff Analysis Method）的务实裁剪版。**

### 流程（1–2 小时）

| 步骤 | 内容 | 产出 |
|------|------|------|
| 1. 呈现驱动因素 | 业务目标 + 关键质量属性（按优先级） | 驱动因素表 |
| 2. 呈现架构 | C4 Context + Container | 架构图 |
| 3. 识别架构方法 | 用了哪些模式/策略 | 方法清单 |
| 4. 构建效用树 | 质量属性 → 可度量场景，按优先级排序 | 效用树 |
| 5. 分析 | 对高优先级场景，找出敏感点与取舍点 | 敏感点/取舍点清单 |
| 6. 识别风险 | 哪些决策可能危及驱动因素 | 风险清单 + 缓解 |
| 7. 风险主题 | 跨决策的系统性风险 | 主题清单 |

### 效用树（Utility Tree）结构

```
效用 Utility
├── 性能 Performance（优先级：高）
│   ├── (H,H) 促销峰值下单 P99 < 2s        ← (业务价值, 技术风险)
│   └── (M,L) 报表查询 < 5s
├── 可用性 Availability（优先级：高）
│   └── (H,H) 单机房故障 30s 内切换，RPO=0
├── 可修改性 Modifiability（优先级：中）
│   └── (M,M) 新增支付方式 ≤ 2 人天
└── 安全性 Security（优先级：高）
    └── (H,M) 敏感数据全程加密，密钥可轮换
```

**括号内 (业务价值, 技术风险)** 用于排序：**(H,H) 的场景最先分析。**

### 输出模板

| # | 场景 | 类型 | 架构方法 | 敏感点 | 取舍点 | 风险 | 缓解 |
|---|------|------|---------|--------|--------|------|------|
| 1 | 促销峰值 P99 < 2s | 性能 | 读写分离 + 缓存 | 缓存命中率 | 缓存 vs 一致性 | 缓存雪崩 | 预热 + 互斥重建 |
| 2 | 单机房故障切换 | 可用性 | 多可用区部署 | 复制延迟 | 一致性 vs 可用 | 脑裂 | Quorum 写 |

## 7. 容量估算（Ferment 到数字）

**架构讨论必须落到数字。以下是常用估算方法。**

### 7.1 基础换算（记住）

| 换算 | 值 |
|------|-----|
| 1 天 | 86,400 秒 ≈ **10^5 秒** |
| 100 万请求/天 | ≈ **12 QPS**（均值） |
| 1 亿请求/天 | ≈ **1,200 QPS**（均值） |
| 峰值系数 | 通常取均值的 **3–10 倍** |
| 1 条记录 1KB × 1 亿 | = **100 GB** |
| 单机 PostgreSQL | 千万级~亿级行尚可（取决于查询） |
| 单机 Redis | 十万级 QPS（简单命令） |
| 单机 Kafka | 十万级消息/秒（视消息大小） |

### 7.2 存储估算示例

```
日活用户 1000 万，人均日产生 10 条行为记录，每条 1KB
日增数据 = 1000万 × 10 × 1KB = 100 GB/天
年增数据 = 100 GB × 365 ≈ 36 TB/年
3 年 + 3 副本 ≈ 36 × 3 × 3 = 324 TB
→ 结论：单机扛不住，需要分区 + 冷热分层 + 副本策略权衡
```

### 7.3 延迟预算分解

```
端到端目标：P99 < 500ms
├── 网络（客户端 → 网关）   50ms
├── 网关处理                 10ms
├── 应用逻辑                 50ms
├── 缓存查询                 5ms
├── 数据库查询（未命中缓存）  100ms
├── 下游服务调用             100ms
└── 序列化/网络返回          50ms
                            ─────
合计预算                    365ms（留 135ms 余量）
→ 任何一跳超预算，就要重新分配或优化
```

## 9. 一页纸决策模板（快速版）

```markdown
## 决策：<一句话>

**驱动因素**：<2-3 条关键质量属性 / 约束>

**备选方案**
- A：<描述> — 代价：<...>
- B：<描述> — 代价：<...>
- C（什么都不做）：<描述> — 代价：<...>

**权衡**（关键维度）
| 维度 | A | B | C |
|------|---|---|---|
| ...  | + | 0 | − |

**推荐**：A
**理由**：<为什么在当前约束下最优>
**代价**：<你会失去什么>
**前提**：<什么条件下这个建议失效>
**可逆性**：单向门 / 双向门
**重估触发点**：<出现什么信号时回头改>
**落地第一步**：<下周就能开始做什么>
```
