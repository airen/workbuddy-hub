# 05 · 领域建模

> 本模块解决：**系统该切成几块？每块的边界在哪？怎么让业务和技术说同一种话？**

DDD（Domain-Driven Design）分两半：**战略设计**（划边界、建模型）和**战术设计**（聚合、实体、值对象）。**战略设计对架构的影响远大于战术设计**，但初学者常只学战术部分。

## 1. DDD 战略设计

### 1.1 核心概念：领域 / 子域

| 概念 | 定义 | 例子（电商） |
|------|------|-------------|
| **领域 Domain** | 软件要解决的业务范围 | 电商 |
| **子域 Subdomain** | 领域的细分部分 | 商品、订单、支付、物流、营销 |
| **核心域 Core Domain** | 竞争差异化所在，**必须自研并投入最强资源** | 推荐算法、定价引擎 |
| **支撑域 Supporting** | 业务需要但不差异化的，**可自研也可外包** | 订单管理、库存管理 |
| **通用域 Generic** | 通用能力，**优先采购/复用** | 认证、短信、支付通道 |

**核心洞察**：**不是所有代码都值得精心设计。** 把最好的架构师放在核心域上，通用域直接买现成的。

> **实操**：做一次"子域盘点"，标注每个子域的类型。核心域才值得上 DDD 战术模式（聚合/领域事件）。

### 1.2 为什么要划边界

**边界是架构最重要的概念。** 划边界的目的是：
- 限制模型的范围，避免"一个模型管所有业务"导致的概念污染
- 让团队能独立演进
- 让变化被隔离

**关键洞见（Eric Evans）**：**一个大模型无法同时满足所有业务场景。** "商品"在**销售**语境下是"可售卖的东西（有价格、库存、促销）"，在**物流**语境下是"可运输的包裹（有重量、体积、危险品标识）"，在**财务**语境下是"一个会计科目"。**硬要统一成一个 `Product` 类，会得到一个谁都不满意的巨型对象。**

→ 所以需要**限界上下文**。

## 2. 限界上下文与上下文映射

### 2.1 限界上下文（Bounded Context）

**定义**：一个**显式的边界**，边界内的模型有**明确且一致的**含义。

**一个限界上下文 = 一个模型 = 一个通用语言 = （通常）一个团队 = （可能）一个服务。**

**关键性质**：
- **同一术语在不同上下文中可以有不同含义**（这是特性，不是 bug）
- 上下文内部模型一致；跨上下文必须通过**明确的映射**沟通
- 上下文边界**不一定要和服务边界一一对应**——一个上下文可以是模块化单体里的一个模块

### 2.2 怎么找限界上下文

**方法（按有效性排序）**：

| 方法 | 做法 |
|------|------|
| **事件风暴 Event Storming** | 召集业务+技术，用便利贴铺出领域事件（橙色）、命令（蓝色）、聚合（黄色）、策略（紫色），自然浮现边界 |
| **业务能力分析** | 列出组织提供哪些业务能力，能力边界 ≈ 上下文边界 |
| **语言边界** | 同一个词在哪个范围里含义一致？不一致处就是边界 |
| **组织结构** | 团队职责边界（康威定律，见 `02-architecture-thinking.md`） |
| **数据所有权** | 哪些数据必须一起变更？哪些可以独立？ |

**判断边界好坏的三个问题**：
1. 这个上下文内部的模型，能不能用一套**不矛盾**的语言描述？
2. 这个上下文能不能**独立演进**（改它不太影响别的上下文）？
3. 一个**小团队**能不能完整理解并拥有它？

> ⚠️ **边界不是一次划对的。** 应该先划一版，然后在演进中调整。**所以早期不要拆成服务**——模块化单体让边界调整成本极低（见 `04-architecture-styles.md`）。

### 2.3 上下文映射（Context Mapping）—— 九种关系

两个上下文之间的关系模式。**选哪种关系，决定了耦合强度和团队的权力关系。**

| 模式 | 说明 | 耦合 | 权力关系 |
|------|------|------|---------|
| **合作关系 Partnership** | 两个团队共同规划、同步发布 | 高 | 对等 |
| **共享内核 Shared Kernel** | 共享一小块代码/模型 | 高 | 对等（危险） |
| **客户-供应商 Customer-Supplier** | 下游依赖上游，上游考虑下游需求 | 中 | 上游 > 下游 |
| **遵奉者 Conformist** | 下游无条件采用上游模型（不做翻译） | 中 | 上游 >> 下游 |
| **防腐层 ACL** | 下游加一层翻译，隔离上游模型 | 低 | 下游自主 |
| **开放主机服务 OHS** | 上游提供一套公开的、稳定的服务协议 | 中 | 上游主导 |
| **发布语言 PL** | 上游发布一套公用的、有文档的数据交换格式 | 中 | 上游主导 |
| **各行其道 Separate Ways** | 两个上下文无集成，各自独立 | 无 | 完全独立 |
| **大泥球 Big Ball of Mud** | 边界混乱的遗留系统 | 极高 | — |

**实操建议**：
- **优先用 ACL**：当下游不希望被上游模型污染时，加一层翻译是最便宜的隔离手段
- **谨慎用 Shared Kernel**：共享代码 = 强制同步发布，多团队场景下是灾难
- **识别 Big Ball of Mud**：如果必须集成遗留系统，用 ACL 把它包起来，别让它污染你的模型

**上下文映射图**：画一张图，节点是上下文，边是关系模式。**这是最有价值的架构图之一**（比组件图更有信息量）。

## 3. 聚合、实体与值对象（战术设计）

> ⚠️ 战术模式只在**核心域/复杂子域**内使用。CRUD 场景用它们是浪费。

### 3.1 实体（Entity）

**有唯一标识、生命周期内标识不变、属性可变。**

- 判据：**两个对象即使所有属性相同，如果 ID 不同，它们仍是不同的东西**
- 例子：订单（订单号）、用户（用户 ID）
- 实现：有 ID 字段，`equals()` 基于 ID

### 3.2 值对象（Value Object）

**没有标识，只由属性定义，不可变。**

- 判据：**两个对象属性相同就是同一个东西**
- 例子：金额（币种 + 数值）、地址、日期范围、颜色
- 实现：不可变（immutable）、`equals()` 基于所有属性

**为什么值对象重要**：
- **可安全共享**（不可变）
- **消除基本类型偏执**（Primitive Obsession）：不要用 `String` 表示邮箱、`BigDecimal` 表示金额——用 `Email`、`Money` 类型，把校验和规则内聚进去
- **表达力强**：`Money(100, "CNY")` 比 `100` 清晰得多

> **架构师建议**：**优先用值对象。** 大多数"实体"其实应该是值对象。值对象越多，模型越稳（不可变的东西不会坏）。

### 3.3 聚合（Aggregate）与聚合根（Aggregate Root）

**定义**：**一组必须保持一致性的对象的集合**，通过**聚合根**作为唯一入口访问。

**聚合的核心规则（Evans / Vernon）**：

| 规则 | 说明 |
|------|------|
| **一致性边界** | 聚合是**事务一致性**的边界：一次事务只改一个聚合 |
| **唯一入口** | 外部只能通过聚合根访问聚合内部对象 |
| **引用其他聚合用 ID** | 聚合之间只存 ID，不存对象引用 |
| **小聚合** | 聚合应该尽量小（Vernon 的建议：多数情况只有一个实体 + 值对象） |
| **最终一致跨聚合** | 跨聚合的一致性通过领域事件 + 最终一致实现 |

**为什么"小聚合"很重要**：
- 聚合 = 锁的粒度。大聚合 → 并发冲突多 → 吞吐低
- 聚合 = 加载粒度。大聚合 → 一次加载大量数据
- **经典错误**：把 `Order` + `Customer` + `Product` + `Payment` 做成一个聚合 → 每次下单锁住整个客户和商品

**聚合设计流程**：
1. 找出**业务不变量**（"订单总额必须等于明细之和"、"库存不能为负"）
2. 需要**强一致**维护的不变量 → 放在**同一个聚合**内
3. 可以**最终一致**的 → 拆成**不同聚合**，用领域事件协调

> **判据**：**"这两样东西必须在一个事务里同时成功或同时失败吗？"** 是 → 同聚合；否 → 不同聚合。

### 3.4 领域事件（Domain Event）

**领域内发生的有业务意义的事实。** 命名用**过去时**：`OrderPlaced`、`PaymentReceived`、`InventoryReserved`。

**用途**：
- 聚合间协调（最终一致）
- 触发跨上下文集成
- 审计与回放
- 解耦（发布者不知道订阅者）

**注意**：领域事件（内部，领域模型的一部分）≠ 集成事件（跨上下文，是公开契约）。两者应分离，集成事件是**稳定的对外格式**。

### 3.5 仓储（Repository）

**为聚合提供持久化的"集合式"访问接口。**

- 一个聚合一个 Repository
- 接口定义在**领域层**（依赖倒置），实现在基础设施层
- **只用于聚合根**，不为每个实体建 Repository
- 不要暴露查询语言细节（`findByXxxAndYyy` 泛滥是坏味道 → 考虑 Specification 模式或 CQRS 读模型）

### 3.6 领域服务 / 应用服务

| | 应用服务 Application Service | 领域服务 Domain Service |
|---|---------------------------|----------------------|
| 职责 | 编排用例：加载聚合 → 调用领域逻辑 → 保存 → 发事件 | 承载**不属于任何单一实体**的领域逻辑 |
| 是否含业务规则 | **否**（薄） | **是** |
| 例子 | `OrderApplicationService.placeOrder(cmd)` | `PricingService.calculateDiscount(order, customer)` |

> ⚠️ **最常见错误**：把业务逻辑全写在应用服务里，领域模型退化成贫血的 DTO（**贫血模型反模式**）。

## 4. 通用语言（Ubiquitous Language）

### 4.1 定义

**在限界上下文内，业务专家和开发者使用同一套、无歧义的语言。** 这套语言直接体现在**代码命名**中。

### 4.2 为什么重要

- **消除翻译损耗**：业务说"授信额度"，代码里叫 `credit_limit`，不是 `max_amount` 或 `field3`
- **暴露模型缺陷**：当你无法用业务语言命名一个类时，说明模型错了
- **降低沟通成本**：需求讨论、代码评审、文档使用同一套词汇

### 4.3 怎么建立

| 做法 | 说明 |
|------|------|
| **词汇表（Glossary）** | 维护一个术语表，随代码一起版本管理 |
| **代码即语言** | 类名/方法名/变量名必须用业务术语 |
| **业务参与建模** | 让领域专家参与事件风暴和模型评审 |
| **发现歧义就停下来** | "你说的'客户'和财务说的'客户'是同一个吗？" |
| **禁止技术词污染** | 不要出现 `OrderManager`、`DataHelper`、`ProcessUtil` |

**通用语言的边界性**：**同一术语在不同限界上下文可以有不同含义，这是允许的。** 试图建立一个"全公司统一的术语表"往往导致模型僵化。**每个上下文有自己的语言。**

## 5. 防腐层（Anti-Corruption Layer, ACL）

### 5.1 定义

**在上下文边界上的一层翻译层，把外部模型的术语/结构转换成内部模型的术语/结构。**

```
你的上下文                  防腐层                    外部/遗留系统
Order (领域模型)  ←→  OrderTranslator  ←→  遗留的 ORD_MST 表结构
                     映射 + 转换逻辑
```

### 5.2 什么时候必须用 ACL

| 场景 | 说明 |
|------|------|
| 集成**遗留系统** | 老系统的模型又脏又乱，绝不能让它渗入新模型 |
| 集成**第三方 API** | 第三方随时改 schema，ACL 把变更挡在外面 |
| 集成**外部团队的服务** | 对方模型与你的不一致（遵奉者的替代方案） |
| 跨上下文调用 | 上游模型不稳定，ACL 保护下游 |

### 5.3 ACL 的形态

| 形态 | 说明 |
|------|------|
| **转换器（Translator）** | 结构/命名转换（DTO ↔ 领域对象） |
| **适配器（Adapter）** | 协议转换（SOAP ↔ REST） |
| **门面（Facade）** | 把多个外部调用聚合为一个 |
| **拦截器/中间件** | 横切处理（鉴权、限流、日志） |

### 5.4 代价

| 代价 | 说明 |
|------|------|
| 额外的代码量与维护成本 | 每个集成点一套映射 |
| 性能开销 | 多一层转换（通常可忽略） |
| 调试复杂度 | 多一层，排障链路变长 |
| **映射漂移** | 外部系统变了，ACL 忘了更新 → 需要契约测试守护 |

> **权衡**：ACL 的成本是**确定的、局部的**；不设 ACL 的成本是**不确定的、会传染的**。集成遗留系统时，**默认加 ACL**。

## 6. DDD 落地的现实建议

| 建议 | 理由 |
|------|------|
| **先战略，后战术** | 边界划错，战术模式再漂亮也没用 |
| **只在核心域用战术模式** | 通用域直接买现成的 |
| **不要一上来就拆服务** | 模块化单体让边界可低成本调整 |
| **限界上下文 ≠ 微服务** | 一个上下文可以是单体里的一个模块 |
| **领域事件不要当集成事件用** | 内部模型会演进，公开契约要稳定 |
| **警惕贫血模型** | 逻辑必须在领域层，不在应用服务里 |
| **聚合要小** | 大聚合 = 低并发 + 高加载成本 |
| **ACL 保护你的模型** | 集成遗留/第三方时默认加 |
| **通用语言是活的** | 随业务演进，不要一次定死 |

## 常见误区

| 误区 | 纠正 |
|------|------|
| DDD = 聚合 + 仓储 + 值对象 | 战略设计（边界）才是核心 |
| 全公司一个统一模型 | 每个限界上下文有自己的模型和语言 |
| 限界上下文 = 微服务 | 上下文可以是模块 |
| 大聚合（一个聚合装下整个业务） | 聚合要小，跨聚合用最终一致 |
| 应用服务里写业务逻辑 | 那是贫血模型；逻辑属于领域层 |
| 领域事件直接当对外契约 | 领域事件和集成事件要分离 |
| 集成遗留系统不加 ACL | 默认加 ACL，隔离污染 |
| 所有子域都精心设计 | 只对核心域投入 |
