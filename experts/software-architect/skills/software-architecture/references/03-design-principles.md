# 03 · 设计原则

> 本模块解决：**怎么划边界？怎么控制依赖方向？怎么在"该抽象"和"该简洁"之间做判断？**

## 1. SOLID

SOLID 是面向对象设计的五条原则。**注意：它们是"启发式规则"，不是法律。** 过度套用会导致抽象爆炸（见 §4 YAGNI）。

### 1.1 S — 单一职责原则 (SRP)

**原始定义**：一个模块应该**只有一个变更的理由**（只有一个 actor 会要求它变更）。

> ⚠️ 常见误读："一个类只做一件事"。正确理解是**"只有一个利益相关者能要求它变更"**。比如 `Employee` 类同时承担"计算工资"（财务要改）和"生成报表"（HR 要改）→ 两个变更理由 → 违反 SRP。

**怎么用**：问"谁会要求改它？"如果有两个不同的答案，就该拆。

### 1.2 O — 开闭原则 (OCP)

**定义**：软件实体应该**对扩展开放，对修改关闭**。

**怎么用**：用**多态/策略/插件**替代"加一个 if-else 分支"。但注意——**OCP 不是为了消灭所有 if，而是为了在"变化轴上"稳定**。如果变化不频繁，一个 if 更简单。

**代价**：过度使用导致抽象层数激增、调试困难。

### 1.3 L — 里氏替换原则 (LSP)

**定义**：子类型必须能够替换其基类型而不破坏程序正确性。

**违反的典型信号**：
- 子类方法抛出基类没有的异常
- 子类需要更强的前置条件 / 更弱的后置条件
- 出现 `if (x instanceof SpecialCase)` 这种类型检查

**为什么重要**：LSP 是**多态可信的前提**。违反 LSP 的继承体系会让调用方不得不做类型检查，多态就废了。

### 1.4 I — 接口隔离原则 (ISP)

**定义**：客户端不应该被迫依赖它不使用的方法。

**怎么用**：把"胖接口"拆成多个"角色接口"。比如 `IWorker` 有 `work()` 和 `eat()`，机器人无法 `eat()` → 拆成 `IWorkable` 和 `IEatable`。

**架构级含义**：**服务/模块的公开 API 也应该按消费者角色拆分**。一个服务暴露一个 50 方法的巨型 API，消费者被迫依赖一堆用不到的契约。

### 1.5 D — 依赖倒置原则 (DIP)

**定义**：
1. 高层模块不应依赖低层模块，二者都应依赖**抽象**
2. 抽象不应依赖细节，细节应依赖抽象

**这是 SOLID 中对架构影响最大的一条。** 它直接决定了**依赖方向**。

```
❌ 传统分层（高层依赖低层）
业务逻辑 → 数据库驱动 → 数据库

✅ 依赖倒置
业务逻辑 → [接口/端口] ← 数据库适配器
              ↑
         业务逻辑定义接口，基础设施实现接口
```

**关键洞察**：**接口应该由"使用者"定义，而不是"实现者"。** 这就是端口与适配器（§3）的理论基础。

**架构级应用**：
- 领域层定义 `OrderRepository` 接口，基础设施层用 JPA/MyBatis 实现
- 应用层定义 `PaymentGateway` 接口，基础设施层对接支付宝/微信
- 这样领域逻辑**不依赖任何框架**，可独立测试、可替换实现

## 2. 内聚与耦合

**这是架构质量最底层的两个度量。** SOLID 本质上是"如何提高内聚、降低耦合"的具体手段。

### 2.1 内聚（Cohesion）——模块内部元素的关联度

**越高越好。** 从低到高：

| 类型 | 说明 | 评价 |
|------|------|------|
| 偶然内聚 | 元素之间毫无关系，只是碰巧放一起 | ❌ 最差 |
| 逻辑内聚 | 按"逻辑相似"分组（如 `Utils` 类） | ❌ 差 |
| 时间内聚 | 同一时间执行（如 `init()` 里做一堆不相关的事） | ❌ 差 |
| 过程内聚 | 按执行顺序组织 | ⚠️ 一般 |
| 通信内聚 | 操作同一份数据 | ⚠️ 一般 |
| 顺序内聚 | 一个的输出是另一个的输入 | ✅ 好 |
| **功能内聚** | 所有元素共同完成**单一明确的功能** | ✅ 最好 |

### 2.2 耦合（Coupling）——模块之间的依赖程度

**越低越好。** 从高到低：

| 类型 | 说明 | 评价 |
|------|------|------|
| 内容耦合 | 一个模块直接改另一个的内部数据 | ❌ 最差 |
| 公共耦合 | 共享全局可变状态 | ❌ 差 |
| 外部耦合 | 依赖外部协议/格式/设备 | ⚠️ |
| 控制耦合 | 传"控制标志"决定对方行为 | ⚠️ 差 |
| 标记耦合 | 传整个对象但只用一部分 | ⚠️ 一般 |
| 数据耦合 | 只传需要的数据 | ✅ 好 |
| **消息耦合** | 通过消息/事件通信，无直接依赖 | ✅ 最好 |

### 2.3 架构层面的耦合度量

在系统级，"耦合"表现为：

| 耦合类型 | 例子 | 风险 |
|---------|------|------|
| **共享数据库** | 两个服务直连同一个库 | 最高——schema 变更互相牵连，无法独立部署 |
| **同步调用链** | A → B → C → D | 可用性乘积下降、延迟累加、级联故障 |
| **共享代码库** | 多个团队改同一个 monorepo 的同一模块 | 协调成本、发布耦合 |
| **共享基础设施** | 共用一个数据库实例/消息队列 | 故障域重叠 |
| **时间耦合** | 必须同时在线才能工作 | 部署耦合、无法独立升级 |
| **契约耦合** | 依赖对方的字段/格式/时序 | 变更传染 |

> **架构师的核心动作**：**找出并消除"最坏的耦合"**——通常是共享数据库和同步调用链。

### 2.4 内聚/耦合的实操判断

**问三个问题**：
1. 改这个功能，要动几个模块？（→ 耦合度）
2. 这个模块里的东西，是不是都在服务同一个目标？（→ 内聚度）
3. 如果要把这个模块单独拿出来复用/替换，需要带走多少别的东西？（→ 依赖面）

## 3. 边界与关注点分离

### 3.1 边界（Boundaries）

**边界是架构的第一性概念。** 架构的本质工作就是**画边界**。

边界的作用：
- **隔离变化**：一边变，另一边不受影响
- **定义契约**：跨边界只能通过明确的接口
- **分配所有权**：边界 = 团队的职责范围
- **限制影响面**：故障、性能问题、安全事件被限制在边界内

**边界的三层来源**：

| 来源 | 说明 | 例子 |
|------|------|------|
| **技术边界** | 按技术关注点分 | 表现层 / 领域层 / 持久层 |
| **业务边界** | 按业务能力分（更重要） | 订单 / 支付 / 库存 / 履约 |
| **组织边界** | 按团队职责分（康威定律） | 团队 A 的代码 / 团队 B 的代码 |

> ⚠️ **优先级**：业务边界 > 组织边界 > 技术边界。**按技术分层切服务是经典反模式**（会导致每次业务变更都要改所有服务）。

### 3.2 关注点分离（Separation of Concerns, SoC）

**每个模块只解决一类关注点。** 常见的关注点轴：

| 轴 | 分离出的关注点 |
|---|---------------|
| 业务逻辑 vs 技术细节 | 领域模型 vs 框架/ORM/HTTP |
| 读 vs 写 | 命令模型 vs 查询模型（CQRS） |
| 同步 vs 异步 | 请求响应 vs 事件流 |
| 策略 vs 机制 | 业务规则 vs 传输/存储机制 |
| 核心域 vs 支撑域 | 自研 vs 采购/复用 |

**判断方法**：**这两件事会不会因为不同的原因而变化？** 会 → 分离。不会 → 别分（YAGNI）。

### 3.3 深模块 vs 浅模块（Ousterhout）

来自《软件设计哲学》（John Ousterhout）——**判断抽象好坏的关键工具**：

| | 深模块 Deep Module | 浅模块 Shallow Module |
|---|-------------------|----------------------|
| 接口 | 简单 | 复杂 |
| 实现 | 复杂/丰富 | 简单 |
| 价值 | **高**（隐藏了复杂度） | **低**（没隐藏什么，还增加了层） |

**深模块 = 窄接口 + 厚实现**。例：Unix 文件 I/O —— 5 个系统调用（open/close/read/write/lseek），背后是几十种文件系统、缓存、权限、设备驱动。

**浅模块反模式**：
- 只是转发参数的 wrapper（`getX() { return this.x; }`）
- 一个类一个方法，方法只是调用另一个类
- "为了分层而分层"的空层

**Ousterhout 的核心观点**：**复杂度是软件设计的唯一敌人。** 好的设计 = 让复杂度尽可能被封装在少数深模块里。

### 3.4 信息隐藏 vs 抽象

| | 信息隐藏（Parnas） | 抽象（常见误用） |
|---|-------------------|-----------------|
| 定义 | 模块应隐藏**最可能变化的设计决策** | 从具体中提取共性 |
| 依据 | **变化轴**（什么会变） | **相似性**（什么看起来像） |
| 风险 | — | 按"看起来像"提取，一旦变化轴不同，抽象就崩 |

> **Parnas 1972 的洞见**：模块划分应该基于**信息隐藏**（隐藏易变的设计决策），而不是基于**流程步骤**。这比 SOLID 早了几十年，且更本质。

**实操**：划分模块时问——**"这个模块隐藏了什么可能变化的东西？"** 答不出来，说明这个模块没有存在的理由。

## 4. 简洁性（YAGNI, KISS, 深模块）

### 4.1 YAGNI（You Aren't Gonna Need It）

**不要为"将来可能需要"的功能做设计。**

**为什么**：
- 预测未来的准确率极低（大多数"将来需要"从未来过）
- 为假想需求做的抽象，会**增加当前所有变更的成本**
- 真的需要时，重构的成本通常**低于**提前抽象的累积成本

**YAGNI 的边界**（不是无脑简化）：
- ✅ 应该为**已知的、近期的**需求留出扩展点
- ✅ 应该为**单向门决策**（数据模型、公共 API）留有余地
- ❌ 不应该为"也许某天要做多租户"提前引入租户隔离抽象
- ❌ 不应该为"以后可能要换数据库"引入 Repository + UnitOfWork + DTO + Mapper 五层

### 4.2 KISS（Keep It Simple, Stupid）

**最简单的方案，通常是最好的方案。**

**复杂度的三个来源**（Ousterhout）：
1. **依赖**：模块之间的相互依赖
2. **模糊**：命名不清、职责不明、文档缺失
3. **不可见的复杂度**：看不出来但会咬人的问题（隐藏耦合、隐含时序）

**KISS 的实操**：
- 优先选**团队已经会用的**技术，而不是最新潮的
- 优先选**能删掉的**方案，而不是"更灵活"的方案
- 优先**一种**实现方式，而不是支持 N 种
- 能用配置解决的不要写代码，能写代码解决的不要上框架

### 4.3 简洁 vs 简单的区别

| | 简单 Simple | 简洁/简约 Minimal |
|---|------------|------------------|
| 定义 | 不含不必要的复杂度（**结构属性**） | 尽可能少的元素（**数量属性**） |
| 关系 | 简单通常意味着元素少且关系清晰 | 元素少不一定简单（可能关系缠绕） |

> **目标不是"少"，而是"没有不必要的复杂度"。**

## 5. 复杂度预算（Complexity Budget）

### 5.1 核心模型

**复杂度是一种有限资源。** 每个架构选择都在**支出**它，团队的交付能力是**偿还能力**。

```
复杂度预算 = 团队能持续承受的复杂度上限
支出项 = 服务数量 + 部署单元 + 技术栈数量 + 抽象层数 + 数据存储种类 + 异步链路
透支信号 = 交付变慢 / 故障变多 / 新人上手难 / 无人敢改
```

### 5.2 复杂度支出清单

引入以下每一项，都在**持续**支出复杂度（不是一次性的）：

| 引入 | 持续成本 |
|------|---------|
| 一个新的微服务 | 部署流水线、监控、日志、告警、契约维护、本地开发环境、跨服务调试 |
| 一个新数据存储 | 备份恢复、运维、驱动升级、一致性处理、团队学习成本 |
| 一个服务网格 | sidecar 资源开销、配置复杂度、排障难度 |
| 事件驱动链路 | 最终一致性处理、幂等、消息顺序、死信、可观测性 |
| 一层抽象 | 理解成本、调试穿透成本、样板代码 |
| 一个新语言/框架 | 招聘、培训、工具链、生态 |

### 5.3 复杂度预算的使用原则

1. **先花在驱动因素上**：只给 2–3 个关键质量属性花复杂度预算，其余从简。
2. **一次性成本 vs 持续成本要分开算**：微服务的初始搭建成本看起来不高，**持续运维成本才是大头**。
3. **认知负荷是硬上限**：团队"装不下"的架构，无论多先进都会失败（呼应团队拓扑）。
4. **做减法比做加法更需要勇气**：架构师的价值常在"阻止引入"，而不是"引入"。
5. **定期审计**：每个季度问一次"我们能不能删掉点什么？"

### 5.4 一个实用的复杂度检查问题清单

- 新加入的工程师，多久能独立提交第一个生产变更？（> 2 周 → 复杂度偏高）
- 本地能跑起完整系统吗？（不能 → 复杂度偏高）
- 一次需求变更平均涉及几个部署单元？（> 3 → 偏高）
- 团队里有几个人能解释清楚整体架构？（< 2 → 知识集中风险）
- 有多少个"没人敢动"的模块？
- 部署一次需要几步人工操作？（> 0 → 偏高）

## 常见误区

| 误区 | 纠正 |
|------|------|
| 把 SOLID 当法律，到处抽象 | SOLID 是启发式；过度抽象比不抽象更糟 |
| 一个类只做一件事 = SRP | SRP 是"一个变更理由"，不是"一个方法" |
| 按技术分层切服务 | 按业务能力/限界上下文切 |
| 用"看起来像"做抽象 | 按"变化轴"抽象（Parnas） |
| 浅模块堆层（为了分层而分层） | 深模块：窄接口 + 厚实现 |
| 为假想需求做设计 | YAGNI；真的需要时再重构 |
| 追求"最灵活"的方案 | 灵活 = 复杂度支出；优先选能删掉的 |
| 认为复杂度是一次性成本 | 大部分复杂度是**持续支出** |
| 只算技术成本，不算认知负荷 | 认知负荷是硬上限 |
