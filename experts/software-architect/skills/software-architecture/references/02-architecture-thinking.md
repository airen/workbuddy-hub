# 02 · 架构思维

> 本模块解决：**怎么做出可辩护的决策？怎么把它记录下来？怎么让架构约束可自动验证？怎么管理技术债和组织约束？**

## 1. 权衡分析（没有免费的午餐）

### 1.1 核心心智模型

**任何架构决策 = 一组属性之间的取舍。** 不存在"更好的架构"，只有"在给定约束下更合适的架构"。

架构师的核心技能不是知道多少模式，而是**在多个属性冲突时做出可辩护的排序**。

### 1.2 权衡分析的六步法

```
1. 明确驱动因素          → 哪些质量属性必须保住？优先级？
2. 列出备选方案（≥3）    → 含"什么都不做"基线
3. 选评价维度            → 从驱动因素中提取 3–6 个关键属性
4. 逐项打分（+ / 0 / −） → 定性或定量（延迟数字、成本估算）
5. 标出敏感点与取舍点    → 哪一处改动影响最大？哪两个属性此消彼长？
6. 判断可逆性并拍板      → 单向门慎重；双向门快试
```

**权衡矩阵示例**（单体 vs 模块化单体 vs 微服务）：

| 评价维度 | 分层单体 | 模块化单体 | 微服务 |
|---------|---------|-----------|--------|
| 交付速度（早期） | + | + | − |
| 独立部署 | − | 0 | + |
| 运维复杂度 | + | + | − |
| 团队自治（多团队） | − | 0 | + |
| 分布式事务/一致性 | + | + | − |
| 技术栈异构 | − | − | + |
| 本地开发体验 | + | + | − |
| 小团队（<10人）适配 | + | **+** | − |

→ 结论不是"微服务最好"，而是"**在当前团队规模和边界成熟度下，模块化单体是更优起点**"。

> 完整方法见 `decision-frameworks.md`。

### 1.3 敏感点与取舍点（ATAM 术语，值得记住）

| 术语 | 定义 | 为什么重要 |
|------|------|-----------|
| **敏感点 Sensitivity Point** | 某个属性对某个决策**高度敏感**（改一点，属性大幅变化） | 这里是设计的"承重点"，必须重点验证 |
| **取舍点 Tradeoff Point** | 一个决策**同时影响两个以上属性且方向相反** | 这是真正需要拍板的地方，也是风险最高处 |
| **风险 Risk** | 可能危及驱动因素的决策 | 需要缓解措施 |
| **非风险 Non-risk** | 已被验证安全的关键决策 | 可以放心 |
| **风险主题 Risk Theme** | 跨决策的系统性风险（如"团队缺乏分布式经验"） | 需要组织层面应对 |

**实操**：在评审设计时，逼自己为每个关键决策标注"它是敏感点还是取舍点？"——**答不上来的决策，说明还没想透。**

### 1.4 决策的可逆性：单向门 vs 双向门

这是**最高杠杆的思维工具**，能省下大量无谓的论证时间。

| | 单向门（One-way Door） | 双向门（Two-way Door） |
|---|----------------------|----------------------|
| 特征 | 难回退、成本高、影响面大 | 易回退、成本低、局部影响 |
| 例子 | 数据模型、数据库选型、服务边界、API 公共契约、云厂商锁定、领域模型 | UI 布局、内部实现、缓存策略、日志格式、模块内部结构 |
| 该怎么做 | **慎重论证、多方案对比、写 ADR、找反例** | **快速决定、快速试错、不过度评审** |
| 错误做法 | 草率决定（灾难） | 反复论证、开三次会（浪费） |

> **Jeff Bezos 的框架**：大多数决策是双向门，应该由**高判断力的个人或小团队快速做出**；只有单向门才需要充分讨论。
> **架构师最常见的浪费**：把双向门当单向门论证。**先分类，再决定投入多少论证成本。**

## 2. 架构决策记录（ADR）

### 2.1 什么是 ADR

ADR（Architecture Decision Record）是一份**轻量的、只增不改的**文档，记录**一个架构决策及其背景**。它是架构的"变更日志"。

**核心价值**：
- **可追溯**：半年后有人问"为什么当初这么设计"，有答案
- **可评审**：决策在写下来时才真正被想清楚
- **可交接**：新人通过 ADR 快速理解系统的"为什么"
- **防重蹈覆辙**：记录被否决的方案及原因，避免反复讨论

### 2.2 ADR 的粒度

**一个决策一份 ADR。** 不要写成"系统架构设计文档"，那会变成没人维护的大文档。

好的 ADR 标题：
- ✅ "采用 Outbox 模式保证订单事件与数据库写入的原子性"
- ✅ "订单服务按限界上下文拆分为订单/支付/履约三个服务"
- ❌ "订单系统架构设计"（太大，无法决策）

### 2.3 ADR 的生命周期

```
提议 (Proposed) → 接受 (Accepted) → [可能] 废弃 (Deprecated) / 被取代 (Superseded by ADR-XXX)
```

**只增不改**：改变决策时，**新写一份 ADR 并把旧的标记为 Superseded**，而不是修改旧文档。这样保留了决策演化的历史。

### 2.4 ADR 的核心内容（MADR 精简版）

1. **标题**：决策的简短陈述（含编号）
2. **状态**：Proposed / Accepted / Deprecated / Superseded
3. **背景（Context）**：什么情况下要决策？驱动因素是什么？
4. **决策（Decision）**：我们决定做什么
5. **备选方案（Alternatives）**：考虑过什么，为什么没选
6. **后果（Consequences）**：正面、负面、中性影响（**负面必写**）
7. **相关**：关联的 ADR、需求、文档

> 完整模板见 `templates/adr.md`；脚手架脚本见 `scripts/new-adr.sh`。

### 2.5 常见 ADR 反模式

| 反模式 | 问题 | 纠正 |
|--------|------|------|
| 只有决策，没有备选 | 无法判断是否想过替代方案 | 强制列 ≥2 个被否决的方案及原因 |
| 只有好处，没有代价 | 说明没想清楚 | **负面后果是必填项** |
| ADR 太粗（一份 = 一个系统） | 无法对应到具体决策 | 一个决策一份 |
| ADR 太细（一份 = 一次代码改动） | 噪音，没人看 | 只记录架构级决策 |
| 写完就锁进 Confluence | 无人知晓 | 与代码同仓（`docs/adr/`），评审时引用 |
| 从不更新状态 | 与实际不符，误导后人 | 决策变更时新增并标记取代关系 |

## 3. 适应度函数（Fitness Functions）

### 3.1 是什么

适应度函数是**对架构特征（质量属性）的自动化验证**。它把"架构应该怎样"从**文档里的约定**变成**可执行、会失败的检查**。

> 类比：演化生物学中的适应度函数衡量个体对环境的适应程度；架构适应度函数衡量**架构对当前需求的适应程度**。

**核心思想**：架构不应该"腐化"，而应该**持续被验证**。没有适应度函数的架构约束，会在半年内被违反。

### 3.2 分类

| 维度 | 类型 | 例子 |
|------|------|------|
| **触发时机** | 原子/持续（每次提交） | 单元测试、依赖规则检查 |
| | 定期（定时） | 每夜压测、月度容量报告 |
| | 按需 | 发布前性能回归 |
| **执行方式** | 自动化 | CI 中的 ArchUnit 依赖检查 |
| | 人工 | 架构评审清单 |
| **验证对象** | 结构 | 模块依赖方向、循环依赖、分层违规 |
| | 行为 | 延迟 SLO、吞吐、错误率 |
| | 运维 | 部署时长、回滚成功率 |

### 3.3 常见适应度函数示例

| 架构目标 | 适应度函数 |
|---------|-----------|
| 保持分层 | 用 ArchUnit / dependency-cruiser 断言"domain 层不得依赖 infrastructure 层" |
| 无循环依赖 | 依赖图分析，CI 中失败即阻断 |
| 服务边界不被穿透 | 断言服务间只通过公开 API 通信，禁止跨库直连 |
| 性能 SLO | 压测断言 P99 < 200ms，超阈值 CI 失败 |
| 依赖许可合规 | CI 扫描依赖许可证，禁止 GPL 进闭源产品 |
| 包体积上限 | 构建后断言主包 < 2MB |
| API 向后兼容 | 契约测试 / schema diff，破坏性变更阻断 |
| 可观测性覆盖 | 断言所有对外接口都打了 trace |
| 文档同步 | 断言新增服务必须在 C4 图中出现 |

### 3.4 怎么落地

1. **从最关键的质量属性出发**：不要一次上十几个，先给 2–3 个真正的驱动因素配适应度函数。
2. **优先放在 CI**：能自动失败才有约束力；只在文档里的规则等于没有。
3. **允许阈值与豁免**：老代码可以豁免，但要有**递减的豁免清单**和期限。
4. **定期回顾**：需求变了，适应度函数也要变。它本身也是一个需要维护的决策。

> 模板见 `templates/fitness-function.md`。

## 4. 技术债与演化压力

### 4.1 技术债的准确理解

**技术债不是"烂代码"，而是"为了短期收益而做出的、未来需要偿还的设计取舍"。**

| 类型 | 说明 | 例子 |
|------|------|------|
| **审慎的（Prudent）** | 明知有代价，为赶窗口主动借 | "先用单体上，验证市场后再拆" |
| **鲁莽的（Reckless）** | 不知道有代价就借 | 直接复制粘贴逻辑、跳过测试 |
| **有意的（Deliberate）** | 清楚记录并计划偿还 | ADR 里写明"这是临时方案，触发条件是 X" |
| **无意的（Inadvertent）** | 事后才发现 | "我们不知道这样会导致 N+1 查询" |

> **不是所有技术债都要还。** 有些债的成本（利息）低于偿还成本（本金），理性选择是**永远不还**——比如一段再也不会改的遗留代码。关键是**知道它的存在并量化利息**。

### 4.2 量化技术债的利息

技术债的"利息"表现为：

| 利息形式 | 度量方式 |
|---------|---------|
| 交付变慢 | 同类需求的历史耗时对比（加了新功能 vs 两年前） |
| 缺陷率上升 | 该模块的缺陷密度 vs 全系统平均 |
| 变更影响面扩大 | 改一处的平均波及文件数/服务数 |
| 认知负担 | 新人上手时间、代码复杂度指标 |
| 发布风险 | 该模块相关的回滚率、故障率 |
| 人才流失 | 没人愿意碰的模块（"代码考古"） |

**量化示例**：
> 「订单模块的变更前置时间从 2024 年的 3 天升到现在的 11 天，其中约 6 天花在理解历史逻辑和回归测试上。按每年 40 次变更计算，年利息约 240 人天。」

**这样的表述才能推动偿还决策**——而不是说"这段代码很烂，需要重构"。

### 4.3 演化压力（Evolutionary Pressure）

**演化压力 = 系统继续演化时遇到的阻力。** 它来自：

| 压力来源 | 表现 |
|---------|------|
| **耦合** | 改 A 必须改 B、C、D |
| **知识集中** | 只有一个人懂某模块（巴士系数 = 1） |
| **测试缺失** | 不敢改，改了不知道会不会坏 |
| **边界模糊** | 不知道该改哪里，改动散落各处 |
| **运维僵化** | 发布流程重、回滚难，导致不敢改 |
| **组织摩擦** | 改一处要协调三个团队 |

**架构师的目标不是"消灭技术债"，而是让系统保持"可演化"**——即：**变更成本不随系统年龄指数上升。**

### 4.4 偿还策略

| 策略 | 适用 |
|------|------|
| **童子军规则**（顺手改） | 小额、局部的债；低成本但见效慢 |
| **专门偿还冲刺** | 大额、集中的债；需要业务方买账 |
| **绞杀者模式** | 遗留系统整体替换 |
| **持续重构** | 日常工程纪律的一部分（推荐） |
| **战略性放弃** | 利息 < 本金的债，明确记录后不管 |

> 相关：绞杀者模式见 `09-evolution-and-production.md`。

## 5. 康威定律与团队拓扑

### 5.1 康威定律

> **"任何设计系统的组织，其产生的设计等同于组织之内、组织之间的沟通结构。"** —— Melvin Conway, 1968

**通俗版**：**系统的架构会镜像团队的沟通结构。**

推论：
- 如果三个团队共用一个代码库，代码库会长成一个纠缠的巨石
- 如果想让系统有清晰的边界，先让团队有清晰的边界（或反过来）
- **"逆康威操作"（Inverse Conway Maneuver）**：**主动调整团队结构，以获得你想要的架构**

**经典案例**：Amazon 的 "两个披萨团队" + 服务化 → 团队自治直接催生了微服务架构。

### 5.2 康威定律的实操含义

| 现象 | 架构师该做什么 |
|------|---------------|
| 一个服务被 5 个团队改 | 要么拆服务，要么合并团队 |
| 团队 A 和 B 频繁互相阻塞 | 边界划错了；重新按团队切分 |
| 想上微服务但只有一个团队 | **别上**。组织撑不起，会得到"分布式单体" |
| 团队按技术分层组织（前端组/后端组/DBA组） | 系统会长成分层巨石；考虑改为按业务能力组织 |
| 想引入新架构但组织不变 | 大概率失败；先谈组织 |

> **记住**：**架构方案若与组织现实冲突，输的总是架构方案。** 组织现实是约束，不是建议。

### 5.3 团队拓扑（Team Topologies）

一种**组织与架构协同设计**的框架，把团队分为四种类型：

| 团队类型 | 职责 | 例子 |
|---------|------|------|
| **流动对齐型 Stream-aligned** | 端到端负责一个业务流（主力） | 订单团队、支付团队 |
| **平台型 Platform** | 提供自助式内部平台，降低认知负担 | 云平台团队、CI/CD 团队 |
| **赋能型 Enabling** | 帮助流动对齐团队获得新能力 | 架构赋能团队、安全赋能团队 |
| **复杂子系统型 Complicated-subsystem** | 负责需要深度的专业子系统 | 推荐引擎团队、视频编码团队 |

**三种交互模式**：
- **协作（Collaboration）**：两个团队紧密合作一段时间（高带宽，成本高，临时）
- **服务（X-as-a-Service）**：一方提供服务，另一方自助消费（低带宽，可扩展）
- **促进（Facilitating）**：赋能团队帮助另一个团队成长（教学性质）

**核心原则**：**限制团队的认知负荷**。团队应该能"装下"自己负责的系统。如果装不下，说明边界该调整了。

> **对架构师的含义**：设计边界时，同时考虑**技术耦合**和**认知负荷**。一个技术上合理的边界，如果超出团队认知能力，仍然会失败。

## 常见误区

| 误区 | 纠正 |
|------|------|
| 只给一个方案就论证 | 至少三个备选，含"什么都不做" |
| 把双向门当单向门反复论证 | 先判可逆性，再决定论证成本 |
| ADR 只写好话 | 负面后果必写 |
| 架构约束只写在文档里 | 做成适应度函数放进 CI |
| 用"代码很烂"推动重构 | 量化利息（人天/缺陷率/前置时间） |
| 认为技术债必须全还 | 利息 < 本金的债理性放弃 |
| 忽视康威定律 | 架构与组织一起设计 |
| 只考虑技术耦合，忽略认知负荷 | 边界要"装得下" |
