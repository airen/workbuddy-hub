# 09 · 演化与生产环境

> 本模块解决：**架构怎么安全地变？怎么知道系统在发生什么？怎么定 SLO？怎么扛住故障？怎么守住安全底线？**

## 1. 演化式架构与绞杀者模式

### 1.1 演化式架构（Evolutionary Architecture）

**核心思想**：**架构应该支持"引导式、增量式的变化"，而不是一次性设计到位。**

三条支柱（Ford/Parsons/Kua）：

| 支柱 | 含义 |
|------|------|
| **增量变化（Incremental Change）** | 变化以小步、可回退的方式落地，而不是大爆炸重构 |
| **引导式变化（Guided Change）** | 变化被**适应度函数**引导（见 `02-architecture-thinking.md`） |
| **适合目的（Appropriate Coupling）** | 耦合不是越松越好，而是"匹配当前需求"——该松的地方松，该紧的地方紧 |

**核心隐喻**：**架构不是建筑，而是园艺。** 建筑建完就定型；系统需要持续修剪。

**架构量子（Architecture Quantum）**：一个可独立部署、且内部高内聚的单元。**量子内的耦合可以很紧，量子间必须解耦。** 架构师的工作是**定义量子的边界**。

### 1.2 绞杀者模式（Strangler Fig）

**渐进式替换遗留系统**——用新系统一点点"缠死"旧系统，而不是一次性重写。

```
阶段 1:  客户端 → 门面/路由 → 旧系统（全部流量）
阶段 2:  客户端 → 门面/路由 → ├─ 旧系统（大部分）
                              └─ 新系统（一个功能，如"新用户注册"）
阶段 3:  ...逐步迁移更多功能...
阶段 4:  客户端 → 门面/路由 → 新系统（全部流量）→ 旧系统下线
```

**关键要素**：

| 要素 | 说明 |
|------|------|
| **门面/路由层** | 拦截流量，按功能/用户/比例分流到新旧系统（可用 API 网关、反向代理、特性开关） |
| **功能切片** | 一次迁移一个**垂直功能**，而不是一个技术层 |
| **双写/数据同步** | 过渡期新旧系统共享数据（CDC 或双向同步）——**最棘手的部分** |
| **回退能力** | 任何一步都能切回旧系统（特性开关） |
| **验收标准** | 新功能通过什么标准才算迁移完成 |

**为什么优于"大爆炸重写"**：
- 重写项目 **70%+ 失败**（业界经验数据）
- 绞杀者**持续交付价值**，每一步都可上线
- 风险被切分成小份，可回退
- 团队持续获得反馈

**最难的三个问题**：
1. **数据拆分**：新旧系统共享数据库时，如何逐步剥离数据？
2. **跨系统事务**：迁移期间一个业务跨新旧系统，一致性怎么保证？
3. **功能对等性**：旧系统有大量"没文档的隐藏行为"，新系统容易漏掉

### 1.3 其他演化模式

| 模式 | 用途 |
|------|------|
| **分支抽象（Branch by Abstraction）** | 同一代码库内，用抽象层隔离新旧实现，逐步替换（适合单体内部） |
| **特性开关（Feature Toggle）** | 运行时控制功能开关，支持灰度、回退 |
| **并行运行（Parallel Run）** | 新旧实现同时跑，比对结果（验证正确性） |
| **扩展-收缩（Expand-Contract）** | 数据/契约的兼容演进（见 `08`） |
| **影子流量（Shadow Traffic）** | 复制生产流量到新系统验证，不影响用户 |

### 1.4 迁移的反模式

| 反模式 | 问题 |
|--------|------|
| **大爆炸重写** | 高风险、长时间无交付、需求漂移 |
| **无门面的直连迁移** | 无法灰度、无法回退 |
| **迁移技术层**（如"先把所有 DAO 换掉"） | 无法验证业务价值 |
| **没有回退开关** | 出问题只能硬扛 |
| **一次性切全量** | 赌上整个系统 |
| **不清理旧系统** | 两套系统永久共存，复杂度翻倍 |

## 2. 可观测性（Observability）

### 2.1 可观测性 vs 监控

| | 监控 Monitoring | 可观测性 Observability |
|---|----------------|---------------------|
| 问题 | "已知的已知"——预定义的指标 | "未知的未知"——任意问题都能被回答 |
| 方式 | 预设仪表盘与告警 | 从外部输出推断内部状态 |
| 数据 | 指标为主 | 日志 + 指标 + 追踪 + 剖析 |

**可观测性三支柱**：

| 支柱 | 回答什么问题 | 特点 |
|------|-------------|------|
| **日志 Logs** | "发生了什么具体事件？" | 离散事件，细节丰富，成本高 |
| **指标 Metrics** | "系统整体健康吗？趋势如何？" | 聚合数值，成本低，适合告警 |
| **追踪 Traces** | "这个请求经过了哪些服务？哪一跳慢？" | 跨服务因果链，分布式排障的核心 |

（**第四支柱**：**剖析 Profiling**——"CPU/内存花在哪里？"）

### 2.2 日志

| 实践 | 说明 |
|------|------|
| **结构化日志** | JSON 格式，字段化（`traceId`、`userId`、`service`），便于查询 |
| **关联 ID** | 每个请求带 `traceId`/`correlationId`，贯穿所有服务 |
| **分级** | DEBUG/INFO/WARN/ERROR，生产环境不用 DEBUG |
| **不要记录敏感数据** | 密码、token、身份证、银行卡 → 脱敏 |
| **成本控制** | 日志量可能爆炸；采样、分级保留、冷热分层 |

**反模式**：`console.log("here")`、无结构的字符串拼接、无关联 ID。

### 2.3 指标

**四大黄金信号（Google SRE）**：

| 信号 | 说明 |
|------|------|
| **延迟 Latency** | 请求耗时（区分成功与失败的延迟！） |
| **流量 Traffic** | 请求量/QPS |
| **错误 Errors** | 错误率 |
| **饱和度 Saturation** | 资源使用率（CPU、内存、队列深度） |

**两种常用指标框架**：

| 框架 | 组成 | 适合 |
|------|------|------|
| **RED** | Rate、Errors、Duration | **面向请求的服务** |
| **USE** | Utilization、Saturation、Errors | **面向资源**（CPU、磁盘、网络） |

**延迟的陷阱**：**平均值会骗人。** 必须看**分位数**（P50/P95/P99）。平均 100ms 可能掩盖了 1% 的请求耗时 10s。

### 2.4 分布式追踪

| 概念 | 说明 |
|------|------|
| **Trace** | 一个请求的完整调用链 |
| **Span** | 链中的一段（一次服务调用/DB 查询） |
| **上下文传播（Context Propagation）** | `traceId`/`spanId` 通过 HTTP header、消息头传递 |

**标准**：**OpenTelemetry（OTel）** —— 厂商中立的统一标准（日志+指标+追踪），**新项目首选**。

**采样策略**：全量采样成本高 → 用**尾部采样**（只保留慢请求/错误请求）或按比例采样。

### 2.5 可观测性的落地建议

- **从第一天就埋点**：事后补追踪几乎不可能
- **统一标准**：OTel，避免厂商锁定
- **关联一切**：日志、指标、追踪用同一个 `traceId` 打通
- **告警面向症状，而非原因**：告警"下单成功率 < 99%"，而不是"CPU > 80%"
- **减少告警噪音**：告警疲劳会让真告警被忽略

## 3. SLIs / SLOs / 错误预算

### 3.1 定义

| 术语 | 含义 |
|------|------|
| **SLI（Service Level Indicator）** | **指标**：实际测量的服务质量（如"成功请求比例"） |
| **SLO（Service Level Objective）** | **目标**：SLI 的目标值（如"成功率达 99.9%"） |
| **SLA（Service Level Agreement）** | **合同**：对外承诺，违约有赔偿。**SLA 应严于 SLO** |
| **错误预算（Error Budget）** | `1 - SLO`：允许的失败额度（99.9% → 0.1% 预算） |

### 3.2 怎么选 SLI

**从用户视角选**，不是从技术视角。

| 服务类型 | 好的 SLI |
|---------|---------|
| 请求响应型 | 可用性（成功请求比例）、延迟（P99 < X ms） |
| 数据处理 | 吞吐（处理速率）、新鲜度（数据延迟）、正确性 |
| 存储 | 可用性、持久性（数据不丢）、延迟 |
| 批处理 | 完成时间、成功率 |

**关键**：**SLI 必须是"用户能感知的"**。"CPU 使用率"不是 SLI，"下单成功率"才是。

### 3.3 怎么定 SLO

| 原则 | 说明 |
|------|------|
| **不要定 100%** | 100% 不可达；追求 100% 会摧毁交付速度 |
| **从当前水平起步** | 先测实际 SLI，再定略高的目标 |
| **按用户旅程定** | 关键路径（下单、支付）SLO 高；次要功能可低 |
| **越严的 SLO 成本越高** | 99.9% → 99.99% 的成本可能翻倍 |
| **定期回顾** | 业务变了，SLO 也要变 |

**可用性换算（记下来）**：

| SLO | 年停机 | 月停机 |
|-----|--------|--------|
| 99% | 3.65 天 | 7.2 小时 |
| 99.9% | 8.76 小时 | 43.8 分钟 |
| 99.95% | 4.38 小时 | 21.9 分钟 |
| 99.99% | 52.6 分钟 | 4.4 分钟 |
| 99.999% | 5.26 分钟 | 26 秒 |

### 3.4 错误预算的用法（这是 SLO 最有价值的部分）

**错误预算把"可靠性"和"交付速度"变成一个可管理的权衡。**

| 预算状态 | 行动 |
|---------|------|
| **预算充足** | **加速发布**新功能（冒风险是被允许的） |
| **预算耗尽** | **冻结功能发布**，全部精力投入可靠性改进 |
| **预算长期充足** | SLO 太松，可以提高（或降低成本） |
| **预算持续耗尽** | SLO 太紧或系统真有质量问题 |

**这是打破"开发 vs 运维"对立的关键机制**：用**同一个数字**衡量双方。

### 3.5 反模式

| 反模式 | 问题 |
|--------|------|
| SLO = 100% | 不可达，导致无意义的告警与疲劳 |
| 用技术指标当 SLI | 用户感知不到 |
| SLO 与业务无关 | 没人关心 |
| 有 SLO 但不执行错误预算 | SLO 沦为装饰 |
| 告警阈值 = SLO 阈值 | 应该在**消耗错误预算过快**时告警（如 2% 预算在 1 小时内耗尽） |

**多窗口多燃烧率告警（SRE 推荐）**：同时看"短窗口高燃烧率"（快速故障）和"长窗口低燃烧率"（慢性问题）。

## 4. 弹性（Resilience）

**弹性 = 系统在部分故障时仍能提供服务的能力。** 目标不是"不故障"，而是**故障时优雅降级**。

### 4.1 四大弹性模式

| 模式 | 作用 | 关键参数 |
|------|------|---------|
| **超时 Timeout** | 防止无限等待耗尽资源 | 必须小于上游超时；逐跳递减 |
| **重试 Retry** | 处理瞬时故障 | 指数退避 + 抖动 + 次数上限；**仅对可重试错误** |
| **熔断 Circuit Breaker** | 下游持续失败时快速失败，避免雪崩 | 阈值、半开探测、恢复时间 |
| **隔板 Bulkhead** | 隔离资源池，防止一处故障拖垮全局 | 每依赖独立线程池/连接池 |
| **限流 Rate Limiting** | 保护系统不过载 | 令牌桶/漏桶；按用户/租户/接口 |
| **降级 Fallback** | 主逻辑失败时返回兜底结果 | 缓存旧数据、默认值、精简功能 |

### 4.2 熔断器（Circuit Breaker）状态机

```
CLOSED（正常）──失败率超阈值──→ OPEN（快速失败）
   ↑                                │
   └──探测成功── HALF-OPEN（试探）←──超时后
```

| 状态 | 行为 |
|------|------|
| **CLOSED** | 正常放行，统计失败率 |
| **OPEN** | 直接返回失败，不调用下游（保护下游 + 快速失败） |
| **HALF-OPEN** | 放行少量请求探测，成功则回 CLOSED，失败则回 OPEN |

### 4.3 雪崩（Cascading Failure）的成因与对策

| 成因 | 对策 |
|------|------|
| 无超时 → 线程耗尽 | 全面设置超时 |
| 重试风暴 → 流量放大 | 退避 + 抖动 + 重试预算 |
| 单点过载 → 拖垮全局 | 限流 + 隔板 |
| 同步深链 → 一跳挂全链挂 | 异步化、降级、缓存 |
| 慢依赖 → 连接池耗尽 | 熔断 + 独立连接池 |
| 缓存击穿 → 全部打到 DB | 互斥锁/单飞（singleflight）、预热 |

### 4.4 高可用的架构手段

| 手段 | 说明 | 效果 |
|------|------|------|
| **冗余（Redundancy）** | 多实例、多副本 | 消除单点 |
| **无状态化** | 服务不保存会话状态 | 可任意扩缩容、易恢复 |
| **故障隔离（舱壁）** | 分区部署、独立资源池 | 限制爆炸半径 |
| **优雅降级** | 关非核心功能保核心 | 保营收路径 |
| **限流与排队** | 过载时排队而非崩溃 | 保护系统 |
| **健康检查 + 自动摘除** | 快速剔除坏实例 | 缩短故障窗口 |
| **多活/双活** | 多机房同时服务 | 机房级容灾 |
| **混沌工程** | 主动注入故障验证 | 提前发现脆弱点 |

> **"为失败而设计"**：**假设依赖一定会挂、网络一定会断、磁盘一定会满。** 问自己"如果 X 挂了会怎样？"

### 4.5 混沌工程（Chaos Engineering）

**主动在生产/预发注入故障，验证系统的弹性。**

| 实验类型 | 例子 |
|---------|------|
| 杀进程/节点 | 随机杀 Pod |
| 网络故障 | 注入延迟、丢包、分区 |
| 依赖故障 | 让下游服务返回错误 |
| 资源耗尽 | 占满 CPU/内存/磁盘 |
| 时钟偏移 | 制造时间不一致 |

**原则**：从预发环境开始、有明确的假设与爆炸半径控制、有停止开关、**不要在没有可观测性的情况下做**。

## 5. 安全、最小权限与密钥管理

### 5.1 安全架构的核心理念

| 理念 | 说明 |
|------|------|
| **零信任（Zero Trust）** | 不信任网络位置；**每次都验证**（内网也不信） |
| **最小权限（Least Privilege）** | 只给完成任务所需的最小权限 |
| **纵深防御（Defense in Depth）** | 多层防护，不依赖单点 |
| **默认拒绝（Default Deny）** | 未明确允许的一律拒绝 |
| **假设已被入侵（Assume Breach）** | 设计时假设攻击者已在内部 |

### 5.2 认证与授权

| | 认证 Authentication | 授权 Authorization |
|---|-------------------|-------------------|
| 问题 | 你是谁？ | 你能做什么？ |
| 手段 | 密码、MFA、OAuth/OIDC、mTLS、生物识别 | RBAC、ABAC、ReBAC、策略引擎 |

**实践要点**：
- **OIDC/OAuth2** 用于用户认证与授权委托；**mTLS** 用于服务间
- **JWT 的坑**：无法撤销（需短过期 + refresh token + 黑名单）、算法混淆攻击、不要在 JWT 里放敏感数据
- **服务间**：用 mTLS 或短期凭证，不要硬编码长期密钥
- **授权决策集中化**：用策略引擎（OPA/Cedar）而非散落在各服务

### 5.3 密钥管理（Secrets Management）

| 反模式 | 问题 |
|--------|------|
| 密钥硬编码在代码/配置 | 进版本库，泄漏无法收回 |
| 密钥在环境变量里明文 | 可能被日志/进程列表泄漏 |
| 长期不变的静态密钥 | 泄漏后影响永久 |
| 所有服务共用一个密钥 | 无法轮换、无法追踪、爆炸半径大 |

**正确做法**：

| 做法 | 说明 |
|------|------|
| **专用密钥管理服务** | Vault、AWS Secrets Manager、KMS、K8s Secrets（配合加密） |
| **动态短期凭证** | 按需签发、自动过期（如 Vault 动态数据库凭证） |
| **密钥轮换（Rotation）** | 定期自动轮换，且**演练过轮换流程** |
| **按服务/环境隔离** | 每个服务独立密钥 |
| **审计访问** | 谁在什么时候取了哪个密钥 |
| **绝不进版本库** | 用 `.gitignore` + pre-commit 扫描 + 密钥泄漏检测 |

### 5.4 数据安全

| 环节 | 手段 |
|------|------|
| **传输** | TLS 全链路（含内网）、mTLS |
| **存储** | 静态加密（磁盘级 + 字段级）、密钥与数据分离 |
| **敏感字段** | 字段级加密、令牌化（tokenization）、脱敏 |
| **日志** | 脱敏，绝不记录密码/token/身份证/银行卡 |
| **备份** | 加密 + 访问控制 + 恢复演练 |
| **删除** | 支持"被遗忘权"（数据主体删除请求） |

### 5.5 常见安全风险（OWASP 视角）

| 风险 | 架构层面的应对 |
|------|--------------|
| 注入（SQL/命令） | 参数化查询、输入校验、最小权限 DB 账号 |
| 认证失效 | MFA、会话管理、凭证填充防护 |
| 敏感数据暴露 | 加密、脱敏、最小暴露 |
| 访问控制失效 | 服务端强制校验（不信任客户端）、默认拒绝 |
| 安全配置错误 | 基础设施即代码、基线加固、自动化扫描 |
| 供应链风险 | 依赖扫描（SCA）、SBOM、锁定版本、审许可证 |
| 日志监控不足 | 审计日志、异常检测、告警 |

### 5.6 安全左移（Shift Left）

**在生命周期早期就考虑安全**：
- 设计阶段：威胁建模（STRIDE）
- 编码阶段：SAST、密钥扫描、依赖扫描
- 构建阶段：容器镜像扫描、SBOM
- 部署阶段：IaC 扫描、基线检查
- 运行阶段：DAST、运行时防护、审计

> **架构师的职责**：**把安全设计进架构**（边界、最小权限、加密、审计），而不是靠上线前的一次渗透测试。

## 6. 生产就绪检查清单

- [ ] 有明确的 **SLI/SLO**，且有**错误预算**机制
- [ ] **三支柱可观测性**：结构化日志 + 指标 + 分布式追踪，用 `traceId` 打通
- [ ] 关键路径有**告警**，且告警面向**症状**
- [ ] 所有网络调用有**超时**，且逐跳递减
- [ ] 重试有**退避 + 抖动 + 上限**
- [ ] 关键依赖有**熔断**与**降级**
- [ ] 有**限流**保护（按用户/租户/接口）
- [ ] 关键服务**无状态**，可任意扩缩容
- [ ] 有**优雅停机**（处理完在途请求）
- [ ] 有**健康检查**与自动摘除
- [ ] **备份 + 恢复演练**做过
- [ ] 有**回滚**方案（且演练过）
- [ ] **密钥**在专用管理服务，有轮换
- [ ] 有**威胁建模**与依赖扫描
- [ ] 有**混沌工程**演练（至少预发）
- [ ] 有**运行手册（Runbook）**：常见故障怎么处理

## 常见误区

| 误区 | 纠正 |
|------|------|
| 大爆炸重写遗留系统 | 绞杀者模式渐进替换 |
| 迁移按技术层推进 | 按垂直功能切片 |
| 没有回退开关 | 每步都要能切回 |
| 事后补可观测性 | 从第一天就埋点 |
| 看平均延迟 | 必须看 P95/P99 |
| SLO = 100% | 不可达；且会摧毁交付速度 |
| 用 CPU 使用率当 SLI | SLI 必须是用户可感知的 |
| 有 SLO 不用错误预算 | SLO 沦为装饰 |
| 告警面向原因（CPU 高） | 告警面向症状（成功率低） |
| 无超时/无退避的重试 | 雪崩主因 |
| 密钥硬编码/长期不变 | 用密钥管理服务 + 动态短期凭证 |
| 只靠上线前渗透测试 | 安全左移，设计进架构 |
