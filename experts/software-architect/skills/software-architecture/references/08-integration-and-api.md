# 08 · 集成与 API

> 本模块解决：**服务之间怎么说话？同步还是异步？API 怎么设计才不烂？流程该谁编排？**

## 1. 同步 vs 异步

### 1.1 本质区别

| | 同步（请求-响应） | 异步（消息/事件） |
|---|-----------------|-----------------|
| 耦合 | 时间耦合（双方必须在线） | 时间解耦（可离线） |
| 延迟 | 端到端 = 各跳之和 | 调用方立即返回，处理延迟不确定 |
| 一致性 | 天然强一致（同一调用链） | 最终一致 |
| 错误处理 | 立即知道成功/失败 | 需要补偿/重试/死信 |
| 可用性 | 乘积下降（A 依赖 B，B 挂 A 也挂） | 可降级（消息堆积，恢复后处理） |
| 调试 | 相对简单（调用栈完整） | 困难（需要追踪） |
| 扩展 | 需要协调扩缩容 | 天然削峰、独立消费 |

**关键公式（同步链路的可用性衰减）**：

```
3 个服务各 99.9% 可用 → 串行调用链可用性 = 0.999³ ≈ 99.7%
→ 年停机从 8.76h 变成 26.3h
```

> **架构含义**：**每增加一跳同步调用，整体可用性就下降一次。** 这就是为什么深调用链是危险的。

### 1.2 选择判据

| 问题 | 同步 | 异步 |
|------|------|------|
| 调用方需要立即得到结果吗？ | ✅ | ❌ |
| 需要强一致吗？ | ✅ | ❌ |
| 下游挂了，上游能继续工作吗？ | ❌ | ✅ |
| 有多个消费者吗？ | ❌ | ✅ |
| 需要削峰/缓冲吗？ | ❌ | ✅ |
| 流程跨越较长时间（分钟/小时/天）吗？ | ❌ | ✅ |
| 团队能处理最终一致的复杂度吗？ | — | 需要 ✅ |

**混合模式**（常见且推荐）：
- **同步查询 + 异步命令**：读用同步（要结果），写用异步（可排队）
- **同步发起 + 异步回调**：发起时同步确认受理，结果通过回调/轮询/事件通知

### 1.3 REST vs gRPC vs GraphQL

| | REST | gRPC | GraphQL |
|---|------|------|---------|
| 协议 | HTTP/1.1 或 2 | HTTP/2 | HTTP/1.1 或 2 |
| 格式 | JSON（文本） | Protobuf（二进制） | JSON |
| 契约 | OpenAPI（可选） | .proto（强制） | SDL schema |
| 性能 | 中 | **高**（二进制、多路复用、流） | 中（可能 N+1） |
| 浏览器友好 | ✅ | ⚠️ 需 grpc-web | ✅ |
| 流式 | SSE/WebSocket 补充 | **原生双向流** | Subscription |
| 适合 | 对外 API、简单 CRUD | **内部服务间**、高性能、强类型 | 客户端灵活查询、聚合层 |

**实操建议**：
- **对外 API 用 REST**（生态成熟、易调试、缓存友好）
- **内部高性能服务间用 gRPC**（强类型契约、二进制效率、流式）
- **GraphQL 用于 BFF/聚合层**（客户端需要灵活组合数据时），但要防 N+1 和查询复杂度攻击
- **不要为了"现代"而全面上 GraphQL**——它把复杂度从服务端移到了客户端和运维

## 2. 队列、发布订阅与事件流

### 2.1 三种消息模型

| 模型 | 语义 | 消费者 | 典型产品 | 适合 |
|------|------|--------|---------|------|
| **点对点队列 Queue** | 一条消息被**一个**消费者处理 | 竞争消费 | RabbitMQ、SQS | 任务分发、工作队列 |
| **发布订阅 Pub/Sub** | 一条消息被**多个**订阅者各自收到 | 每个订阅者一份 | Redis Pub/Sub、SNS | 事件广播 |
| **事件流 Event Stream** | 持久化的**追加日志**，可回放、可多消费组 | 消费组 + 位点 | Kafka、Pulsar、Kinesis | 事件溯源、CDC、流处理 |

### 2.2 关键区别：消息队列 vs 事件流

| | 消息队列 | 事件流（Kafka 类） |
|---|---------|------------------|
| 消息保留 | 消费后删除 | **保留一段时间/永久** |
| 回放 | 不支持 | **支持（重置位点）** |
| 消费者 | 消费即消失 | 多消费组各自独立读 |
| 顺序 | 队列内（有限） | **分区内严格有序** |
| 定位 | 任务分发 | 事件骨干 / 数据管道 |

**选型判据**：
- 需要**任务分发 + 复杂路由**（死信、延迟队列、优先级） → RabbitMQ
- 需要**事件回放 + 多消费者 + 高吞吐** → Kafka
- 云托管简单队列 → SQS / 云厂商 MQ

### 2.3 消息系统的必知问题

| 问题 | 说明 | 应对 |
|------|------|------|
| **顺序性** | 全局有序几乎不可能；Kafka 只保证分区内有序 | 需要有序的用同一分区键；或设计成无序容忍 |
| **重复投递** | 至少一次是常态 | 消费端幂等（见 `06`、`07`） |
| **消息积压** | 消费慢于生产 → 堆积 | 扩容消费者、批量消费、限流生产、监控 lag |
| **死信（DLQ）** | 反复失败的消息 | 转入死信队列 + 告警 + 人工处理 |
| **消息过大** | 超过 broker 限制 | 存对象存储，消息只传引用（Claim Check 模式） |
| **毒丸消息（Poison Pill）** | 永远处理失败的消息 | 重试 N 次后进 DLQ |
| **事务性** | 生产/消费与业务写入的原子性 | Outbox（生产侧）/ 幂等（消费侧） |

### 2.4 消息投递语义与消费模式

| 模式 | 说明 |
|------|------|
| **至少一次** | 最常用；靠幂等消费处理重复 |
| **至多一次** | 可能丢，不重复 |
| **消费组（Consumer Group）** | 组内竞争消费，组间广播（Kafka） |
| **位点提交（Offset Commit）** | 先处理再提交（至少一次）；先提交再处理（至多一次） |

## 3. API 设计、契约与版本控制

### 3.1 API 设计原则

| 原则 | 说明 |
|------|------|
| **契约优先（Contract-First）** | 先定 OpenAPI/proto，再实现；前后端可并行 |
| **资源导向（REST）** | 用名词表示资源，用 HTTP 方法表示动作 |
| **幂等性明确** | GET/PUT/DELETE 幂等；POST 不幂等（除非用幂等键） |
| **错误结构化** | 统一错误格式（code、message、details、traceId） |
| **分页一致** | 统一分页方式（cursor 优于 offset，深分页友好） |
| **避免过度获取** | 不返回无用字段；大列表用分页 |
| **Hyrum 定律** | **任何可观察行为都会被依赖**——错误消息文本、字段顺序、时间格式都会被依赖 |

**Hyrum 定律的含义**：**你暴露的每一个可观察行为都是事实契约。** 所以要**刻意控制暴露面**，并且**在变更时假设有人在依赖它**。

### 3.2 契约管理

| 手段 | 说明 |
|------|------|
| **OpenAPI / Protobuf / GraphQL SDL** | 机器可读的契约 |
| **契约测试（消费者驱动）** | Pact 等：确保提供者变更不破坏消费者 |
| **Schema Registry** | 消息格式的集中管理与兼容性检查（Kafka + Avro/Protobuf） |
| **契约即代码，进版本库** | 与实现一起评审、一起演进 |

### 3.3 版本控制策略

| 策略 | 说明 | 适用 |
|------|------|------|
| **URI 版本**（`/v1/orders`） | 直观、易路由 | 对外公共 API |
| **Header 版本**（`Accept: application/vnd.x.v2+json`） | URL 干净 | 内部/成熟 API |
| **Query 参数**（`?version=2`） | 简单 | 临时/内部 |
| **无版本 + 向后兼容演进** | 只做兼容性变更 | **内部服务推荐** |

**兼容性变更（安全）**：
- 新增可选字段
- 新增端点
- 放宽校验
- 新增枚举值（**注意**：消费者要能容忍未知枚举值）

**破坏性变更（危险，需版本化或迁移）**：
- 删除/重命名字段
- 改字段类型/语义
- 收紧校验
- 改默认值
- 改错误码

**演进策略（推荐）**：
1. **扩张-收缩（Expand-Contract）**：先加新字段（双方都支持）→ 迁移 → 再删旧字段
2. **并行运行（Parallel Run）**：新旧版本同时在线，灰度迁移
3. **弃用周期（Deprecation）**：公告 → 双写/双读 → 监控使用量 → 下线

> **内部服务尽量不做版本号**，而是**只做向后兼容的增量演进 + 扩张收缩**。版本号会迅速碎片化。

### 3.4 图查询语言与 BFF

| 模式 | 说明 |
|------|------|
| **BFF（Backend For Frontend）** | 为每种前端（Web/iOS/Android）提供一个聚合层，避免前端多次调用 |
| **API 网关** | 统一入口（见 §5） |
| **聚合服务** | 把多个后端调用合成一个响应 |

## 4. 编排（Choreography）vs 协调（Orchestration）

### 4.1 定义

| | 编排 Choreography | 协调 Orchestration |
|---|------------------|-------------------|
| 谁控制流程 | **无中心**：各服务监听事件，自发响应 | **有中心**：协调器（Orchestrator）指挥各服务 |
| 类比 | 舞蹈（各自跟着音乐跳） | 乐队指挥（指挥统一调度） |
| 耦合 | 松（服务间不知道彼此） | 中（都依赖协调器） |
| 可见性 | 流程分散，**难追踪** | 流程集中，**一目了然** |
| 修改流程 | 要改多个服务 | 只改协调器 |
| 单点风险 | 无 | 协调器（需高可用） |
| 适合 | 简单流程、事件广播、松耦合 | **复杂流程**、需要状态可视、需要补偿 |

### 4.2 选择建议

| 场景 | 推荐 |
|------|------|
| 2–3 步的简单流程 | 编排（Choreography） |
| 多步骤、有分支、需补偿的流程 | **协调（Orchestration）**（如 Saga 协调器、Temporal、Camunda） |
| 事件广播（多个无关消费者） | 编排 |
| 需要人工介入/长时间运行 | 协调（工作流引擎） |

**关键洞察**：**编排会随着流程复杂度增长而失控。** 一个 5 步的编排式流程，很难回答"现在走到哪了"。**复杂流程用协调器 + 显式状态机。**

> ⚠️ **反模式**：用编排（Choreography）实现复杂业务流程，结果事件满天飞、没人能说清完整流程（"事件地狱"）。

### 4.3 工作流引擎

长时间运行、需要状态持久化、需要人工任务、需要重试的流程，考虑专门的工作流引擎：

| 引擎 | 特点 |
|------|------|
| **Temporal** | 代码即工作流（写普通代码），状态持久化，重试内建 |
| **Camunda / Zeebe** | BPMN 可视化建模 |
| **AWS Step Functions** | 云原生状态机 |
| **Cadence** | Temporal 的前身 |

**收益**：把"分布式流程的复杂度"从业务代码里剥离出来，交给引擎。**代价**：引入一个重组件（复杂度预算）。

## 5. 网关、服务网格与服务发现

### 5.1 API 网关（API Gateway）

**所有外部流量的统一入口。**

| 职责 | 说明 |
|------|------|
| 路由 | 按路径/域名转发到后端服务 |
| 认证鉴权 | 统一 JWT/OAuth 校验 |
| 限流熔断 | 保护后端 |
| 协议转换 | 外部 REST → 内部 gRPC |
| 聚合 | 合并多个后端调用（BFF 变体） |
| 可观测 | 统一日志、指标、追踪入口 |

**⚠️ 反模式**：
- **把业务逻辑放进网关** → 网关变成"上帝服务"，成为瓶颈和发布耦合点
- **网关成为单点** → 必须集群化
- **网关层数太多** → 网关 → 网关 → 网关，延迟累加

### 5.2 服务发现（Service Discovery）

**服务实例动态变化时，调用方如何找到它们？**

| 模式 | 说明 | 例子 |
|------|------|------|
| **客户端发现** | 客户端查注册中心，自己选实例 | Eureka + Ribbon、Consul |
| **服务端发现** | 客户端调负载均衡器，由它转发 | K8s Service、AWS ALB |
| **DNS 发现** | 用 DNS 解析（SRV 记录） | K8s Headless Service |
| **服务网格** | Sidecar 代理处理 | Istio、Linkerd |

**K8s 环境**：**Service + DNS 已经解决了大部分服务发现问题**，通常不需要额外引入 Eureka/Consul。

### 5.3 服务网格（Service Mesh）

**把服务间通信的横切关注点（mTLS、重试、熔断、追踪、流量切分）下沉到基础设施层（Sidecar 代理）。**

| 收益 | 代价 |
|------|------|
| 应用代码不含通信逻辑 | **每跳多一次代理**（延迟 + 资源开销） |
| 统一 mTLS、零信任 | 配置复杂度、学习曲线 |
| 细粒度流量控制（金丝雀、镜像） | 排障更难（多一层） |
| 统一遥测 | 运维负担（控制平面） |

**引入判据**：
- ✅ 服务数量多（> 20–30）、多语言、需要统一 mTLS 与流量治理
- ❌ 服务少、单语言、团队小 → **用语言级库（如 Resilience4j、Polly）就够了，别上网格**

> **服务网格是复杂度预算的重大支出。** 用 K8s + 一个库能解决的，不要上 Istio。

### 5.4 集成方式选型速查

| 需求 | 建议 |
|------|------|
| 对外简单 API | REST + API 网关 |
| 内部高性能调用 | gRPC |
| 客户端灵活取数 | GraphQL（BFF 层） |
| 任务分发、复杂路由 | RabbitMQ |
| 事件骨干、回放、高吞吐 | Kafka |
| 复杂长流程 | 工作流引擎（Temporal 等） |
| 服务发现 | K8s Service / DNS |
| 统一 mTLS 与流量治理 | 服务网格（服务多时） |

## 常见误区

| 误区 | 纠正 |
|------|------|
| 深同步调用链 | 可用性乘积下降；用异步或聚合 |
| 认为微服务更快 | 把函数调用换成了网络调用 |
| 全局有序 | 几乎不可行；用分区键保证局部有序 |
| 忽略消息重复 | 至少一次是常态；消费端必须幂等 |
| 无 DLQ | 毒丸消息会永久阻塞 |
| 网关里放业务逻辑 | 网关会变成上帝服务 |
| 内部服务频繁升版本号 | 用扩张收缩做兼容演进 |
| 用编排实现复杂流程 | 事件地狱；复杂流程用协调器 |
| 团队小就上服务网格 | 用语言级库就够；网格是重资产 |
| 忽略 Hyrum 定律 | 任何可观察行为都会被依赖 |
