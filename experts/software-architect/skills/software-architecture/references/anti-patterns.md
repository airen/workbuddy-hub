# 架构反模式速查

> **用途**：审查一份已有设计时，逐条对照。每条给出"症状 → 为什么坏 → 怎么修"。
> 反模式不是"绝对禁止"，而是"默认危险，除非有明确理由"。

## A. 结构类

### A1. 大泥球（Big Ball of Mud）
- **症状**：模块间随意互相引用；没有清晰边界；"改一处崩三处"；新人无法理解
- **为什么坏**：耦合无处不在，任何变更成本都极高；无法独立测试/部署
- **怎么修**：先识别核心域（DDD 战略）→ 用绞杀者模式逐步抽出边界 → 用适应度函数守护（禁止跨模块 import）

### A2. 分布式单体（Distributed Monolith）
- **症状**：服务拆开了，但必须**一起部署**才能工作；改一个字段要同步改多个服务；服务间直连数据库
- **为什么坏**：拿到了微服务的全部复杂度，却没有拿到任何独立性
- **怎么修**：要么**合并回去**（诚实的单体），要么**真正解耦**（独立数据、独立部署、契约稳定）

### A3. 按技术层切服务
- **症状**：前端服务 / 业务服务 / 数据服务；或 UI 服务 / 逻辑服务 / 存储服务
- **为什么坏**：每次业务变更都要跨所有层；无法独立演进；本质是分布式单体
- **怎么修**：按**业务能力 / 限界上下文**切；垂直切片而非水平分层

### A4. 共享数据库
- **症状**：多个服务/应用直连同一个库；跨服务 join；一个团队改 schema 其他人崩
- **为什么坏**：最高强度的耦合；无法独立部署；故障域重叠
- **怎么修**：明确数据所有权；其他方通过 API 或读副本/CDC 访问；过渡期用视图/ACL 隔离

### A5. 循环依赖
- **症状**：A→B→C→A；模块/服务/包之间成环
- **为什么坏**：无法独立理解、测试、部署；变更传染；本质是边界没划对
- **怎么修**：抽出共享部分为第三个模块；用事件解耦；调整依赖方向（依赖倒置）；用适应度函数阻断

### A6. 上帝服务 / 上帝对象
- **症状**：一个服务/类承担了大部分职责；所有功能都要改它
- **为什么坏**：单点、瓶颈、发布耦合、无法独立扩展、团队争抢
- **怎么修**：按职责/变更理由拆分；识别其中的限界上下文

### A7. 分层地狱（Layered Lasagna）
- **症状**：Controller → Service → Manager → Facade → DAO → Entity → DTO，一半是纯转发
- **为什么坏**：全是浅模块；加一个字段改七层；调试要穿透多层
- **怎么修**：删掉纯转发的层；合并职责；用深模块（窄接口 + 厚实现）

## B. 耦合类

### B1. 同步深链（Synchronous Chain）
- **症状**：A → B → C → D → E 同步串行调用
- **为什么坏**：可用性乘积下降（0.999^5 ≈ 99.5%）；延迟累加；一跳慢全链慢
- **怎么修**：异步化非关键步骤；聚合（BFF）；并行调用；缓存；降级

### B2. 共享内核（Shared Kernel）滥用
- **症状**：多个团队共享一块代码/模型，必须同步发布
- **为什么坏**：强制协调；任何改动影响所有人；发布耦合
- **怎么修**：复制而非共享（在上下文边界处）；用 ACL 翻译；只共享真正稳定的契约

### B3. 时序耦合（Temporal Coupling）
- **症状**：系统 A 必须在线，B 才能工作；部署必须同时
- **为什么坏**：无法独立升级；一方故障拖垮另一方
- **怎么修**：异步消息 + 重试；本地缓存/副本；版本兼容的契约

### B4. 契约泄漏（Leaky Contract）
- **症状**：API 暴露内部数据结构；消费者依赖未文档化的行为；改内部实现就破坏消费者
- **为什么坏**：Hyrum 定律——所有可观察行为都会被依赖；变更成本不可控
- **怎么修**：定义显式的对外契约（DTO）；内部模型与契约分离；契约测试

### B5. 双向依赖（服务间互调）
- **症状**：A 调 B，B 也调 A
- **为什么坏**：部署顺序耦合；循环依赖；无法单独理解
- **怎么修**：抽出共享逻辑到第三个服务；改为事件驱动；明确依赖方向

## C. 数据类

### C1. 双写（Dual Write）
- **症状**：应用同时写数据库和缓存/消息/另一个库
- **为什么坏**：无法保证原子性；一个成功一个失败就永久不一致
- **怎么修**：Outbox（业务写 + 事件写同事务）；CDC 从日志同步

### C2. 天真的事务边界（跨服务事务）
- **症状**：用 2PC/XA 或"尽量同时提交"实现跨服务强一致
- **为什么坏**：性能差、协调者单点、可用性下降
- **怎么修**：优先**重划边界**（把强一致的东西放同一聚合/服务）；否则用 Saga + 补偿 + 幂等

### C3. 非幂等的重试
- **症状**：网络超时后重试，导致重复下单/重复扣款
- **为什么坏**：超时后请求可能已成功；至少一次投递是常态
- **怎么修**：幂等键 + 去重表；乐观锁；状态机；天然幂等操作

### C4. 假设消息只投递一次
- **症状**：消费端不做去重；依赖"恰好一次"
- **为什么坏**：实际是"至少一次 + 幂等消费"
- **怎么修**：消费端幂等；去重表；位点提交策略明确

### C5. 无界查询（Unbounded Query）
- **症状**：`SELECT * FROM orders`；offset 深分页；没有分页/限制
- **为什么坏**：数据增长后 OOM/超时；深分页性能崩溃
- **怎么修**：强制分页；游标（cursor）分页；限制返回条数；加索引

### C6. 缓存一致性忽视
- **症状**：缓存与数据库不一致；缓存雪崩/击穿/穿透；没有过期策略
- **为什么坏**：用户看到脏数据；缓存失效瞬间打垮数据库
- **怎么修**：明确失效策略（TTL/主动失效）；随机化 TTL 防雪崩；互斥重建防击穿；空值缓存防穿透；预热

### C7. 分区键选错
- **症状**：按低基数字段（性别、状态）分区；热点分区；跨分区查询频繁
- **为什么坏**：热点导致单分区过载；跨分区查询/事务昂贵；**分区键极难更改（单向门）**
- **怎么修**：选高基数、访问均匀、与查询匹配、不常变的键；热点 key 二次拆分

## D. 接口与集成类

### D1. 网关里的业务逻辑
- **症状**：API 网关包含业务规则、数据转换、流程编排
- **为什么坏**：网关变成上帝服务；发布耦合；瓶颈
- **怎么修**：网关只做横切（路由、认证、限流、观测）；业务逻辑下沉到服务

### D2. 过度版本化（Version Explosion）
- **症状**：每个小改动就升 API 版本；v1/v2/v3 并存
- **为什么坏**：维护成本爆炸；客户端碎片化
- **怎么修**：内部服务只做向后兼容演进（扩张-收缩）；版本号只用于真正的破坏性变更

### D3. 事件地狱（Event Hell / Choreography 滥用）
- **症状**：用纯事件编排实现复杂流程；事件满天飞；没人说得清完整流程
- **为什么坏**：流程不可见、难调试、难修改、易循环依赖
- **怎么修**：复杂流程用**协调器（Orchestration）+ 显式状态机**；简单流程才用编排

### D4. 无 DLQ 的消息系统
- **症状**：消费失败就重试到死；毒丸消息永久阻塞
- **为什么坏**：消息积压；消费者卡死
- **怎么修**：重试 N 次后进死信队列 + 告警 + 人工处理流程

### D5. 透明远程调用（Transparent RPC）
- **症状**：用 RPC 框架让远程调用"看起来像本地调用"
- **为什么坏**：掩盖了网络延迟、失败、部分失败的语义差异
- **怎么修**：显式区分本地/远程；为远程调用设计超时、重试、幂等、降级

## E. 演化与运维类

### E1. 大爆炸重写（Big Bang Rewrite）
- **症状**：一次性重写整个系统，长时间不上线
- **为什么坏**：70%+ 失败率；需求漂移；无法验证；风险集中
- **怎么修**：绞杀者模式；分支抽象；并行运行；小步交付

### E2. 无回退的迁移
- **症状**：切换没有特性开关；出问题只能硬扛
- **为什么坏**：故障时无法快速恢复
- **怎么修**：每步都有开关与回退路径；灰度发布

### E3. 事后补可观测性
- **症状**：上线后才发现没有追踪/指标；排障靠猜
- **为什么坏**：分布式系统没有追踪几乎无法排障
- **怎么修**：从第一天用 OpenTelemetry 埋点；traceId 贯穿

### E4. 无超时的调用
- **症状**：HTTP/RPC/DB 调用没有超时设置
- **为什么坏**：慢依赖耗尽线程池/连接池 → 雪崩
- **怎么修**：全面设置超时；逐跳递减；配合熔断

### E5. 无退避的重试（重试风暴）
- **症状**：失败立即重试；所有客户端同时重试
- **为什么坏**：流量放大 → 雪崩
- **怎么修**：指数退避 + 抖动 + 次数上限 + 重试预算；仅对可重试错误重试

### E6. 单点（SPOF）
- **症状**：某个组件挂了全系统不可用；无冗余
- **为什么坏**：可用性上限 = 该组件的可用性
- **怎么修**：冗余部署；无状态化；健康检查 + 自动摘除

### E7. 有状态服务
- **症状**：服务在本地保存会话/缓存，无法随意扩缩容
- **为什么坏**：扩缩容困难；故障恢复慢；粘性会话成为瓶颈
- **怎么修**：状态外置（Redis/DB）；无状态设计；粘性会话仅作临时方案

### E8. 手工部署
- **症状**：部署靠文档 + 手动步骤
- **为什么坏**：易错、不可重复、慢、无法回滚
- **怎么修**：CI/CD；基础设施即代码；一键部署与回滚

### E9. 没有恢复演练的备份
- **症状**：有备份策略，但从没验证过能否恢复
- **为什么坏**：备份可能损坏、不完整、恢复流程不可行
- **怎么修**：定期恢复演练；明确 RTO/RPO；自动化恢复流程

### E10. 秘钥硬编码 / 静态长期凭证
- **症状**：密钥在代码/配置/环境变量；长期不变
- **为什么坏**：泄漏无法收回；无法轮换；爆炸半径大
- **怎么修**：密钥管理服务（Vault/KMS）；动态短期凭证；定期轮换；密钥扫描进 CI

## F. 决策与组织类

### F1. 象牙塔架构（Ivory Tower）
- **症状**：架构师脱离代码与团队，产出无人能落地的设计
- **为什么坏**：设计与现实脱节；团队不买账；无法验证
- **怎么修**：持续参与实现与值班；与团队共同设计；ADR 让决策可追溯

### F2. 银弹崇拜（Silver Bullet）
- **症状**：追新技术/新架构，忽视具体约束
- **为什么坏**：为不匹配的场景引入复杂度；团队没有能力承接
- **怎么修**：先问"它解决什么被量化的问题"；权衡分析；试点验证

### F3. 过度设计（Over-engineering / YAGNI 违反）
- **症状**：为假想的未来引入抽象/扩展点/微服务
- **为什么坏**：复杂度支出；当前所有变更变慢；假想需求大多不来
- **怎么修**：YAGNI；只为**单向门**决策留余地；用"最早可能需要的时间"判断

### F4. 不做决策（Analysis Paralysis）
- **症状**：只罗列选项，长期不拍板；反复讨论同一件事
- **为什么坏**：不决策也是决策（默认选最差的）；团队停滞
- **怎么修**：区分单向门/双向门；双向门快速决定；明确决策人与截止时间

### F5. 忽视康威定律
- **症状**：设计了一个组织撑不起的架构（如小团队上微服务）
- **为什么坏**：架构与组织冲突时，输的总是架构
- **怎么修**：架构与组织一起设计；用逆康威操作；考虑认知负荷

### F6. 认知超载（超出团队承载）
- **症状**：技术栈过多、服务过多、抽象过多，团队"装不下"
- **为什么坏**：交付变慢、故障变多、知识集中、人才流失
- **怎么修**：控制复杂度预算；限制技术栈数量；平台化降低认知负荷；做减法

### F7. 复杂度预算透支
- **症状**：本地跑不起来、新人上手 > 2 周、一次需求动 5 个服务、无人敢改
- **为什么坏**：交付能力被复杂度吃掉
- **怎么修**：复杂度审计；合并/删除服务；简化技术栈；停止引入新模式

### F8. 用"最佳实践"压人
- **症状**：以"业界都这么做"为由推行方案，不讨论具体约束
- **为什么坏**：忽略前提；可能不适用；团队抵触
- **怎么修**：每个模式都带适用条件；用权衡矩阵而非权威

## 使用建议

1. **审查设计时**：按 A→F 顺序逐类扫一遍，标注命中的条目
2. **命中的条目**：判断是"有明确理由的例外"还是"真问题"
3. **优先级**：先修**高耦合**类（A/B/C），再修接口类（D），最后是决策类（F）
4. **不要一次全改**：按影响面与风险排序，小步演化
5. **每条修复都写 ADR**：记录为什么改、代价是什么

> ⚠️ **反模式是启发式，不是教条。** 有明确理由的"反模式"可能是正确的选择（如：小团队故意选单体 = 不是反模式；大团队被迫选单体 = 才是问题）。**关键是能说清理由与代价。**
