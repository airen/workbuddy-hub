# 架构评审清单

> 用法：评审一份架构设计时逐项过。每项标注 ✅ 通过 / ⚠️ 需讨论 / ❌ 缺失。
> 重点不是"打分"，而是**发现风险**与**让取舍显式**。
> 完整的架构评估流程见 `references/decision-frameworks.md` 的 ATAM-lite 部分。

---

## 0. 材料完整性

- [ ] 驱动因素已明确写出（关键质量属性 + 硬约束 + 优先级）
- [ ] 有 C4 Context 图（系统与外部关系）
- [ ] 有 C4 Container 图（部署单元）
- [ ] 关键流程有时序图
- [ ] 关键决策有 ADR
- [ ] 数据模型与归属已说明

> ⚠️ **驱动因素缺失 = 无法评审。** 因为没有前提，任何设计都"看起来可以"。

---

## 1. 驱动因素与质量属性

- [ ] 业务目标清晰（要解决什么问题、成功长什么样）
- [ ] 量级有数字（QPS、数据量、增长、延迟要求）
- [ ] 关键质量属性有**可度量的场景**（六要素：刺激源→刺激→制品→环境→响应→度量）
- [ ] 质量属性之间有**明确优先级**（因为必然冲突）
- [ ] 硬约束已列出（技术/合规/时间/预算/存量系统）
- [ ] 利益相关者已识别（尤其能一票否决的人）

**要问的问题**：
- "如果两个质量属性冲突，保哪个？"
- "'高性能'具体是多少？怎么验证？"

---

## 2. 边界与结构

- [ ] 边界基于**业务能力/限界上下文**划分（不是按技术层）
- [ ] 每个边界的**职责**能用一句话说清
- [ ] 跨边界交互**最小化**（不是每个操作都跨边界）
- [ ] 依赖方向**单向**，无循环依赖
- [ ] 每个边界的**数据所有权**唯一且明确
- [ ] 边界与**团队结构**匹配（康威定律）
- [ ] 边界与**认知负荷**匹配（团队装得下）

**要问的问题**：
- "这个边界是基于什么划的？如果业务变化，边界会怎么变？"
- "改这个模块，会不会被迫改其他模块？"

---

## 3. 质量属性设计

### 3.1 性能
- [ ] 有延迟预算分解（端到端目标 → 各跳分配）
- [ ] 有容量估算（当前/1 年/3 年）
- [ ] 关键路径有缓存策略
- [ ] 有性能测试计划（压测场景 = 真实场景）

### 3.2 可用性
- [ ] SLA/SLO 明确（且不是 100%）
- [ ] 无单点（或单点有明确理由与缓解）
- [ ] 故障域隔离（爆炸半径受控）
- [ ] 有降级策略（关非核心保核心）
- [ ] RTO/RPO 明确且演练过

### 3.3 可伸缩性
- [ ] 扩展方向明确（水平/垂直、读/写）
- [ ] 无状态化（或状态外置）
- [ ] 有分区/分片策略（如需要）
- [ ] 有热点应对（大 key、大 V、爆款）

### 3.4 可修改性
- [ ] 变化轴已识别（什么会变？变的时候要动多少？）
- [ ] 有明确的扩展点（新增一种 X 需要改哪里？）
- [ ] 契约稳定（内部实现可变，对外契约稳定）

### 3.5 安全性
- [ ] 认证与授权方案明确（服务端强制校验）
- [ ] 最小权限（服务/DB 账号/密钥）
- [ ] 敏感数据加密（传输 + 存储 + 字段级）
- [ ] 密钥管理（专用服务、轮换、不进版本库）
- [ ] 有威胁建模（STRIDE）

### 3.6 可测试性
- [ ] 关键逻辑可独立测试（不依赖外部系统）
- [ ] 有契约测试（服务间）
- [ ] 有测试数据策略

### 3.7 可部署性
- [ ] 可独立部署（不要求同步发布其他服务）
- [ ] 有回滚方案
- [ ] 支持灰度/金丝雀
- [ ] 部署自动化（无手工步骤）

---

## 4. 数据

- [ ] 每份数据有唯一所有者
- [ ] 访问模式清晰（查询维度、读写比、量级）
- [ ] 存储选型有理由（对照访问模式，不是"因为流行"）
- [ ] 一致性策略明确（强一致/最终一致，各自的理由）
- [ ] 跨服务写操作**幂等**
- [ ] 需要时用了 Outbox / Saga，补偿逻辑已设计
- [ ] 分区键选择合理（高基数、均匀、与查询匹配、不常变）
- [ ] 数据增长预测（1 年/3 年）与归档策略
- [ ] 备份 + **恢复演练**
- [ ] 合规（数据主权、留存期、删除权）

---

## 5. 集成与通信

- [ ] 同步/异步选择有理由
- [ ] 同步调用链**足够浅**（可用性乘积）
- [ ] 所有网络调用有**超时**，且逐跳递减
- [ ] 重试有**退避 + 抖动 + 上限**，且仅对可重试错误
- [ ] 关键依赖有**熔断**与**降级**
- [ ] 有**限流**保护
- [ ] 消息系统有 **DLQ** 与积压监控
- [ ] 契约管理方式明确（OpenAPI/proto/Schema Registry）
- [ ] 版本策略明确（扩张-收缩 / 版本号）
- [ ] 复杂流程用**协调器**而非纯事件编排

---

## 6. 故障模式与弹性

- [ ] 每个外部依赖挂了会怎样？逐一回答
- [ ] 网络分区时的行为（CP 还是 AP）？
- [ ] 有级联故障防护（熔断、隔板、限流）
- [ ] 有优雅停机（处理完在途请求）
- [ ] 有健康检查与自动摘除
- [ ] 幂等覆盖所有跨进程写
- [ ] 做过混沌工程演练（至少预发）

**要问的问题**：
- "如果数据库挂了 30 秒，系统表现是什么？"
- "如果消息重复投递 10 次，会怎样？"
- "如果下游变慢 10 倍，会怎样？"

---

## 7. 可观测性

- [ ] 结构化日志（含 traceId）
- [ ] 关键指标（RED / USE，含 P95/P99 延迟）
- [ ] 分布式追踪（OpenTelemetry）
- [ ] 日志/指标/追踪通过 traceId 打通
- [ ] 告警面向**症状**（不是原因），且噪音可控
- [ ] 有仪表盘（关键业务与关键资源）
- [ ] 有 Runbook（常见故障处理步骤）
- [ ] 敏感数据不进日志

---

## 8. 演化

- [ ] 单向门决策已识别并慎重论证
- [ ] 有增量落地路径（不是大爆炸）
- [ ] 迁移有回退开关
- [ ] 有适应度函数守护架构约束
- [ ] 技术债已识别并量化利息
- [ ] 有明确的"何时该重估"触发点

---

## 9. 成本与组织

- [ ] 复杂度预算支出被评估（新增了几个服务/存储/技术栈？）
- [ ] 团队能承接（认知负荷、技能、人数）
- [ ] 运维负担可承受（值班、告警、恢复）
- [ ] 初始成本与**持续成本**都估算过
- [ ] 第三方依赖的**开源许可**已核对（可商用？合规？）
- [ ] 供应商锁定风险已评估
