# 架构 Kata 工作表

> **架构 Kata = 限时的架构设计演练。** 目的是**练习决策能力**，不是练习画图。
> 完整说明见 `references/10-practice-and-communication.md`。

## 1. 基本设定

| 项 | 内容 |
|----|------|
| 题目 | |
| 时长 | 90 分钟（可裁剪为 45 / 60 分钟） |
| 分组 | 每组 3–5 人 |
| 产出 | C4 Context + Container 图、关键决策清单、≥1 份 ADR |
| 评委 | 1–2 人（负责出题、提问、复盘） |

## 2. 流程与时间盒

| 阶段 | 时长 | 做什么 | 产出 |
|------|------|--------|------|
| 1. 读题 | 5 min | 阅读需求（含驱动因素与约束） | — |
| 2. 澄清 | 5 min | 向出题人提问，补齐缺失信息 | 澄清记录 |
| 3. 设计 | 40 min | 协作产出架构与决策 | 图 + 决策清单 |
| 4. 展示 | 5 min/组 | 讲解设计（**重点是取舍**） | — |
| 5. 互评 | 20 min | 互相提问挑刺 | 问题清单 |
| 6. 复盘 | 15 min | 总结敏感点/取舍点/盲区 | 复盘记录 |

> ⚠️ **严格计时。** 时间压力正是练习的一部分——真实项目里也没有无限时间。

## 3. 题目模板（出题人用）

```markdown
## 题目：<系统名称>

### 业务背景
<一句话说清这个系统做什么、给谁用>

### 已知量级
- 用户规模：<DAU / 总用户>
- 峰值 QPS：<数字>
- 数据量：<当前 + 增长预测>
- 延迟要求：<P99 目标>
- 可用性要求：<SLO>

### 硬约束
- 技术：<必须用的 / 禁止用的>
- 组织：<团队规模、技术栈熟悉度>
- 时间：<上线时间>
- 合规：<等保/隐私/行业要求>
- 存量：<必须复用的系统>

### 关键质量属性（按优先级）
1. <属性> —— <为什么重要>
2. ...

### 交付要求
- C4 Context + Container 图
- 关键决策清单（含备选与取舍）
- 至少 1 份 ADR
- 失败场景分析（至少 3 个）
- 演化路径（第一版做什么，何时扩展）
```

### 参考题目库

| 题目 | 主要考点 |
|------|---------|
| 设计一个短链服务 | 高并发读、ID 生成、缓存、存储选型 |
| 设计一个秒杀系统 | 削峰、库存一致性、限流、防超卖 |
| 设计一个 Feed 流 | 推拉模式、大 V 问题、分页、排序 |
| 设计一个支付系统 | 幂等、对账、状态机、最终一致、合规 |
| 设计一个 IM 消息系统 | 长连接、消息可靠性、离线消息、多端同步 |
| 设计一个文件存储服务 | 分块上传、去重、CDN、元数据 |
| 设计一个订单系统 | 领域建模、状态机、Saga、补偿 |
| 设计一个搜索服务 | 倒排索引、数据同步、排序、相关性 |
| 把单体拆成微服务 | 边界划分、数据拆分、迁移策略 |
| 替换一个遗留系统 | 绞杀者模式、双写、回退 |

## 4. 设计阶段引导问题

**驱动因素**
- 这个系统最关键的质量属性是哪 2–3 个？
- 它们之间有冲突吗？保哪个？

**边界**
- 有哪些子域？哪些是核心域？
- 边界按什么划？为什么？
- 跨边界交互能再少一点吗？

**数据**
- 每份数据归谁所有？
- 一致性要求是什么？
- 分区键选什么？

**集成**
- 哪些调用同步、哪些异步？为什么？
- 失败怎么处理？
- 重复怎么处理？

**失败模式**（**必答**）
- 如果数据库挂了 30 秒会怎样？
- 如果下游服务变慢 10 倍会怎样？
- 如果消息重复投递 10 次会怎样？
- 如果流量突然涨 10 倍会怎样？
- 如果某个服务部署到一半失败了会怎样？

**演化**
- 第一版最小可用是什么？
- 什么时候需要扩展？扩展的触发信号是什么？
- 哪些决策是单向门？

**组织**
- 几个团队？怎么分工？
- 团队装得下这个设计吗？

## 5. 评分表

| 维度 | 权重 | 评分要点 | 得分（1–5） |
|------|------|---------|-----------|
| **驱动因素识别** | 20% | 是否准确识别关键质量属性与约束？是否给了数字？ | |
| **权衡与取舍** | 25% | 是否列出多个备选？是否明确说出代价？ | |
| **边界划分** | 20% | 边界依据是否合理？是否按业务而非技术切？ | |
| **失败模式** | 15% | 是否考虑了依赖故障、重复、并发、超时？ | |
| **数据与一致性** | 10% | 数据归属清晰吗？一致性策略明确吗？ | |
| **演化与落地** | 10% | 有增量路径吗？有回退吗？ | |

> **注意**：**"图漂不漂亮"不在评分项里。** 重点永远是**决策质量**。

## 6. 互评问题清单

向其他组提问（每组至少问 3 个）：

- 你的关键质量属性是什么？为什么是这个而不是别的？
- 这个决策的**代价**是什么？
- 如果 X 挂了会怎样？
- 为什么这样划边界？如果业务变化边界会怎么变？
- 这个决策是单向门还是双向门？
- 你的方案 A 和方案 B 都可行，为什么选 A？
- 数据一致性怎么保证？
- 你怎么知道这个方案真的能满足性能要求？
- 团队能承接这个复杂度吗？
- 第一版你会做什么？什么时候扩展？

```markdown
- <哪两个属性此消彼长？我们选了哪边？为什么？>

-

- 
```

## 8. 组织建议

| 建议 | 说明 |
|------|------|
| **固定周期** | 每两周一次，形成习惯 |
| **轮流出题** | 出题人也要思考"什么才是好题目" |
| **真实场景优先** | 用团队正在面对的真实问题做题目（但脱敏） |
| **严格计时** | 时间压力是练习的一部分 |
| **强制提问** | 互评阶段每人至少问 3 个问题 |
| **记录并沉淀** | 复盘结论沉淀成团队的设计检查清单 |
| **新人参与** | 观察学习，逐步参与 |
| **不要变成考试** | 目标是暴露盲区，不是评判个人 |
