# 工作流树与注册表工具包

用树结构思考，不用散文叙述。产出结构化规格，让开发据此实现、QA 据此测试。

## 何时用本技能

- 要把业务流程/系统流程规格化成工作流树
- 要找出代码里存在但没人写下来的隐式工作流
- 要维护一份四视图工作流注册表
- 要定义系统间的交接契约与验收条件

不适用于：多 Agent 拓扑选型（那是 `topology-select` 的活）。

## 两个交付物（对应 references/）

| 文件 | 交付什么 | 什么时候读 |
|---|---|---|
| `references/discovery-method.md` | 发现无人告知你的工作流：七类必读文件 + 四问追问法 | 动手设计前 |
| `references/workflow-registry.md` | 四视图工作流注册表：按工作流 / 按组件 / 按用户旅程 / 按状态 | 维护注册表时 |

## 工作流程

1. **先发现再设计**：按 `discovery-method.md` 读路由文件、Worker/Job、数据库迁移、编排配置、IaC、配置与环境变量、ADR——每个都是隐式工作流的入口
2. **反复追问四问**：是什么触发了它？接下来会发生什么？如果失败了怎么办？谁来清理？
3. **画工作流树**：正常路径 + 所有分支条件 + 故障模式 + 恢复路径 + 交接契约
4. **登记注册表**：按四视图交叉登记，状态用 `Approved` / `Review` / `Draft` / `Missing` / `Deprecated`
5. **标出隐患**：存在于代码中却没有规格说明的工作流，一律记为 `Missing`——它会因缺乏完整理解而被改崩

## 硬规则

- **每条路径必须显式命名**：没写下来的路径等于不存在的路径
- **故障模式必须配恢复动作**：只写"如果超时"不够，要写"超时后谁重试、重试几次、失败谁兜底"
- **交接必须有契约**：系统间交接要写清输入、输出、验收条件，不靠口头约定
- **注册表是权威参考**：不只是一份规格文件清单，要让工程师/运维/产品/Agent 都能从任意角度查到
- **不写代码不做 UI 决策**：设计的是代码和 UI 必须遵循的工作流
