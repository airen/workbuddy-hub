# 支付与订阅接入

指导支付流程、Webhook 回调和订阅功能的接入，处理集成中的常见问题。

> 支付集成最容易出事的地方不在"能不能付成功"，而在**重复扣款、漏单、密钥泄露**。

## 适用场景

- 首次接入支付
- 加订阅 / 周期性扣费
- 支付回调不可靠、订单状态对不上
- 上线前的支付安全检查

## 输入

- 业务模式：一次性付款 / 订阅 / 两者都有
- 技术栈与运行环境
- 已有的订单与用户体系
- 是否已有所需的商户账号与密钥管理机制

## 执行步骤

### 步骤 1 — 设计支付流程

先画清楚状态机：

```
创建订单 → 发起支付 → 用户支付 → 收到回调 → 更新订单 → 交付
                    ↘ 支付失败 / 超时 → 订单回到可支付状态
```

明确每个状态的**谁负责更新**（回调更新，还是前端轮询更新）。**不要让前端的成功页面成为订单生效的唯一依据。**

### 步骤 2 — 接入支付

- 密钥只从环境变量或密钥管理服务读取，**不写进代码、不进版本库、不进日志**
- 区分测试密钥与生产密钥，环境切换有明确开关
- 金额以最小货币单位（分）传递，避免浮点误差
- **金额与订单身份由服务端决定（硬性）**：金额、币种、商品 / 订阅项、归属用户一律以**服务端根据订单记录自己算出**的值为准，**绝不接受客户端传入的金额、币种、折扣或单价**。客户端最多传 `cart_id` / `sku` + 数量这类**引用**，服务端查库定价后使用。
- **密钥不进对话、不进输出**：不得要求用户把密钥粘贴到对话里，也不得在报告、代码块、错误说明或任何输出中写出密钥原文（一律写成 `<已配置>`）。配置缺失就**停下来让用户自己去配环境变量**，不由我代劳转发
- **日志按需脱敏**：排错时打印的是变量名与是否命中，不是值；原始回调载荷只落地结构化字段（事件 ID、类型、金额、本地订单号），不整体打印
- **最小权限**：优先用受限 / 只读密钥，权限范围与实际用途匹配
- **泄露即轮转**：一旦发现密钥疑似泄露（进过对话、日志、聊天记录、外部文件），**先轮换密钥再处理其他事**，清理历史只是第二步

### 步骤 3 — Webhook 回调（重点）

必须做五件事，缺一不可：

1. **验签**：用官方 SDK 或按文档校验签名，不验签的回调任何人都能伪造
2. **幂等**：同一个事件可能重复投递，用事件 ID 去重，避免重复发货 / 重复加权益
3. **快速响应**：先返回成功，再异步处理业务逻辑，避免超时被判失败而重投
4. **可重放**：处理失败时要能安全地再处理一次
5. **不信任回调里的业务字段**：回调只用于回答「哪一笔支付成功了」，**不代表它说了多少钱就是多少钱**。金额、币种、订单归属以本地订单记录，以及随后向支付平台发起的**服务端主动查询**为准。任何「回调说已付 X 元就按 X 元发货」的逻辑，等于把定价权交给了外部请求。

| 常见坑 | 后果 | 做法 |
|---|---|---|
| 不验签 | 伪造回调，白拿商品 | 必须校验签名 |
| 不幂等 | 重复发货、重复扣款 | 事件 ID 去重 + 状态检查 |
| 回调里做慢操作 | 超时重投 | 先 ack，后处理 |
| 依赖前端跳转成功 | 用户关页面就漏单 | 以回调为准 |

### 步骤 4 — 订阅生命周期

- 明确试用期、续费、升级降级、取消的时间点语义
- 处理扣款失败：重试策略、宽限期、最终失效
- 用户取消后，权益什么时候真正结束（不要立即断，也不要无限延长）

### 步骤 5 — 对账与监控

- 定期对照支付平台账单与本地订单，发现漏单与重复单
- 关键指标：支付成功率、回调失败率、订阅续费失败率
- 回调失败要有告警，不能静默

### 步骤 6 — 上线前检查

- [ ] 密钥不在代码与日志中
- [ ] 回调验签已生效（用伪造请求验证被拒）
- [ ] 重复投递同一事件不会重复发货
- [ ] 金额单位正确，无浮点误差
- [ ] 测试环境与生产环境密钥隔离
- [ ] 用被篡改的请求验证会被拒：金额改小、数量改多、订单号换成他人账号下的订单
- [ ] 同一订单号重复投递只发货一次（发货侧有唯一性约束，不只是回调去重）
- [ ] 有对账手段与告警
- [ ] 仓库含 `.env.example`（只有占位符）且真实 `.env*` 已在 `.gitignore` 中
- [ ] 代码与日志中搜索 `sk_live_` / `sk_test_` / `whsec_` 无任何命中
- [ ] 所用密钥是受限密钥，权限与实际用途匹配

## 输出

- 支付流程与订单状态机
- 回调处理方案（验签、幂等、异步）
- 订阅生命周期定义
- 上线前检查清单与验证结果

## 反模式

- **不验签**：等于把发货接口公开
- **回调不幂等**：重复发货是最常见的线上事故之一
- **密钥写进代码或日志**：泄露后损失不可控
- **信前端不信回调**：用户关页面就漏单
- **金额用浮点数计算**：精度误差会导致对账不平
- **没有对账手段**：问题会以"用户投诉"的形式被发现
