# 设计两遍（Design It Twice）

当用户想为某个已选定的深化候选对象探索备选接口时，用这套并行子代理（用 Agent 工具）的模式。它基于「Design It Twice」（Ousterhout）：你的第一个想法不太可能是最好的。

沿用 [SKILL.md](../SKILL.md) 里的词汇：**模块（module）**、**接口（interface）**、**接缝（seam）**、**适配器（adapter）**、**杠杆（leverage）**。

## 流程

### 1. 框定问题空间

在拉起子代理之前，为这个已选定的候选对象写一份面向用户的问题空间说明：

- 任何新接口都需要满足的约束
- 它会依赖哪些依赖，以及这些依赖属于哪个类别（见 [DEEPENING.md](DEEPENING.md)）
- 一段粗略的示意性代码草稿，用来把约束落地——不是提案，只是让约束变得具体的一种方式

把这份说明给用户看，然后立刻进入第 2 步。用户阅读和思考的同时，子代理在并行工作。

### 2. 拉起子代理

并行拉起 3 个以上的子代理。每个都必须为这个深化后的模块产出**截然不同**的接口。

给每个子代理一份独立的技术简报（文件路径、耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖类别、接缝后面放着什么）。这份简报与第 1 步里面向用户的问题空间说明相互独立。给每个代理一个不同的设计约束：

- 代理 1：「最小化接口：入口点最多控制在 1–3 个。把每个入口点的杠杆最大化。」
- 代理 2：「最大化灵活性：支持多种用例和扩展。」
- 代理 3：「为最常见的调用方优化：让默认用例变得轻而易举。」
- 代理 4（如果适用）：「围绕端口与适配器来设计跨接缝的依赖。」

简报里要同时带上 [SKILL.md](../SKILL.md) 的词汇和 GLOSSARY.md 的词汇，好让每个子代理的命名既跟架构语言一致，也跟项目的领域语言一致。

每个子代理输出：

1. 接口（类型、方法、参数，外加不变量、顺序、错误模式）
2. 展示调用方如何使用它的用例示例
3. 实现在接缝后面隐藏了什么
4. 依赖策略与适配器（见 [DEEPENING.md](DEEPENING.md)）
5. 取舍：杠杆高在哪里，薄在哪里

### 3. 呈现并比较

依次呈现各个设计，好让用户逐个消化，然后用文字把它们做比较。按**深度**（接口处的杠杆）、**局部性**（变更集中在哪里）和**接缝位置**来对照。

比较之后，给出你自己的推荐：你认为哪个设计最强、为什么。如果不同设计里的元素能很好地组合，就提出一个混合方案。要有主见：用户想要的是一个强有力的判断，不是一张菜单。
