# 原型（prototype）

原型是**用来回答一个问题的、用完即弃的代码**。问题决定它的形态。

## 选一条分支

判断正在回答的是哪个问题，依据用户的提示、周围的代码，或者（如果用户在场）直接问：

- **「这套逻辑 / 状态模型感觉对吗？」** → [LOGIC.md](references/LOGIC.md)。构建一个单独的可分享 HTML 文件（自由试玩按钮，加上分标签页的引导式走查），把状态机推过那些在纸上难以推理的场景，并且让非开发者也能操作。
- **「这东西应该长什么样？」** → [UI.md](references/UI.md)。在单个路由上生成几个截然不同的 UI 变体，通过 URL 查询参数（search param）和一个悬浮底栏来切换。

这两条分支产出的东西差别很大，选错就白白浪费掉整个原型。如果问题确实含糊、又联系不上用户，就默认选那条跟周围代码更匹配的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部写明这个假设。

## 两条分支都适用的规则

1. **从第一天起就是一次性的，并明确标记出来。** 把原型代码放在它将来真正会被用到的地方附近（挨着它所原型化的模块或页面），让上下文一目了然，但命名要让随便一个读者都能看出这是原型、不是生产代码。对一次性的 UI 路由，遵守项目已有的路由约定；不要发明一套新的顶层结构。
2. **跑起来毫不费力。** UI 原型从项目任务运行器里的一条命令启动：`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示是一个用户双击就能打开的单个 HTML 文件。无论哪种，启动它都不需要动脑子。
3. **默认不持久化。** 状态活在内存里。持久化正是原型要去*检验*的东西，而不是它应该依赖的东西。如果问题明确涉及数据库，就打到一台临时数据库，或者一个名字明确写着「PROTOTYPE, wipe me」的本地文件上。
4. **跳过打磨。** 不要测试，除了让原型*能跑起来*所需的之外不要错误处理，不要抽象。重点是快速学到点东西。
5. **把状态摆到台面上。** 每个动作之后（逻辑）或每次切换变体时（UI），把全部相关状态打印或渲染出来，好让用户看到什么变了。
6. **完成后把它存档。** 把任何经过验证的决策并入真实代码，然后把原型本身作为**一手来源（primary source）**存档：把它提交到一个一次性分支上，排除在 main 之外，并在实现 issue 上留下一个指向那个分支的上下文指针。答案也要记下来（结论，以及它了结的那个问题），写进 issue 或某个 commit。main 分支只保留经过验证的决策。
