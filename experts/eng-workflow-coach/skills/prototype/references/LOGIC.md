# 逻辑原型（Logic Prototype）

一个单独、自包含的 HTML 文件（一份**可分享的演示**），让任何人都能靠点击按钮来驱动一个状态模型。当问题关乎**业务逻辑、状态迁移或数据形态**时用它：这类东西在纸上看着合理，只有真正推过几个真实场景之后才感觉出不对劲。

因为它是一个无需安装任何东西的文件，你可以把它交给非开发者（设计师、PM、领域专家），让他们自己感受这个模型。所以它说的是他们的语言，而不是代码的语言。

## 什么时候这才是对的形态

- 「我不确定这个状态机能不能处理先 X 再 Y 的边界情况。」
- 「这个数据模型到底能不能让我表示出……这种情况？」
- 「我想在动手写之前，先摸清楚这个 API 应该长什么样。」
- 任何有人想**按按钮、看着状态变化**的场景。

如果问题是「这东西应该长什么样」，那这就是错的分支。用 [UI.md](UI.md)。

## 流程

### 1. 把问题写下来

在写代码之前，写下你正在原型化的是哪个状态模型、哪个问题。一段话，放在演示的顶部（放在可见的引言里，不能只写成注释）。一个答错问题的逻辑原型是纯浪费，所以把问题写明确，好让它以后能被核对，无论用户是现在看着还是离开（AFK）后再回来。

### 2. 把逻辑隔离在一个可移植的模块里

把真正的逻辑（真正在回答问题的那个部分）放进一个单独的 `<script>` 块里，写成一个小而纯的模块，好让它以后能被拎出来、直接放进真实的代码库。它周围那个页面是一次性的；这个模块不是。

正确的形态取决于问题：

- **一个纯 reducer**：`(state, action) => state`。当动作是离散事件、状态是单个值时好用。
- **一个状态机**：显式的状态和迁移。当「此刻到底哪些动作是合法的」本身属于问题的一部分时好用。
- **一组作用于普通数据类型的纯函数**。当没有隐式的当前状态、只有转换时好用。
- **一个方法面清晰的类或模块**，当逻辑确实拥有一份持续存在的内部状态时用。

挑那个最契合所问问题的形态，*而不是*最容易接到页面上的形态。保持纯净：不要 DOM，不要 `document`，不要按钮处理器伸手进去。页面调用它；没有东西反向流动。正是这一点让原型在超出自身寿命之后依然有用：问题一旦被回答，经过验证的 reducer / 状态机 / 函数组就能自己升格进真实模块。

### 3. 构建可分享的 HTML 文件

一个文件，纯 HTML/CSS/JS：不用框架、不用打包器、不用服务器，所有东西都内联，这样双击就能打开，转发邮件也不会坏。任何人打开它就应该能跑。

把它写给非开发者。每个标签都用**领域语言**，而不是代码：按钮和状态读起来像业务，而不是像 reducer。用大白话解释正在发生什么。

用干净的层级从上到下排布：

1. **标题和一行说明**，讲清这个演示让你探索什么（第 1 步里的那个问题）。
2. **当前状态**：全部相关状态，渲染成一块易读的面板（带标签的字段，不是原始 JSON dump），每次点击后都重新渲染，好让变化看得见。在有助于非开发者跟上思路的地方，点出刚刚变了什么。
3. **自由试玩按钮**：每个动作一个按钮，始终可用，让任何人都能按任意顺序摆弄这个模型。每次点击都派发它对应的动作并重新渲染状态。
4. **引导式走查**：一组**场景**，每个标签页一个。每个标签页里放一段对场景的简短大白话描述（它搭起的处境，以及要留意什么），下面是为该场景排好序的**要按的按钮**。每一步都是一个真实的按钮：点它就执行那个动作并前进到下一步。启动一次走查会重置到一个已知的初始状态，好让这个场景每次都跑得一模一样。

挑选那些能展示别扭场景的场景，也就是在纸上难以推理的那些：happy path、棘手的边界情况、一次对「本应非法」之事的尝试。

保持好看但克制：干净的排版、宽松的间距、一个强调色。不要动画、不要花哨玩意：不要有任何跟状态和按钮抢注意力的东西。

### 4. 交出去

把文件发给他们，或者替他们打开。他们有空时会点着走查和自由试玩过一遍；有意思的时刻是他们说「等等，这不应该可能啊」或者「咦，我以为 X 会不一样」的时候；那些是 _想法本身_ 的 bug，而这正是全部意义所在。如果他们想要新动作或新场景，就加上。原型是会演化的。

### 5. 存档答案和原型

原型回答了它的问题之后，先存档答案，再按 [SKILL](../SKILL.md) 描述的方式存档原型。逻辑原型的具体映射是：经过验证的 reducer / 状态机 / 函数组升格进真实模块（决策，被吸收）；HTML 外壳则跟着去那个一次性分支，把原型作为一手来源保留下来，而由于它是单个自包含文件，在那里依然能毫不费力地重跑。

## 反模式

- **不要加测试。** 一个需要测试的原型就不再是原型了。
- **不要把它接到真实数据库上。** 用内存状态，除非问题专门关乎持久化。
- **不要做泛化。** 不要「万一以后想支持 X 呢」。原型只回答一个问题。
- **不要把逻辑和页面搅在一起。** 如果那个纯模块引用了 DOM、`document` 或按钮处理器，它就不再能被拎出来了。让页面成为纯模块外面一层薄薄的外壳。
- **不要去抓框架、打包器或服务器。** 一个收件人双击就能打开的文件；一个 React 应用或 dev server 会把「可分享」这一点彻底毁掉。
- **不要把 HTML 外壳发到生产环境。** 那个页面是为「用鼠标一页页点过去」而优化的。它背后那个逻辑模块才是值得留下的部分。
