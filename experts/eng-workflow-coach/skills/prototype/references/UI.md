# UI 原型（UI Prototype）

在单个路由上生成**几个截然不同的 UI 变体**，用一个悬浮底栏来切换。用户在浏览器里翻来翻去，挑一个（或者从每个里各偷一点），然后把其余的扔掉。

如果问题关乎逻辑 / 状态，而不是某个东西长什么样，那这就是错的分支。用 [LOGIC.md](LOGIC.md)。

## 什么时候这才是对的形态

- 「这个页面应该长什么样？」
- 「我想在定下来之前，先看看这个仪表盘的几个方案。」
- 「给设置页换个布局试试。」
- 任何用户否则会在脑子里对着三个模糊的稿子纠结一整天的时刻。

## 两种子形态：强烈偏好子形态 A

当 UI 原型**紧贴着应用其余部分**时，判断起来容易得多：真实的 header、真实的侧边栏、真实的数据、真实的密度。一个孤立的一次性路由是个真空：每个变体单独看都挺好。只要有一个说得过去的既有页面能承载这些变体，就默认用子形态 A。只有当原型确实没有近旁可安身之处时，才去用子形态 B。

### 子形态 A：对既有页面的调整（首选）

路由已经存在。变体渲染在**同一个路由上**，由 `?variant=` URL 查询参数来把关。既有的数据获取、参数和鉴权全都保留。只有渲染部分被替换。这是默认选项；除非有明确理由不这么做，否则就选它。

如果原型针对的东西还没有页面，但*天然就该住在某个页面里*（仪表盘的新区块、设置页上的新卡片、既有流程里的新步骤），那它仍然属于子形态 A。把变体挂载在宿主页面里。

### 子形态 B：一个新页面（最后手段）

只有当被原型化的东西确实没有可安身的既有页面时（例如一个全新的顶层界面，或者一个无法合理嵌入任何地方的流程），才用它。

按项目已有的路由约定创建一个**一次性路由**。不要发明一套新的顶层结构。命名要让它明显是原型（例如在路径或文件名里带上 `prototype` 这个词）。同样的 `?variant=` 模式。

在决定采用子形态 B 之前，先做个常识检查：真的没有任何既有页面能把它嵌进去吗？一个空路由会掩盖掉那些页面一有内容就会暴露的设计问题。

两种子形态里，悬浮底栏是完全一样的。

## 流程

### 1. 写下问题并选定 N

默认 **3 个变体**。超过 5 个就不再是截然不同，而开始变成噪音，所以上限就卡在那。

用一行把计划写下来，放在原型所在位置，或者文件顶部的注释里：

> 「设置页的三个变体，通过 `?variant=` 切换，挂在既有的 `/settings` 路由上。」

无论用户是不是在场来提出异议，这都管用。

### 2. 生成截然不同的变体

起草每个变体。每个都要满足：

- 页面的用途，以及它能访问到的数据。
- 项目的组件库 / 样式体系（TailwindCSS、shadcn、MUI、纯 CSS，随便什么）。
- 一个清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须在**结构上不同**：不同的布局、不同的信息层级、不同的主要可供性（affordance），而不只是颜色不同。三个稍微改了改的卡片网格不是 UI 原型，是壁纸。如果两份草稿出来太像，就带着明确的「不要用卡片网格」指引重做其中一个。

### 3. 把它们接起来

在路由上创建一个单一的切换器组件：

```tsx
// 伪代码，按项目的框架调整
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对子形态 A（既有页面）：把所有既有的数据获取都保留在切换器上方；只有被渲染的子树随变体变化。

对子形态 B（新页面）：`/prototype/<name>` 下那个一次性路由挂载同一个切换器。

### 4. 构建悬浮切换器

一条小的固定定位横栏，位于屏幕底部居中，包含三个部分：

- **左箭头**：切到上一个变体（循环）。
- **变体标签**：显示当前变体的 key，如果该变体导出了名字，也显示那个名字。例如 `B (Sidebar layout)`。
- **右箭头**：向前切换（循环）。

行为：

- 点箭头会更新 URL 查询参数（用框架的路由器，例如 Next 上的 `router.replace`、React Router 上的 `navigate` 等），好让变体可分享、刷新后也稳定。
- 键盘：`←` 和 `→` 方向键也能切换。当 `<input>`、`<textarea>` 或 `[contenteditable]` 获得焦点时，不要拦截方向键。
- 在视觉上跟页面区分开（例如高对比度的胶囊样式、淡淡的阴影），好让它明显不属于正在被评估的设计。
- 在生产构建里隐藏：用 `process.env.NODE_ENV !== 'production'` 或等价检查来把关，这样一次误合并的原型不会把这个横栏发到用户那里。

把切换器放进一个单一的共享组件，好让两种子形态都能复用它。把它放在项目里存放共享 UI 的地方。

### 5. 交出去

把 URL（以及 `?variant=` 的各个 key）摆出来。用户有空时会翻着看。有意思的反馈通常是**「我想要 B 的 header 配 C 的侧边栏」**，那才是他们真正想要的设计。

### 6. 存档答案并清理

一旦某个变体胜出，就存档答案（哪个变体、为什么），然后按 [SKILL](../SKILL.md) 描述的方式存档原型。把胜出者并入真实代码，把其余的移到那个一次性分支上，而不是并进 main：

- **子形态 A**：把胜出者并入既有页面；从 main 上删掉落败的变体和切换器。
- **子形态 B**：把胜出的变体提升为一个真实路由；从 main 上删掉那个一次性路由和切换器。

整套变体是一手来源，所以它落到那个一次性分支上，而不是垃圾桶里，因为留在 main 分支上的变体组件和切换器会很快腐烂，让下一个读者困惑。

## 反模式

- **只在颜色或文案上不同的变体。** 那是微调，不是原型。真正的变体在结构上就有分歧。
- **变体之间共享太多代码。** 共享一个 `<Header>` 没问题；共享一个 `<Layout>` 就毁掉了意义。每个变体都应该能自由地扔掉布局。
- **把变体接到真实的写操作上。** 只读原型就挺好。如果一个变体需要写入，就把它指向一个桩（stub）：问题是「这东西应该长什么样」，而不是「后端能不能跑通」。
- **把原型直接提升到生产环境。** 变体代码是在原型的约束下写的（没测试、错误处理极少）。并入时要好好重写。
