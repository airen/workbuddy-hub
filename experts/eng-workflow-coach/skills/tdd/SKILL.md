# 测试驱动开发（TDD）

TDD 就是红 → 绿这个循环。本技能是让这个循环产出「值得留下的测试」的参考手册：什么样的测试是好测试、测试放在哪、有哪些反模式、循环的规则是什么。**每一节在每一个循环里都适用**：要在循环开始前和进行中查阅，而不是循环结束后才看。

探索代码库时，读一下 `GLOSSARY.md`（如果存在），让测试命名和接口用词与项目的领域语言保持一致；同时遵守你要触碰那块区域里的 ADR。

## 什么是好测试

测试验证的是**通过公开接口表现出来的行为**，而不是实现细节。代码可以整个换掉，测试不应该跟着改。一个好测试读起来像一份规格说明：「user can checkout with valid cart」明确告诉你存在什么能力，而且它能扛住重构，因为它不关心内部结构。

示例见 [tests.md](references/tests.md)，mock 的使用准则见 [mocking.md](references/mocking.md)。

## 接缝（seam）：测试写在哪

**接缝（seam）**是你在其上做测试的公开边界：一个让你能观察行为、又不必伸手进去的接口。测试只住在接缝上，绝不针对内部实现。

**只在事先约定好的接缝上写测试。** 写任何测试之前，先把要测的接缝写下来，并跟用户确认。**未确认的接缝上，一个测试都不写。** 你不可能什么都测，所以提前约定接缝，正是把测试精力落在关键路径和复杂逻辑上、而不是散到每个边界情况的原因。

要问：「公开接口是什么，我们该测哪些接缝？」

当这个接口的形态本身还有疑问时（模块该多深、接缝该放在哪、接口该暴露什么），调用 Skill 工具加载 `codebase-design` 技能来获取词汇。它是模块、接口、深度、接缝、适配器、杠杆、局部性这些术语的共同来源，是一份**供查阅的参考**，不是一个要跑起来的流程。

## 反模式

- **与实现耦合（Implementation-coupled）**：mock 内部协作者、测私有方法，或者通过旁路渠道验证（去查数据库而不是走接口）。识别特征：你重构了但行为没变，测试却挂了。
- **同义反复（Tautological）**：断言用跟代码一样的方式重算期望值（`expect(add(a, b)).toBe(a + b)`、手工按同样算法推出的快照、把一个常量断言成它自己），于是它天然通过，永远不可能跟代码产生分歧。期望值必须来自**独立的真相来源**：一个已知正确的字面量、一个算好的例子、或者规格说明。
- **横向切片（Horizontal slicing）**：先把所有测试写完，再写所有实现。批量测试验证的是**想象出来的**行为：你测的是事物的**形状**而不是面向用户的行为，测试会对真实变更变得不敏感，而且你在还没理解实现之前就把测试结构定死了。改用**垂直切片**：一个测试 → 一个实现 → 再来一遍，每个测试都是一发**曳光弹（tracer bullet）**，对上一轮循环教给你的东西作出反应。

## 循环的规则

- **红在绿前。** 先写失败的测试，再只写刚好能通过它的代码。不要预判未来的测试，也不要加投机性的功能。
- **一次一个切片。** 一个循环里：一个接缝、一个测试、一个最小实现。
- **重构不属于这个循环。** 它属于评审阶段（见 `code-review` 技能），不属于红 → 绿的实现循环。
