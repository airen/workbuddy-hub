# 三份报告解读指南

三份报告由同一份 `audit.json` 生成，数字互相一致，可交叉引用。

## PDF（给客户/上级）

结构（按出现顺序）：

1. **封面 + 摘要** —— 站点、日期、总体结论，第一眼看这份；
2. **计划（Plan）与流水线（Pipeline）** —— 审计是怎么跑的（爬取 → 规则 → Jev → PageSpeed → 评分），给「凭什么信」；
3. **记分卡（Scorecard）** —— 分区域得分。**只用于排整改顺序，不预测排名**；
4. **影响力 vs 努力矩阵** —— 整改排期的核心图：右上角（高影响低努力）先做；
5. **站点地图** —— 爬到的页面全景；
6. **排名 / 关键词机会 / Jev 卡片 / 质量热力图** —— `--full` 与 Jev 的判断细节；
7. **投资方向（Investment）** —— 按区域的整改投入建议；
8. **按区域分类的发现（Findings by area）** —— 每条发现带优先级与出处；
9. **页面清单 / 方法 / 来源** —— 每个 URL 的判断与全部引用来源。

## XLSX（执行者当进度表）

| 工作表 | 怎么用 |
|---|---|
| **Actions** | 主战场：每条整改项带**优先级、改法、官方出处**，状态列是下拉菜单，改完就改状态 |
| **Summary** | 从 Actions 实时计数，看完成度 |
| **Pages** | 每页明细 |
| **Technical / Performance** | 技术规则与 CWV 明细 |
| **Rankings / Opportunities / Competitors / SERPs / AI mentions** | `--full` 数据：排名、关键词机会、竞品、实时 SERP、AI 引用 |
| **带概率的原始 Jev 判断** | Jev 每问的保留概率答案；决定性区间外标 `to verify` |
| **Charts / Method** | 图表与方法说明 |

用法建议：把 Actions 原表当项目进度表用，别另起一张——保证「报告即事实来源」。

## Markdown（GitHub / Obsidian）

- 图表 + Mermaid 饼图 + 目录 + 尺寸化图片，直接在 GitHub/Obsidian 渲染；
- 适合进仓库/知识库做**历史快照**，跨版本对比审计变化。

## 解读纪律（三条硬规矩）

1. **分数只排序。** 分数变化 0.03 量级都可能是 Jev 的正常波动（实测同 59 页重跑平均差 ≤ 0.03），别过度解读单次波动；看趋势、看未解决项清零。
2. **`to verify` 不当结论用。** Jev 在决定性区间之外的答案一律标注，建议人工看 SERP 复核后再动手。
3. **启发式规则要注明。** 52 条里标「启发式」的是编辑惯例、非搜索引擎硬性要求，向客户解释时区分开，避免把建议说成「Google 要求」。

## 叙述校验（为什么报告里的数字可信）

jev-seo 的叙述层有自动校验：拒绝引用未知行动 ID、标记不在审计数据中的数字、标记不匹配的 effort 区间。所以报告里出现的每个数字都能追溯回审计数据——引用时可以直接用，但引用时仍写清出处（哪份报告哪个发现）。
