# 提示词工程与评测迭代工具包

把「我想要个能干活的东西」写成四段式系统提示词，再用评测证明改动真的变好。

## 何时用本技能

- 要把需求写成系统提示词、agent 人格、工具说明
- 要优化一条效果不稳定的提示词
- 要判断「改了提示词是不是真的变好」——设计评测集
- 要同一任务输出多种格式

不适用于：给已有产品写营销文案（那是内容团队的活）。

## 三个交付物（对应 references/）

| 文件 | 交付什么 | 什么时候读 |
|---|---|---|
| `references/system-prompt-template.md` | 系统提示词四段架构：角色定义 / 任务描述 / 约束条件 / 输出格式 | 写提示词时 |
| `references/design-principles.md` | 设计原则：安全合规、测试边界情况、可复现性 | 写之前 |
| `references/eval-and-iterate.md` | 评测与迭代：怎么证明变好了、版本管理与回滚 | 改完之后 |

## 工作流程

1. **定角色**：按模板第一段写清"你是谁"——身份、能力边界、不负责什么
2. **定任务**：第二段写"要做什么"——输入、处理步骤、输出物
3. **定约束**：第三段写"不能做什么"——安全红线、诚实要求、越界处理
4. **定格式**：第四段写"怎么回答"——结构、字段、长度、失败时输出什么
5. **建评测**：按 `eval-and-iterate.md` 搭一组能稳定复现的用例，记录基线分数
6. **迭代**：改提示词 → 跑评测 → 对比基线 → 保留或回滚；**没有评测不上线**

## 硬规则

- **改动必须可归因**：每次只改一处，跑评测对比；一次改多处等于没改（无法归因）
- **版本管理与回滚**：提示词变更要留记录，能回到上一个已知良好版本
- **测试边界情况**：好的提示词在异常输入、缺输入、冲突指令下也能合理处理
- **不写空泛人设**："你是一位资深专家"这种话不进提示词——换成具体的能力、流程和交付物
- **诚实优先**：提示词必须要求"不确定就说不确定"，禁止编造数据与结论
