# 05 · checklist（质量清单）

**命令**：`checklist`　**频率**：按需（质量关卡）　**产物**：`specs/NNN-slug/checklists/<类型>.md`

## 它是什么

> **这是"需求的单元测试"。**

它**不测代码**，测的是**规格本身**是否完整、清晰、无歧义、一致。

问的都是这类问题：

- 「每一列的拖拽规则都定义了吗？」
- 「被指派的用户被删除时，行为有定义吗？」
- 「空列表、超长文本、并发编辑，各有说法吗？」

## 关键语义（最容易搞错的地方）

| 标记 | 含义 |
|---|---|
| `[x]` | **评审人**确认「需求质量判据」已满足 |
| `[ ]` | 仍需澄清 / 修正 / 评审 |

> ⚠️ **`[x]` 不代表实现完成。** 它代表需求质量过关。这两件事必须分清楚 —— 混了就会出现"清单全绿但东西没做"的假象。

**归属**：自定义清单是**评审人拥有**的产物。Agent 可以在被明确要求时协助评估，但**实现过程绝不能自己给自己打勾**。`implement` 只**读**清单状态当关卡，**不允许改标记**。

## 与 `checklists/requirements.md` 的区别

| | `checklists/requirements.md` | `checklists/<自定义>.md` |
|---|---|---|
| 谁生成 | `specify` 内建创建，`clarify` 重新评估 | `checklist` 命令 |
| 生命周期 | 独立的、随规格一起演化的内建清单 | 一次性的评审产物 |
| 谁维护 | 规格流程自己维护 | 评审人 |

**不要把两者混用。**

## 执行步骤

1. **不带参数** → 出一份覆盖面广的清单。
2. **带焦点** → 只针对某个方面深挖：

```
/checklist Focus on the Kanban board interactions and comment permissions.
```

3. **组织方式**：按类别分组（如「交互一致性」「权限与边界」「错误处理」「非功能需求」），条目编号 `CHK001`、`CHK002`… 顺序递增便于引用。
4. **每条必须是一个可判定的判据**，不是感想。❌「拖拽体验要好」 ✅「每一列的拖拽落点行为都有明确定义」。

## 发现缺口怎么办

**回环到 `specify` 或 `clarify` 把规格补好**，再往下走 —— 不要在任务拆解或实现里去补需求。

## 收尾

告诉用户：清单文件路径、几个类别、几条判据、**发现了几处规格缺口**（这是这一步的真正价值）、建议回哪一步补。
