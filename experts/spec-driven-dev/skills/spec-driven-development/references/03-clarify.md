# 03 · clarify（澄清）

**命令**：`clarify`　**频率**：`plan` 之前，可重复多次　**产物**：更新 `spec.md`（回写答案）+ 更新 `checklists/requirements.md`

## 它解决什么问题

> **在模糊之上做设计，是最大的浪费。**

`clarify` 的唯一职责：把规格里**说不清的地方**问出来，并把答案**编码回 `spec.md`**。它不改需求，只把需求变清楚。

## 执行步骤

### 1. 扫描规格，找出欠定义区域

优先扫这几类：

- 残留的 `[NEEDS CLARIFICATION]` 标记
- 一句话里塞了多个动作的验收场景
- 有名词但没有行为定义的实体（"任务卡"是什么？能改状态吗？谁能改？）
- 边界没说的交互（删掉被指派的用户会怎样？空列表显示什么？）
- 权限 / 配额 / 上限 / 超时 —— 凡是"数量"的地方

### 2. 一次最多问 5 个

**这是硬上限。** 一次问 30 个问题等于没问 —— 用户会挑几个答，剩下的变成新的模糊。

每个问题必须：
- **有明确的备选答案**（"邮箱密码 / SSO / OAuth？"），不要问"你希望怎么认证？"
- **指向规格里的具体位置**（哪条 FR / 哪个用户故事）
- **问完就能改规格**，不是"再想想"

### 3. 用户答完，回写规格

- 答案填进对应的 `FR-xxx` / 验收场景 / 实体定义
- **删掉对应的 `[NEEDS CLARIFICATION]` 标记**
- 如果答案暴露了新的需求，加新的 `FR-xxx` 编号（不要复用旧号）
- 同步更新 `checklists/requirements.md` 的评估状态

### 4. 需要就再来一轮

每轮盯**不同的区域**。用户也可以直接指定焦点：

```
/clarify Focus on the task card behavior: status changes, comment limits, and who can be assigned.
```

## 什么时候可以停

- 规格里没有遗留的 `[NEEDS CLARIFICATION]`
- 每个验收场景都能被一个不参与讨论的人**照着测**
- 没有"这个要看情况"级别的悬空描述

## 与 `analyze` 的回环

如果之后 `analyze` 报出了需求缺口 → **回到 `clarify`（或 `specify`）** 把源头改掉，然后重跑 `analyze`。不要在 `plan` 或实现里绕过缺口。

## 收尾

告诉用户：这一轮问了几个问题、改动了规格的哪几处、还剩几个待澄清项、能不能进 `plan` 了。
