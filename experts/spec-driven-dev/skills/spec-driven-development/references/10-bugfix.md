# 10 · Bug 修复（assess → fix → test）

**入口**：独立于 SDD。修 bug **不需要**先走 SDD 全流程。
**产物**：`.specify/bugs/<slug>/` 下的 `assessment.md`、`fix.md`、`verification.md`

## 为什么拆成三步

> **把诊断、修复、验证严格分开。**

因为 AI 最常见的失败模式是：**看到一个症状，立刻改了一处代码，然后宣布修好了** —— 改的是它以为的原因，而不是真正的原因；而且它从来不复验原始症状。

三步分离强制：先**评估出因果**，再**在限定范围内修复**，最后**回到原始症状去验证**。

## 三步

### 1. `bug-assess` —— 诊断

**输入**：症状描述 + 一个 slug。

```
/bug-assess "Submitting an empty password crashes the login form." slug=login-crash
```

产出 `assessment.md`，必须包含：

- **可复现步骤**（最小复现）
- **观察到的行为 vs 期望行为**
- **根因假设**，以及**支撑它的证据**（哪段代码、哪条日志、哪次实验）
- **影响范围**（哪些功能受牵连）
- **修复范围建议**（改哪些文件，明确不改哪些）

⚠️ **不许在这一步改代码。** 诊断阶段只产出假设和证据。

### 2. `bug-fix` —— 修复

```
/bug-fix slug=login-crash
```

- **只针对 `assessment.md` 里评估出的原因**动手
- **严格限制在建议的范围内** —— 顺手重构、顺手改风格，一律禁止
- 如果修复过程中发现根因判断错了 → **回到 assess 重来**，不要在 fix 里改诊断
- 产出 `fix.md`：改了什么、为什么这么改、有没有偏离评估结论

### 3. `bug-test` —— 验证

```
/bug-test slug=login-crash
```

**回到最初报告的症状**去验证，而不是验证"我改的那段代码看起来对"：

- 原始复现步骤现在还会不会触发问题？
- 有没有引入回归？
- 产出 `verification.md`

## 最终判定（三选一，不许含糊）

| 判定 | 含义 |
|---|---|
| **`verified`** | 原始症状已复现不出来，且回归检查通过 |
| **`partial`** | 部分修复：主症状消失但相关场景仍异常，或只覆盖了部分复现路径 |
| **`failed`** | 没修好，或根因判断错误 |

> **缺失的验证不是成功的修复。** 没跑过验证就报 `verified` 是最严重的错误。

## 收尾

告诉用户：判定结果、证据（跑了什么、看到什么）、改了哪些文件、有没有回归风险。
