# 07 · analyze（一致性校验）

**命令**：`analyze`　**频率**：`tasks` 之后、`implement` 之前（质量关卡）；实现后也可再跑一次　**产物**：**只读报告**（不写文件）

## 核心特性

> **它是只读的。它绝不编辑任何文件。**

它交叉检查 `spec.md`、`plan.md`、`tasks.md` 三者，报告**冲突、缺口、歧义**。它可以**建议**修复方案，但要用户批准才执行。

## 找什么

| 类型 | 例子 |
|---|---|
| **孤儿任务** | 某个任务找不到对应的需求 |
| **孤儿需求** | 某条 FR 没有任何任务覆盖它 |
| **方案与规格冲突** | `plan.md` 的技术选择与 `spec.md` 的约束矛盾 |
| **章程违规** | 方案违反了章程条款且没进复杂度追踪表 |
| **验收覆盖缺口** | 某个验收场景没有对应测试任务 |
| **歧义** | 同一概念在 spec / plan 里说法不一致 |
| **任务依赖错误** | `[P]` 标记的任务实际有依赖，或依赖成环 |

## 严重度分级

报告先给**分级摘要**：`CRITICAL` / `HIGH` / `MEDIUM` / `LOW`。

- 与章程里的 **MUST** 冲突 → `CRITICAL`
- 需求无覆盖 / 任务无来源 → `HIGH`
- 术语不一致 / 描述模糊 → `MEDIUM`
- 措辞与格式问题 → `LOW`

## 发现问题后怎么办（关键）

**回到拥有它的那一步去改源头**，不要在实现里绕过：

| 问题类型 | 回到哪一步 |
|---|---|
| 需求缺口、需求歧义 | `specify` 或 `clarify` |
| 设计冲突、技术选型矛盾 | `plan` |
| 任务拆分/排序/依赖问题 | `tasks`（重新生成） |

改完 → **重跑 `analyze`** → 直到报告干净。

## 时机

- **实现前**：最重要。此时改文档的代价几乎为零。
- **实现后**：可作为额外审查，检查实现有没有偏离规格。

## 收尾

告诉用户：发现几处问题、分级分布、每处的**责任归属**（该回哪一步）、以及"现在能不能进 `implement`"的明确结论。

> ⚠️ 不要在 `analyze` 里顺手把文件改了。用户问"你改了没"，答案必须永远是"没有"。
