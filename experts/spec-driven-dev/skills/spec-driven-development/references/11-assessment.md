# 11 · 想法评估（intake → research → define → shape → decide）

**入口**：独立于 SDD。**在没有一行代码的项目里也能跑**（甚至不需要项目）。
**产物**：`.specify/assessments/<slug>/` 下的五个文件，最终落到一个决策

## 它解决什么问题

> **在投入之前收集证据。**

用户说"我想做个 X"，你的第一反应不该是"好，那我们来写规格"，而是"**这个 X 值不值得做？**"。

这个流程的产出是一个有证据支撑的决策：**go / needs-clarification / kill**。

**注意：停下来也是一个有价值的结果。** 带着文档化的理由停掉一个坏想法，和做出一个好功能一样值钱。

## 五步

### 1. `assess-intake` —— 收集原始意图

```
/assess-intake "Let users work offline and sync when they reconnect." slug=offline-mode
```

产出 `intake.md`：想解决什么问题、为谁解决、成功长什么样、有哪些已知约束。**这一阶段不评判，只记录。**

### 2. `assess-research` —— 调研证据

产出 `research.md`：

- 已有方案 / 竞品怎么做的
- 技术可行性（难点在哪、有没有先例）
- 成本量级（工作量、依赖、维护负担）
- 风险与未知项

**结论必须有来源。** 凭印象写的"业界普遍认为"不算证据。

### 3. `assess-define` —— 定义问题边界

产出 `definition.md`：把模糊意图收敛成**可判定**的问题陈述。什么在范围内、什么明确不在。

### 4. `assess-shape` —— 成型可选方案

产出 `shape.md`：2–3 个可选形态，各自的**代价与收益**，以及**如果要做，最小可行版本是什么**。

### 5. `assess-decide` —— 决策

产出 `decision.md`，落到三者之一：

| 决策 | 含义 |
|---|---|
| **`go`** | 证据支持投入。可以交给 `specify` 开始 SDD。 |
| **`needs-clarification`** | 证据不足，缺的是具体哪一项（写清楚）。 |
| **`kill`** | 不值得做。**必须写明理由**，理由要能被人复核。 |

## 迭代方式

**直接改已有的 Markdown 产物**（或让 agent 改），**不要重新生成整个阶段**。评估是渐进收敛的，不是流水线重跑。

## 与 SDD 的衔接

`go` 决策**可以**交给 `specify` —— 但**不是自动的**，由用户决定要不要真的开建。

## 收尾

告诉用户：决策是什么、支撑它的关键证据、以及（如果是 `go`）建议的下一步。
