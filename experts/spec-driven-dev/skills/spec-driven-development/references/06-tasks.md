# 06 · tasks（任务拆解）

**命令**：`tasks`　**频率**：每个功能一次　**产物**：`specs/NNN-slug/tasks.md`

## 输入

必需：`plan.md`、`spec.md`（用户故事来自这里）
若存在则一并读：`data-model.md`、`contracts/`、`research.md`

## 输出结构（固定）

```
Phase 1: Setup                —— 项目初始化、基础结构
Phase 2: Foundational         —— 阻塞性前置（⚠️ 不完成，任何用户故事都不能开始）
Phase 3: User Story 1 (P1) 🎯 MVP
Phase 4: User Story 2 (P2)
Phase 5: User Story 3 (P3)
...
Phase N: Polish & Cross-Cutting —— 文档、重构、性能、安全加固
```

**每个用户故事一个阶段**，按优先级排序。用户故事内部，测试任务（如果要做）**写在该故事阶段内**，不单独成阶段。

## 任务格式（严格）

```
[ID] [P?] [Story] Description
```

- **ID**：`T001`、`T002`… 全局连续编号
- **`[P]`**：可并行（不同文件、无依赖）
- **`[Story]`**：`[US1]` / `[US2]`… 归属哪个用户故事
- **描述里必须有确切文件路径**

示例：

```
- [ ] T012 [P] [US1] Create Album model in src/models/album.py
- [ ] T014 [US1] Implement AlbumService in src/services/album_service.py (depends on T012, T013)
```

## 任务派生规则

| 来源 | 派生成 |
|---|---|
| `contracts/` 里的契约 | 契约测试任务（`[P]`） |
| 验收场景 | 集成 / e2e 测试任务 |
| `data-model.md` 里的实体 | 模型创建任务（`[P]`） |
| 服务 / 端点 | 实现任务（带依赖） |

## 并行机会（要标出来）

- Setup 阶段所有 `[P]` 任务可并行
- Foundational 阶段内的 `[P]` 任务可并行
- Foundational 完成后，**所有用户故事可并行**（如果有人力）
- 同一用户故事内的 `[P]` 测试、`[P]` 模型可并行

## 阶段依赖（写进文件里）

- **Setup**：无依赖，可立即开始
- **Foundational**：依赖 Setup；**阻塞所有用户故事**
- **User Stories**：都依赖 Foundational；然后可并行或按 P1→P2→P3 顺序
- **Polish**：依赖所有目标用户故事完成

**用户故事之间不允许有破坏独立性的依赖** —— 可以有"与 US1 集成"这种软依赖，但每个故事仍必须能独立测试。

## 铁律

1. **每个任务必须可追溯到需求。** 追溯到 FR-xxx / 用户故事 / 契约的，留；追不到的，删。
2. **禁止投机性任务**：没有 "might need"、"将来可能"。这类任务一律砍掉。
3. **禁止模糊任务**：❌「完善错误处理」 ✅「为 US1 的创建接口加 400/409 错误分支处理」。
4. **禁止同文件冲突**：标了 `[P]` 的任务不能改同一个文件。
5. **测试可选**：只有当规格里明确要求测试时才生成测试任务。别默认加。
6. **实现顺序**（每个故事内）：测试先失败 → 模型 → 服务 → 端点 → 集成 → 收尾。

## 模板里的示例任务是占位符

`templates/tasks-template.md` 里的任务**只是示例**。生成的 `tasks.md` 里**必须**替换成基于本功能真实需求的任务，**不能留着示例**。

## 收尾

告诉用户：任务总数、几个阶段、多少个 `[P]` 可并行、MVP 边界在哪（哪几个阶段做完就能交付）、下一步建议跑 `analyze`。
