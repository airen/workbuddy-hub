# 00 · SDD 方法论（为什么这套东西成立）

> 译写自 GitHub Spec Kit 上游 `spec-driven.md`（MIT）。保留原论证结构，术语不简化。

## 一、核心哲学：权力倒置

传统开发中「代码为王」，规格说明书只是服务代码的脚手架，用完即弃。SDD 彻底颠倒这个结构：

> **规格不为代码服务 —— 代码为规格服务。**
> *Specifications don't serve code — code serves specifications.*

- PRD 不再是"实现的指南"，而是**生成实现的源头**（the source that generates implementation）。
- 技术方案不再是"指导编码的文档"，而是**精确产生代码的定义**。
- 这不是渐进式改进，而是对「什么驱动开发」的根本性反思。

### 规格—实现鸿沟是怎么被消除的

传统方法想用「更好的文档、更详细的需求、更严格的流程」去**弥合**鸿沟 —— 但它们默认鸿沟不可避免，所以注定失败。

SDD 的做法是让规格与实现计划**可执行**（executable）：

> **当规格与实现计划生成代码时，没有鸿沟 —— 只有转化。**
> *When specifications and implementation plans generate code, there is no gap — only transformation.*

**为什么现在才可行**：AI 已经能理解并实现复杂规格。但**裸 AI 生成会产生混乱**（raw AI generation without structure produces chaos）；SDD 用精确、完整、无歧义的规格与实现计划提供结构。规格成为**首要工件**（primary artifact），代码是它在特定语言与框架中的**表达**（expression）。

**开发语言层级上移**：团队的"通用语言"（lingua franca）上移到自然语言层，代码退化为"最后一公里"。这被称为**意图驱动开发**（intent-driven development）。

## 二、六条核心原则

1. **规格即通用语言**：规格是首要工件，代码是其表达。维护软件 = 演化规格。
2. **可执行规格**：规格必须精确、完整、无歧义，足以生成可运行系统。
3. **持续精炼**：一致性验证持续进行，不是一次性关口。AI 持续分析规格中的歧义、矛盾与缺口。
4. **研究驱动的上下文**：研究代理在规格化过程中收集关键技术背景 —— 技术方案、性能影响、组织约束。
5. **双向反馈**：生产现实反哺规格演化 —— 指标、事故、运营经验成为规格精炼的输入。
6. **分支探索**：从同一规格生成多个实现方案，探索不同优化目标（性能 / 可维护性 / 体验 / 成本）。

## 三、模板纪律：结构如何约束 LLM

> 命令的真正力量不只在自动化，更在于**模板引导 LLM 走向更高质量的规格**。模板是精密提示词，以生产性的方式约束输出。
>
> **模板把 LLM 从"创造性写作者"转变为"有纪律的规格工程师"。**
> *The templates transform the LLM from a creative writer into a disciplined specification engineer.*

七种约束机制：

1. **防止过早的实现细节** —— 模板明确要求聚焦 WHAT（用户需要什么）与 WHY（为什么），避免 HOW（技术栈、API、代码结构）。
   - ✅ Focus on WHAT users need and WHY
   - ❌ Avoid HOW to implement
2. **强制显式的不确定性标记** —— 强制 `[NEEDS CLARIFICATION]`，禁止猜测。不猜"登录用邮箱密码"，而是标记 `[NEEDS CLARIFICATION: auth method not specified]`。
3. **通过清单进行结构化思考** —— 清单充当规格的"单元测试"，迫使 LLM 系统性自审（无遗留待澄清标记、需求可测试且无歧义、成功标准可衡量）。
4. **通过关口的章程合规** —— 实现计划模板用阶段关口强制架构原则（如"简洁关口"要求 ≤3 个项目、"反抽象关口"要求直接使用框架）。关口失败必须进「复杂度追踪」并写明理由，形成问责。
5. **层级化细节管理** —— 实现计划保持高层可读；代码样例与详细算法下沉到 `implementation-details/` 文件。
6. **测试优先思维** —— 强制文件创建顺序：先 `contracts/`，再按 契约 → 集成 → e2e → 单元 的顺序创建测试，最后创建源码让测试通过。
7. **防止投机性功能** —— 明确禁止 "might need" 功能，每个功能都必须追溯到有明确验收标准的具体用户故事。

## 四、章程基础：把架构纪律变成关卡

章程（`.specify/memory/constitution.md`）是治理「规格如何变成代码」的原则集，相当于系统的**架构 DNA**。

### 九条开发条款（经典版）

| 条款 | 名称 | 要求 |
|---|---|---|
| I | **库优先**（Library-First） | 每个功能必须作为独立库诞生，无一例外。强制模块化。 |
| II | **CLI 接口强制**（CLI Interface Mandate） | 每个库必须通过命令行接口暴露功能 —— 文本输入、文本输出、支持 JSON 结构化交换。强制可观测性与可测试性。 |
| III | **测试优先强制**（Test-First Imperative） | **不可协商**：任何实现代码之前，必须先写单元测试、测试经用户验证批准、确认测试失败（红阶段）。 |
| IV–VI | **项目自定义治理** | 由各项目章程自行定义（集成测试、可观测性、版本化、破坏性变更等）。`analyze` 会评估项目自己的章程，所以这些自定义条款与内建条款一样参与合规检查。 |
| VII–VIII | **简洁性与反抽象**（Simplicity & Anti-Abstraction） | 对抗过度工程。初始实现最多 3 个项目，额外项目需文档化理由；直接使用框架特性，不要包裹它们。 |
| IX | **集成优先测试**（Integration-First Testing） | 优先真实环境测试 —— 真实数据库而非 mock、真实服务实例而非桩、实现前强制契约测试。 |

**执行机制**：实现计划模板通过 `Phase -1: Pre-Implementation Gates` 把条款操作化 —— 这些关口是**架构原则的编译期检查**，LLM 必须通过，或把例外写进「复杂度追踪」。

**为什么不可变原则有力**：
- 跨时间一致性：今天的代码遵循与明年相同的原则
- 跨 LLM 一致性：不同 AI 模型产出架构兼容的代码
- 架构完整性：每个功能强化而非削弱系统设计

> **章程把 AI 从"代码生成器"转变为"架构伙伴"。**
> *The constitution transforms AI from a code generator into an architectural partner.*

原则不可变，应用可演化。修订需要：文档化理由 + 维护者评审批准 + 向后兼容性评估，并带日期记录。

## 五、与"凭提示词祈祷"的关键差异

| 维度 | 裸 AI 生成 / 提示词驱动 | SDD |
|---|---|---|
| **结构** | 无结构产生混乱 | 精确、完整、无歧义的规格 + 实现计划提供结构 |
| **首要工件** | 代码 | 规格（代码是其表达） |
| **不确定性处理** | LLM 常做"看似合理但可能错误"的假设 | 强制 `[NEEDS CLARIFICATION]`，禁止猜测 |
| **抽象层级** | 直接跳到"用 React + Redux 实现" | 强制聚焦 WHAT/WHY，避免 HOW |
| **质量保障** | 生成代码后希望它能工作 | 测试优先：先写测试 → 批准 → 确认失败 → 再实现 |
| **架构约束** | 易过度工程 | 章程九条款 + 关口强制简洁与反抽象 |
| **一致性** | 一次性生成，无持续验证 | 持续精炼，非一次性关口 |
| **需求变化** | 视为障碍 | 视为正常流程，系统性再生 |
| **文档角色** | 静态、易过时 | 活文档 —— 因为规格生成代码 |

**一句话**：SDD 用**可执行规格 + 章程约束 + 模板纪律**驯服裸 AI 生成的混乱，使 AI 从"创造性地生成代码"转变为"有纪律地生成可运行、可测试、架构一致的实现"。

## 六、效率对比（上游给的实例）

构建一个聊天功能：

| | 传统方式 | SDD 命令方式 |
|---|---|---|
| 产出 | PRD 2–3h + 设计文档 2–3h + 项目结构 30min + 技术规格 3–4h + 测试计划 2h | 完整功能规格 + 详细实现计划 + API 契约与数据模型 + 综合测试场景，全部在功能分支中版本化 |
| 耗时 | **约 12 小时** | **约 15 分钟**（之后需人工评审与精炼） |

结构化自动化的四个收益：**无遗忘细节**（模板保证从非功能需求到错误处理都被考虑）、**可追溯决策**（每个技术选择链回具体需求）、**活的文档**（规格生成代码所以不会过时）、**快速迭代**（改需求后分钟级而非天级重新生成计划）。

## 七、值得记住的引语

> 「规格不为代码服务 —— 代码为规格服务。」

> 「当规格与实现计划生成代码时，没有鸿沟 —— 只有转化。」

> 「规格成为首要工件。代码成为它在特定语言和框架中的表达。」

> 「这是不可协商的：所有实现必须遵循严格的测试驱动开发。」

> 「章程把 AI 从代码生成器转变为尊重并强化系统设计的架构伙伴。」

> 「模板把 LLM 从创造性写作者转变为有纪律的规格工程师。」

> 「SDD 提供实现这种对齐的方法论 —— 通过**生成**代码而非仅仅**指导**代码的可执行规格。」
