# 交互式网页工具

通过自然语言描述需求，做出能用的仪表盘、计算器和其他网页工具。

> 交付标准是「能打开、能算、不出错」，不是「看起来像」。

## 适用场景

- 计算器 / 换算器 / 估算表
- 数据仪表盘与看板
- 单文件离线工作台（要长期填、数据不能丢）
- 需要交互的原型或演示页

## 输入

- 工具要做什么（输入什么、输出什么）
- 计算逻辑与公式（必须明确，不能靠猜）
- 数据：初始数据、是否需要持久化
- 运行环境：单文件离线 / 有后端 / 嵌到现有页面

## 执行步骤

### 步骤 1 — 先确认计算逻辑

把每一条公式或规则明确写下来，并让用户确认。**公式错了，界面再漂亮也没用。**

规则复杂的，先用一个具体数值手算一遍，把过程写进说明里作为验收依据。

### 步骤 2 — 定形态

| 需求 | 形态 |
|---|---|
| 一次性的换算 / 计算 | 单页，输入 → 输出 |
| 要长期填、要保存数据 | 单文件 + 本地存储 |
| 看数据、要图表 | 仪表盘，注意数据量与渲染方式 |
| 多人共用 / 要跨设备 | 需要后端，单文件撑不住 |

**单文件撑不住时直说**，不要硬塞。

### 步骤 3 — 搭结构

- 输入区（表单 / 上传 / 选择）
- 计算区（逻辑与状态）
- 输出区（结果、图表、导出）
- 说明区（公式、口径、限制）

另外两件必做：

- **输出一律编码后再渲染**：任何用户输入、URL 查询参数、远端数据写进页面时，用 `textContent` 或框架默认转义，**不用 `innerHTML` 拼接字符串**。确需富文本时先用白名单消毒器处理，再把结果插入 DOM
- 单文件页面默认加 CSP，并按页面的实际加载方式调整：内联脚本 / 样式的单文件工作台用 `<meta http-equiv="Content-Security-Policy" content="default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src 'self' data:; connect-src 'self'; object-src 'none'; base-uri 'none'">`；若已拆成外部文件则收严为 `script-src 'self'`。**加了 CSP 之后必须再按步骤 5 真的在浏览器里点一遍**，确认功能没被自己的安全策略挡住

### 步骤 4 — 处理边界与错误

必须处理：

- 空输入、非法字符、超出范围
- 除零、负数、精度与舍入
- 大数据量下的性能（表格虚拟化、图表采样）
- 本地存储失败或被禁用
- **本地存储的内容边界**：localStorage / IndexedDB 只放**非敏感的填报数据**，且每条 key 加统一前缀便于清理。**不放**凭据、令牌、API Key、个人敏感信息——它是明文、同域任意脚本可读、且无限期留存。确需保存敏感数据就只能上后端
- **有后端就必须有归属校验**：多人共用场景一旦上后端，每个读写请求都要校验「当前用户是否有权访问这条数据」，不能只校验登录态；并提供明确的导出与删除路径

每个错误都要给出**用户能看懂的提示**，不是控制台报错。

### 步骤 5 — 自测

打开页面，用这些输入验一遍：

1. 正常值 → 结果正确（对照步骤 1 手算的结果）
2. 边界值 → 不崩、有提示
3. 非法输入 → 有提示、不丢已填数据
4. 刷新页面 → 数据按预期保留或清空

**没在浏览器里真的点一遍，不算完成。**

### 步骤 6 — 说明与交付

在页面上写明：公式口径、数据来源、精度处理、已知限制。交付时给出文件打开方式。

## 输出

- 可运行的页面文件
- 公式与口径说明（写在页面上）
- 自测记录（测了哪些输入、结果如何）
- 已知限制

## 反模式

- **公式靠猜**：算错了没人会发现，直到有人拿它做决策
- **不做边界处理**：一个空输入就让页面白屏
- **只在代码层面检查，不真的点一遍**：运行时错误只有打开才发现
- **单文件硬塞多人协作需求**：该有后端时要有后端
- **不写口径说明**：用户不知道结果是怎么算出来的
- **图表塞一万条数据不采样**：页面卡死
