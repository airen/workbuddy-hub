# 测试驱动开发

先写一个会失败的测试，再写最少的代码让它通过，最后在测试保护下整理代码。

> 没有先变红的测试，就无法证明修好了任何东西。

## 适用场景

- 开发新功能
- 修复 Bug（先补一个能复现它的测试）
- 重构前需要安全网
- 行为不明确，需要用测试把行为钉死

## 输入

- 要实现的单一行为（一句话说清"输入什么、期望什么"）
- 现有测试的位置与运行方式
- 被测模块的入口（真实入口，不是为测试造的后门）

## 执行步骤

### 步骤 1 — 挑一个最小行为

不要挑"实现整个功能"。挑一个**单独可验证**的行为：

```
这次只做：输入为空数组时，返回空列表而不是报错
```

判断标准：这个行为能在 10 行测试内表达清楚。说不清就再切小。

### 步骤 2 — 写测试，跑一次确认它红

```js
test('空输入返回空列表', () => {
  expect(flatten([])).toEqual([]);
});
```

跑测试，**看到它失败**。失败原因应该是"功能不存在 / 行为不对"，而不是"语法错"或"import 路径错"——后者说明测试本身没写对。

一个测试只断言一个行为。塞五个断言进去，失败时你不知道是哪个坏了。

### 步骤 3 — 写最少的代码让它绿

只写让这个测试通过的**最少**代码。允许这一步代码很难看：硬编码返回值、不做错误处理、有重复——都行。

禁止在这一步做：顺手重构、提前加参数、考虑"以后可能要支持 X"。

### 步骤 4 — 重构（仅在绿灯下）

测试通过后才整理：去重、改名、抽函数、收敛分支。

**每改一次跑一次测试。**改完不跑，等于把安全网解开走钢丝。

### 步骤 5 — 回到步骤 1

一个行为做完，挑下一个。每轮循环控制在几分钟内。

### 步骤 6 — 提交粒度

每完成一个有意义的行为就提交一次，提交说明按 Conventional Commits 写。让每次提交都能被单独读懂和回滚。

## 输出

- 一组失败转通过的测试
- 最小实现 + 重构后的代码
- 可展示的测试运行输出（红 → 绿）

## 反模式

- **先写实现再补测试**：补的测试只会验证已写的代码，不会发现设计问题
- **测试没先跑红**：可能它本来就会通过，那它什么都没证明
- **一次写十个测试**：全红之后无法定位，等于没有反馈
- **为了好测改设计**：允许为可测性做**小**调整，但降低封装、开后门式的改法是设计倒退
- **红灯下重构**：没有测试保护的重构是在赌
- **一个测试断言一堆事**：失败时无法定位
- **测试依赖真实外部服务**：让测试变慢且不稳定，用替身

## 参考

- Bug 修复同样走这套循环：先补一个复现该 Bug 的测试，再修。
- 排错场景配合 `systematic-debugging`：它负责定位根因，本技能负责把修复钉死在测试上。
