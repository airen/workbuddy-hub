# PRD 拆任务

把一份需求拆成可以分别领取的任务，每个任务都有明确范围，并说明哪些必须先完成、哪些可以独立推进。

## 适用场景

- 实施计划已定，要交给多人 / 多 Agent 并行推进
- 需要判断哪些任务能并行、哪些被阻塞
- 想让每个任务都能被单独验收和回滚
- 需求很大，需要一个能逐项打勾的清单

## 输入

- PRD 与实施计划（阶段划分、每阶段产出）
- 可用人力 / 并行度
- 现有仓库的模块归属（便于按模块归类）

## 执行步骤

### 步骤 1 — 按功能模块归类

先按模块把工作分组（数据层 / 接口层 / 界面层 / 配置 / 文档），再在组内拆粒度。**跨模块的任务要拆开**——一个任务横跨三层，谁都不好领。

### 步骤 2 — 控制单任务粒度

判断标准：

| 太大 | 合适 | 太小 |
|---|---|---|
| "实现用户系统" | "新增用户表的迁移脚本与回滚脚本" | "改一个字段名" |
| 一天做不完 | 半小时到半天可完成，能单独提 PR | 单独提 PR 不值当 |
| 无法描述完成判据 | 有一两条可验证的验收标准 | 只是某个任务的一行 |

例外：探索性任务（"调研 X 方案可行性"）可以大，但必须有明确的时间盒和产出物。

### 步骤 3 — 标依赖关系

每个任务显式写出：

- **阻塞于**：必须先完成哪些任务
- **阻塞**：哪些任务在等它
- **可并行**：与哪些任务互不干扰

依赖标错比不标更糟：不标大家会自己问，标错了会有人白等。

### 步骤 4 — 每个任务写五项

```
### <模块前缀> <任务名>
范围：做什么（一句话）
不做什么：边界在哪
验收标准：怎么确认做完了（可验证）
依赖：阻塞于 #x，阻塞 #y
备注：需要注意的坑或参考实现
```

### 步骤 5 — 排出可并行批次

按依赖把任务分批：第一批能同时开工的、第二批、第三批。让领取的人一眼看出"现在我该拿哪个"。

### 步骤 6 — 标出关键路径

依赖链最长的那条路径单独标出。它就是整个需求的最短工期，任何一处延误都会顺延整体。

## 输出格式

```
# 任务清单：<功能名>

## 批次 1（可立即并行）
### #1 <模块> 任务名（范围 / 不做 / 验收 / 依赖）
### #2 …
## 批次 2（依赖批次 1 的 #1）
## 关键路径：#1 → #4 → #7
## 未纳入本次的任务（及原因）
```

## 反模式

- **任务粒度过大**："实现支付模块"不是任务，是一个项目
- **不写"不做什么"**：领取的人会自行扩张范围
- **验收标准不可验证**：做完没做完全凭感觉
- **依赖全标成串行**：本来能并行的被人为阻塞，工期翻倍
- **不标关键路径**：不知道该优先保障哪条链
- **拆完不留缓冲**：探索性任务必然有意外，清单里要给它留位置

## 参考

- 与 `prd-to-plan` 的分工：它负责**阶段与顺序**，本技能负责**拆成可分别领取的任务**。两者配合使用。
