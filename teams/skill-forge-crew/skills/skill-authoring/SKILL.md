# 技能锻造

把「每次都要重新交代一遍」的工作，变成一个文件夹。

## 适用场景

- 同一套动作做到第三次（需求澄清、发布检查、数据整理……）
- 某类任务每次都要重复解释同一批约束和标准
- 已有的 Skill 在特定步骤反复出错，需要按真实失败点改指令
- 已有一份草稿，需要整理成规范结构（入口文件放什么、深度资料怎么分层）

## 输入

- 这套工作的**真实执行记录**（做过几次、每次卡在哪、有哪些例外）
- 期望的输出形态（文件 / 报告 / 代码改动 / 对话结论）
- 已有的约束（不能碰什么、必须过什么检查）

> 没有真实执行记录就先做 2～3 次再写。凭想象写出来的 Skill，第一次用就会散架。

## 执行步骤

### 步骤 1 — 用要点列出步骤（不要写长句）

先把流程写成 5～12 条要点，每条一个动作。例：

```
1. 读状态文件，判断是新建还是续跑
2. 只问会改变方向的问题，最多 3 个
3. 产出简报卡，停下等确认
4. 按平台分别改写，不共享正文
```

这一步的目标是把隐性经验显性化。**写不出来的步骤，说明你自己也没想清楚。**

### 步骤 2 — 起草 SKILL.md

frontmatter 至少写全四项：`name`（kebab-case，与目录名一致）、`description`（一句话说清解决什么问题 + 何时触发）、`version`、`category`。

正文按这个骨架写：

| 章节 | 写什么 |
|---|---|
| 适用场景 | 什么时候该用它，附触发词 |
| 输入 | 需要什么材料，缺什么就先问 |
| 执行步骤 | 编号步骤，每步有明确产出 |
| 输出 | 交付什么，长什么样 |
| 反模式 | 这一步最容易犯的错 |
| 参考 | `references/` 里还有什么可以深读 |

写 `description` 的技巧：把「用户会怎么说这句话」写进去。触发靠的是这句话匹配用户意图，不是靠标题漂亮。

### 步骤 3 — 拿 3～5 个真实任务试跑

挑**难度递增**的真实任务，不要挑三个一样的：

1. 最典型的那个（验证主路径）
2. 最边界的那个（验证异常处理）
3. 最不典型但真实发生过的（验证泛化能力）

每个任务跑完记录：**哪里没做好、当时缺什么信息、指令被理解成了什么。**

### 步骤 4 — 按失败点改指令

改指令，不是加指令。常见三类失败：

| 失败类型 | 症状 | 改法 |
|---|---|---|
| 步骤太粗 | 每次执行结果都不一样 | 把这一步拆成 2～3 个子步骤，写明判断依据 |
| 约束没写 | 输出格式每次不同 | 在对应步骤里写明「必须 / 禁止」，而不是放在开头 |
| 缺判断分支 | 遇到某种输入就乱走 | 加一个路由表：什么情况走哪条路 |

改完重跑失败的那个任务，确认它变好了。**只改不验证等于没改。**

### 步骤 5 — 整理结构

- 入口 `SKILL.md` 只放**每次都要读**的内容，控制在 200 行以内
- 深度资料放 `references/`，用到时再读
- 可执行脚本放 `scripts/`，静态资源和模板放 `assets/`
- 评测用例放 `evals/`

判断标准：一段内容如果只有 20% 的任务会用到，它就不该在入口文件里。

## 输出

- 一份 `SKILL.md`（frontmatter 完整 + 六个章节）
- 按需的 `references/` / `scripts/` / `assets/` / `evals/`
- 试跑记录：跑了哪几个任务、发现了什么问题、改了什么

## 反模式

- **凭想象起草**：没真实执行过就写，第一次用必崩
- **把约束堆在开头**：写在开头的约束会被忽略，要写在触发它的那一步里
- **一份 SKILL.md 装所有内容**：入口文件越长，实际被读进去的越少
- **只写 happy path**：不写边界和失败分支，遇到异常就乱走
- **改完不重跑**：无法确认改动是修好了还是改坏了
- **名字起得太泛**：`helper`、`utils` 这类名字无法被正确触发
