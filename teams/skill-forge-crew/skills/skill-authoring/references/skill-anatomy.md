# Skill 结构解剖

写给要动手写 Skill 的人：入口文件放什么、深度资料怎么分层、哪些写法会被驳回。

## 一、目录结构

```
<skill-id>/
├── SKILL.md              # 唯一必需文件，每次都会被读
├── references/           # 深度资料，用到时才读
│   └── <topic>.md
├── scripts/              # 可执行脚本
├── assets/               # 模板、示例、图片等静态资源
└── evals/                # 评测用例
```

判断标准：**一段内容如果只有 20% 的任务会用到，它就不该在 SKILL.md 里。**

## 二、frontmatter 字段

```yaml
---
name: <skill-id>              # kebab-case，必须与目录名一致
description: "<一句话：解决什么问题 + 何时触发>"
version: 1.0.0
category: development-tools
author: <作者>
---
```

| 字段 | 要求 |
|---|---|
| `name` | 全平台全局唯一，与目录名一致。重名会被驳回 |
| `description` | 触发的关键。把"用户会怎么说这句话"写进去，不是写标题 |
| `version` | 语义化版本，改动后升位 |
| `category` | 从固定枚举选：`development-tools` / `content-creation` / `design-tools` / `business-tools` / `knowledge-learning` / `productivity-tools` |

## 三、SKILL.md 正文骨架

| 章节 | 写什么 | 建议长度 |
|---|---|---|
| 适用场景 | 什么时候该用，附触发词 | 5～8 条 |
| 输入 | 需要什么材料，缺什么先问 | 3～6 条 |
| 执行步骤 | 编号步骤，每步有产出 | 主体，占 60% |
| 输出 | 交付什么，长什么样 | 3～6 条 |
| 反模式 | 这一步最容易犯的错 | 6～10 条，最容易被跳过但最有价值 |
| 参考 | 还有什么可以深读 | 2～3 条 |

**反模式这一节不要省。**它把"试跑时踩过的坑"固化下来，是 Skill 最值钱的部分。

## 四、写指令的三条经验

1. **约束写在触发它的那一步里**。堆在开头的约束会被忽略。
2. **要有判断分支**。遇到不同输入该走哪条路，写成路由表，不要指望执行者自己判断。
3. **步骤要细到可执行**。"做好错误处理"不是步骤；"对失败分支返回 4xx + 错误码，并记录上下文日志"才是。

## 五、常见驳回原因

| 现象 | 原因 |
|---|---|
| 名称已被占用 | `name` 全平台唯一，加更具体的前缀后重打包 |
| 类目不符 | 上传页的市场展示分类要勾含 AI 创作的类目 |
| 解析失败 / 缺字段 | frontmatter 字段不全或 YAML 语法错（冒号后要有空格） |
| 找不到 SKILL.md | 打包时多套了一层目录，第一层必须是资产目录 |
| 提示未找到 SKILL.md（专家包误传技能页） | 专家包第一层是 `agents/`+`skills/`+`.codebuddy-plugin/`，没有 SKILL.md |

## 六、试跑清单

定稿前，用真实任务过一遍：

- [ ] 最典型的任务能一次跑通
- [ ] 最边界的任务有明确分支可走
- [ ] 入口文件里没有只在少数任务用到的内容
- [ ] 每个反模式都对应一个真实踩过的坑
- [ ] `description` 里包含用户真实会说的说法
