# 仓库防线

让错误在最早、最便宜的地方被拦住。

> 人可以犯错，仓库不该允许犯错。`push --force` 到主分支这种事，不该依赖"记得别这么做"。

## 适用场景

- 新项目开工，先把保护机制配好
- 让 AI 参与重要仓库的开发之前
- 很久没维护，准备集中整理依赖
- 需要并行开发多个功能，互不干扰

## 输入

- 项目的技术栈与包管理器
- 已有的 lint / 格式化 / 测试脚本
- 团队对"高风险操作"的界定

## 执行步骤

### 第一部分 — 提交前自动检查

#### 步骤 1 — 先摸清现状，别急着装

检查项目已有的：包管理器（npm / pnpm / yarn）、lint 配置、格式化配置、类型检查脚本、测试脚本。

**已有方案就沿用，不强行替换为"更好的"工具。**引入团队不熟的工具链，本身就是一个风险。

#### 步骤 2 — 装钩子

配置提交前钩子（如 Husky），配合 lint-staged 只检查暂存文件：

```
提交 → lint-staged → 格式化 → lint → 类型检查 → 相关测试 → 允许提交
```

要点：
- 只跑**受影响文件**的检查，不要每次全量跑（慢到没人用就会被绕过）
- 类型检查必须包含，它能拦住一大类低级错误
- 测试只跑与改动相关的部分

#### 步骤 3 — 验证钩子真的生效

**装完必须制造一次失败来验证**：故意写一个格式错误的文件提交，确认被拦住。没验证的钩子等于没装。

### 第二部分 — 危险命令拦截

#### 步骤 4 — 界定高风险操作

至少包含：

| 命令 | 风险 |
|---|---|
| `push --force` / `push -f` | 覆盖他人提交 |
| `reset --hard` | 丢弃未提交改动 |
| `clean -fd` | 删除未跟踪文件 |
| `checkout .` / `restore .` | 批量丢弃改动 |
| `branch -D` | 强删未合并分支 |

#### 步骤 5 — 配置拦截并留**受审计的**绕过方式

在执行前拦截，提示要写清：这条命令会发生什么、代价是什么（例如将丢弃哪几个提交、哪几个未跟踪文件）。

绕过必须同时满足四条，缺一条等于没拦：

1. **逐次显式确认**：必须是**当次命令上**人工键入的一次性确认（交互式输入 `yes`，或一次性命令行参数）。**不得**实现为常驻环境变量、全局配置或「设一次长期生效」的开关
2. **可归属**：放行动作写入日志——谁、什么时间、命令原文、为什么放行
3. **不得是「跳过检查」类参数**：绕过的是**拦截器的提示**，不是**钩子本身**。任何跳过钩子的写法都不算绕过方式，那叫拆掉防线
4. **失效时 fail-closed**：拦截器自身缺失、报错或版本不匹配时，按**拦住**处理；默认安全是拦截，不是放行

**我（AI）不得为自己省事而使用绕过，也不得替用户键入确认。**需要放行时，向用户说明将丢失什么，由用户本人确认。

### 第三部分 — 依赖体检

#### 步骤 6 — 扫描并分级

扫 `package.json`（及其他 manifest），按三级出清单：

| 级别 | 判定 | 动作 |
|---|---|---|
| 有漏洞 | 存在已知安全公告 | 尽快修，优先升到修复版本 |
| 严重过时 | 落后多个大版本 | 排期升级，评估破坏性变更 |
| 无人维护 | 长期无更新、维护者失联 | 评估替换成本，制定备选 |

不一律"升级到最新"：大版本升级的破坏性变更可能比漏洞本身更贵。

**除了版本，同样要看这三件事**（比版本更常被忽略，且审计工具替你看不了）：

- **权威锁文件**：CI 是否锁定并复用同一份 lockfile（冻结安装）；同一个安装边界是否出现了多个包管理器或多份互斥锁文件
- **安装脚本**：新增依赖是否有 `preinstall` / `postinstall` 脚本；首次安装前先看脚本源码，按最小集合逐条批准并写下策略，**不做全量放行**
- **包来源**：新增包是否与已有包拼写相近（抢注包），维护者、发布时间与发布来源是否正常

**前置钩子除了 lint / 类型 / 测试，再加一道密钥扫描**：检测暂存区文件中疑似密钥的字符串并拦住提交。这道检查最便宜，也是唯一能在本机就挡住误提交密钥的一层。

### 第四部分 — 环境隔离

#### 步骤 7 — 用工作树隔离并行工作

需要同时开发多个功能或做实验性方案时，用 Git 工作树给每个分支一个独立目录：

- 主目录保持干净，随时能切回去处理紧急事情
- 实验性方案失败，直接删目录，不影响任何东西
- 构建产物和依赖各自独立，不会互相污染

## 输出

- 钩子配置说明（装了什么、检查哪些、绕过方式与**审计日志位置**）
- 拦截清单（拦哪些命令、如何确认放行）
- 依赖处理清单（三级分类 + 每项建议动作与风险）
- 工作树使用说明（如适用）

## 反模式

- **为了统一而换掉项目已有工具**：引入风险，且招人怨
- **钩子跑全量检查**：慢到没人用，最后钩子会被人挪掉，保护归零——只检查暂存文件
- **装完不验证**：钩子可能根本没生效
- **拦截不给绕过方式**：人会直接删掉钩子，保护归零
- **依赖一律升到最新**：大版本破坏性变更可能代价更高
- **工作树与主目录共用依赖**：构建产物互相污染，隔离失效
- **用跳过钩子的方式实现「绕过」**：那是拆掉防线，不是绕过拦截器（见步骤 5 第 3 条）
