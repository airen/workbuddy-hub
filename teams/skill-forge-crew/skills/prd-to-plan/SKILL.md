# PRD 转实施计划

把"要做什么"变成"按什么顺序做"。

> 每一步都尽量完成一个从界面到后端能跑通的小功能，尽早发现不同模块接不起来的问题。

## 适用场景

- PRD 已定稿，需要排实施顺序
- 多个模块要并行开发，需要确定谁先谁后
- 想尽早验证技术可行性
- 需要向他人解释"为什么要先做这个"

## 输入

- 已定稿的 PRD（目标、非目标、成功标准、改动面）
- 现有系统结构（依赖方向、部署方式）
- 约束：人力、并行度、时间窗口、外部依赖的就绪时间

## 执行步骤

### 步骤 1 — 列改动面，标依赖

把 PRD 的改动面拆成模块级条目，画出依赖：谁依赖谁的数据 / 接口 / 部署顺序。

### 步骤 2 — 选第一个切片（最关键）

第一个切片要同时满足：

- **端到端能跑通**：从入口到存储，能演示一个真实结果
- **跨模块**：故意让它穿过最多的集成点，早暴露接口对不上的问题
- **不依赖未决事项**：不卡在第三方审批、数据迁移这类外部因素上

> 第一个切片选错了，集成问题会全部堆到最后一天。

### 步骤 3 — 排后续阶段

排序原则：

1. 被依赖的先做（数据层 → 接口层 → 界面层）
2. 风险高的先做（不确定能否实现的部分尽早验证）
3. 能独立交付价值的先做（万一中断，已有的部分仍然可用）
4. 同类改动聚在一起（减少上下文切换）

### 步骤 4 — 每阶段写四件事

```
### 阶段 N：<名字>
目标：这一阶段结束时能做到什么（可演示）
范围：涉及哪些模块
产出：可验证的东西（跑通的调用 / 页面 / 测试）
完成判据：怎么确认这一阶段真的做完了
```

### 步骤 5 — 标出验证点与回滚点

每个阶段结束都要有一个**可验证的节点**；每个阶段都要能独立回滚。一次性大改然后祈祷，不是计划。

### 步骤 6 — 列风险与未决项

对每阶段标注：风险点、 mitigation、以及"如果这一步卡住，Plan B 是什么"。

## 输出格式

```
# 实施计划：<功能名>

## 阶段总览（表格：阶段 / 目标 / 依赖 / 可验证产出）
## 阶段 1：…（目标 / 范围 / 产出 / 完成判据 / 风险）
## 阶段 2：…
## 跨阶段风险与未决项
## 回滚策略
```

## 反模式

- **按技术层排阶段**（先做完全部后端，再做完全部前端）：集成问题全部压到最后
- **第一个切片不跨模块**：看起来进展很快，实际上什么都没验证
- **阶段没有完成判据**：无法判断该不该进入下一阶段
- **阶段不可回滚**：一次失败就得全盘退回
- **不写 Plan B**：风险兑现时只能硬扛

## 参考

- 与 `prd-to-issues` 的分工：本技能负责**阶段与顺序**，它负责**拆成可分别领取的任务**。两者配合使用：先排顺序，再按阶段拆任务。
