# 接口方案比选

这里的 Interface 指**模块接口**：函数签名、API 形状、数据契约、模块边界。

> 只给出一个方案时，用户无法判断好坏。摆出三五个差异明显的方案，才能按项目限制做选择。

## 适用场景

- 模块边界怎么切，有多种合理做法
- API 形状定不下来（REST vs RPC、同步 vs 异步、粒度粗细）
- 数据契约要在多个消费方之间取舍
- 设计评审需要对比依据，而不是一个人的意见

## 输入

- 接口要满足的需求（谁调用、调用频率、数据规模）
- 项目约束（技术栈、团队熟悉度、性能要求、兼容要求）
- 已有的相关接口（保持风格一致）

## 执行步骤

### 步骤 1 — 明确评判维度

先定好评判标准，再生成方案。常用维度：

| 维度 | 问什么 |
|---|---|
| 易用性 | 调用方写起来顺手吗，会不会用错 |
| 可扩展性 | 加一个新场景要改接口吗 |
| 性能 | 调用次数、传输量、是否 N+1 |
| 兼容性 | 老调用方要改吗，破坏性多大 |
| 实现成本 | 服务端做起来多复杂 |
| 可测试性 | 好不好写测试，能不能 mock |

### 步骤 2 — 生成差异明显的方案

**关键：方案之间必须实质不同**，不能是同一个设计的三种写法。至少产出 3 个，最多 5 个。

典型差异轴：

- 粒度：粗粒度（一次拿全部）vs 细粒度（分次取）
- 耦合：强类型契约 vs 通用字典
- 方向：拉（轮询）vs 推（回调 / 订阅）
- 归属：调用方适配 vs 服务方适配

### 步骤 3 — 每个方案写清楚

每个方案都要包含：

```
方案 N：<一句话定位>
接口形态：签名 / 端点 / 数据结构（给代码示例）
调用示例：真实调用长什么样
优点：针对评判维度的强项
代价：明确的缺点，不回避
适用场景：什么情况下该选它
```

### 步骤 4 — 做对比表

按步骤 1 的维度做表，每个方案逐项打分（1～5 或 高/中/低）。

### 步骤 5 — 给推荐，但要说明前提

推荐必须写成条件句：

> 如果调用方固定且追求易用性，选方案 A；如果调用方会长期增加且不在你控制范围内，选方案 C，代价是初期实现复杂一些。

不给前提的推荐等于没说。

### 步骤 6 — 记录未采纳的原因

被否掉的方案写一句"为什么不选"。三个月后有人重新提出同样方案时，这份记录能省一次讨论。

## 输出

- 3～5 个实质不同的方案（含代码示例）
- 对比表
- 带前提的推荐
- 未采纳原因记录

## 反模式

- **只给一个方案**：用户没有选择余地，也就没有判断依据
- **方案之间只有表面差异**：换了个参数顺序也算新方案，是自欺欺人
- **只写优点不写代价**：没有代价的方案说明没想透
- **评判维度事后才定**：先出方案再想维度，等于为既定结论找理由
- **推荐不给前提**：脱离项目约束的推荐无法落地
- **跳过未采纳记录**：同一场讨论会反复发生

## 参考

- 接口设计先于实现：接口一旦被多个调用方依赖，改动成本会指数上升。
