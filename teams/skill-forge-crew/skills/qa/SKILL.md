# 功能质检

对一个功能做完整的质量检查，把发现的问题拆成任务，并标明处理顺序和依赖关系。

## 适用场景

- 提交 PR 之前
- 功能刚做完，需要一轮系统检查
- 改动跨多个模块，担心破坏原有功能
- 上线前的最后一轮验收

## 输入

- 被测功能的需求或规格（成功标准是什么）
- 改动范围（哪些文件、哪些模块）
- 可运行的验证手段（测试、脚本、手动路径）

## 执行步骤

### 步骤 1 — 列出入口与状态变化

先把这个功能的所有入口列出来（UI 入口、API 端点、定时任务、消息消费），再列出它会引起的所有状态变化（写库、发消息、改缓存、触发外部调用）。

**列不全入口，就一定会漏测。**

### 步骤 2 — 走主路径

按规格走一遍正常流程，确认结果符合成功标准。同时记录：响应时间、产生的副作用（写了几张表、发了几条消息）。

### 步骤 3 — 走边界与异常

逐项检查：

| 类别 | 检查什么 |
|---|---|
| 边界值 | 空、零、最大值、超长、刚好越界 |
| 非法输入 | 类型错误、缺失字段、恶意内容 |
| 并发 | 同时操作同一资源、重复提交 |
| 中断 | 中途失败、网络断开、进程被杀 |
| 权限 | 无权限 / 越权访问 |
| 数据 | 脏数据、历史数据、已删除数据的引用 |

### 步骤 4 — 查回归

对照改动范围，检查：

- 改动模块的其他功能是否仍正常
- 调用方是否受影响（签名变了、行为变了）
- 共享状态 / 缓存 / 配置是否被破坏

### 步骤 5 — 把发现拆成任务

每个发现写成：

```
问题：<一句话>
复现：<具体步骤 / 输入>
期望 vs 实际
影响面：<谁会受影响>
优先级：阻断 / 高 / 中 / 低
依赖：<是否需要先修别的问题>
```

### 步骤 6 — 排序

排序依据：**影响面 × 触发概率**，不是修起来的难易程度。

- 阻断：会导致数据丢失、安全漏洞、主流程不可用 → 必须修完才合并
- 高：边界情况但用户会遇到
- 中：体验问题或罕见场景
- 低：吹毛求疵，可延后

## 输出

- 检查覆盖清单（走过哪些路径）
- 发现列表（含复现步骤、影响面、优先级、依赖）
- 结论：能不能合并，以及哪些必须先修

## 反模式

- **只测 happy path**：问题全在边界和异常里
- **不列入口就开始测**：漏掉定时任务、消息消费这类隐形入口
- **只看新功能，不查回归**：破坏原有功能比新功能有 Bug 更严重
- **按修复难度排序**：应该是按影响排序
- **发现不写复现步骤**：别人无法验证，也无法确认修好了
- **报"应该没问题"**：要么给出测过什么的清单，要么明说没测

## 参考

- 与 `code-review` 的分工：本技能验证**行为对不对**，`code-review` 检查**代码好不好**。
