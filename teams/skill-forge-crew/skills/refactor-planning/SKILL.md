# 重构规划

先通过问答了解重构目标，再制定细致的计划，把修改拆成小步提交。

## 适用场景

- 老项目职责过多、谁都不想碰的大函数
- 模块只有薄薄一层封装，实际价值存疑
- 逻辑本该集中却被分散在多处
- 代码不好测，每次改动都心惊胆战

## 输入

- 重构的目标（想解决什么：可维护性 / 可测试性 / 性能 / 解耦）
- 现有代码（要读，不靠描述）
- 约束：能不能停服务、有没有测试保护、时间窗口

## 执行步骤

### 步骤 1 — 先问清楚为什么重构

"代码丑"不是重构理由。目标必须是可衡量的：

| 差 | 好 |
|---|---|
| 代码太乱 | 新增一个支付方式要改 7 个文件 |
| 不好维护 | 这块逻辑散在 4 处，改一处漏三处 |
| 想用新框架 | 当前写法无法写单元测试，回归全靠手工点 |

**没有明确痛点的重构，性价比通常是负的。**

### 步骤 2 — 读代码，找坏味道

重点查三类：

1. **薄封装**：模块只做转发，没有自己的语义。要么充实它，要么删掉它
2. **该集中却分散**：同一条业务规则在多处各自实现，改一处漏三处
3. **不好测**：依赖硬编码、副作用混在纯逻辑里、构造一个对象需要先起半个系统

同时记录：这块代码有没有测试保护。**没有测试就先补测试，再谈重构。**

### 步骤 3 — 找出问题最集中的地方

不要全仓重构。按"问题密度 × 改动频率"排序，找出最值得动的两三处。

改动频率低的烂代码，就让它烂着——那里的重构收益最低。

### 步骤 4 — 出 2～3 种方案

每种方案必须实质不同（例如：抽模块 vs 换架构 vs 局部收敛），并且每种都标注：

```
方案 N：<一句话>
做法：改什么（模块级描述）
风险：哪里可能出问题、最坏情况
工作量：大致规模（小 / 中 / 大）+ 主要成本在哪
收益：解决了步骤 1 里的哪个痛点，收益多大
回滚难度：能不能分步回退
```

### 步骤 5 — 拆成小步提交

选中的方案按这个顺序拆：

1. **先补测试**（覆盖现有行为，作为安全网）
2. **先加后删**（新结构建好并切换调用方，再删旧结构）
3. **每步可独立提交、独立回退**
4. **接口兼容期**：新旧共存一段时间，避免一次性切换

### 步骤 6 — 明确不做什么

写下这次明确不重构的部分。重构的最大风险是范围蔓延。

## 输出

- 重构目标（可衡量的痛点）
- 坏味道清单（位置 + 类型 + 严重度）
- 2～3 个方案，各带风险 / 工作量 / 收益 / 回滚难度
- 推荐方案的小步提交序列
- 本次不做的部分

## 反模式

- **没有明确痛点就重构**：付出成本，收益说不清
- **没有测试就动手**：重构后无法确认行为没变
- **全仓重构**：范围失控，无法回退
- **一步到位的大改**：失败就得全盘退回
- **先删后建**：中间状态不可运行，无法分步验证
- **只给一个方案**：用户无法判断代价与收益是否划算
