# 现成方案检索

找 Skill 和找软件依赖是一个道理：**准备自己写之前，先看看有没有现成的。**

## 适用场景

- 正准备动手写一个新的 Skill
- 遇到一类任务，感觉"别人应该做过"
- 已有方案能用但不够贴合，想找个更好的基础版本来改
- 想评估某类任务在社区里的成熟做法

## 输入

- 任务描述（要做什么、输入输出是什么）
- 硬约束（语言 / 框架 / 平台 / 许可要求）
- 可接受的改造成本（读完就能用 / 需要大改 / 只能参考思路）

## 执行步骤

### 步骤 1 — 提炼检索词

把任务抽象成**可检索的能力名词**，不要用整句需求。

| 需求原话 | 检索词 |
|---|---|
| 每次提交前自动跑一遍 lint 和格式化 | pre-commit hooks / lint-staged |
| 帮我把 PDF 里的表格抽出来 | pdf table extraction |
| 给网站做一轮技术 SEO 检查 | technical seo audit |

同时准备 2～3 组同义检索词（中英文各一组），第一次搜不到就换词，不要只搜一次。

### 步骤 2 — 检索公开市场

优先顺序：

1. **官方仓库**（如 Anthropic 官方 skills）：质量稳定，许可清晰
2. **知名个人维护者的合集**：覆盖面广，风格统一
3. **社区聚合市场**：数量最多，质量参差，需要逐个验

对搜到的每个候选，记录：来源链接、最近更新时间、许可、Star / 下载量（有的话）。

### 步骤 3 — 评估适配度

按三项打分，每项 1～5 分：

| 维度 | 看什么 |
|---|---|
| 能力匹配 | 核心步骤是不是同一套，还是只是名字像 |
| 约束兼容 | 语言、框架、平台、许可是否冲突 |
| 改造成本 | 直接能用，还是要拆开重写 |

**总分 ≥ 12 且约束无冲突** → 采用，在其基础上改。
**总分 9～11** → 摘取其中有用的章节，自己写骨架。
**总分 ≤ 8** → 自己写，但把它的失败点记下来当反面参考。

### 步骤 4 — 验证可运行

找到方案不等于能用。落地前必须确认：

- 依赖的工具在当前环境是否存在（不要假设用户会去装）
- 引用的外部脚本 / API 是否仍然可达
- 许可是否允许改造和再分发

### 步骤 5 — 改造成自己的版本

- 保留原作者与来源链接（写在 `references/` 或文件末尾）
- 按自己的实际流程改步骤，不要原样搬运
- 用 2～3 个自己的真实任务试跑，验证改造后仍然成立

## 输出

- 候选清单：来源链接 + 三项评分 + 采纳结论
- 采纳方案的改造记录：改了什么、为什么改
- 未采纳时的说明：搜过哪些词、为什么自己写

## 反模式

- **只搜一次就下结论**：检索词不对时，一次搜索的结果毫无意义
- **看名字就采用**：名字像和能力匹配是两回事
- **忽略许可**：商用或再分发场景下这是硬风险
- **原样搬运不改**：别人流程里的假设往往和你的不一样
- **找到就宣称完成**：不验证可运行性，等于没找到
