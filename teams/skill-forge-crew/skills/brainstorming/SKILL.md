# 想法展开

把一个初步想法，展开成能讨论的方案。

> 开始写代码前，先讨论数据结构、API 接口，以及出错后怎么恢复和回滚。

## 适用场景

- 只有一个模糊想法，还没到能写 PRD 的程度
- 想先验证技术可行性，再决定投不投入
- 需要比较几条完全不同的路线
- 想法之间有冲突，需要收敛

## 输入

- 一句话想法
- 期望的结果（解决什么问题）
- 已知的限制（技术栈、时间、不能碰的东西）

## 执行步骤

### 步骤 1 — 先复述，确认没理解错

用自己的话把想法复述一遍，并说出**你认为它要解决的核心问题**。理解错了就在这里纠正，不要往下走。

### 步骤 2 — 问三件事（每件事连问到有答案）

1. **数据长什么样**：核心实体有哪些、关系如何、存在哪、会怎么变
2. **接口长什么样**：谁调用、传什么、返回什么、同步还是异步
3. **出错怎么办**：失败语义、恢复路径、回滚方式、数据一致性

第三件最常被跳过，也最容易在后期变成事故。

### 步骤 3 — 给 2～3 条路线

每条路线写：核心思路、关键技术选择、大致工作量、最大风险。

路线之间要真的不同（自建 vs 用现成服务、同步 vs 异步、集中 vs 分布），不是同一条路线的三种表述。

### 步骤 4 — 找最小验证

对每条路线，问：**花半天时间，能验证它的哪个关键假设？**

例：
- 假设"第三方 API 能提供所需数据" → 最小验证：调一次真实接口看返回结构
- 假设"实时同步可行" → 最小验证：写个 50 行的原型测延迟

验证不出来的假设，标注为"未验证，需投入后才能知道"。

### 步骤 5 — 收敛并给出下一步

明确三件事：

- 推荐哪条路线，以及为什么
- 接下来第一步做什么（要小到能立刻开始）
- 哪些问题现在不必解决（推迟决策，而不是假装不存在）

## 输出

- 需求复述与核心问题确认
- 数据结构 / 接口 / 失败恢复三方面的初步结论
- 2～3 条路线，各带风险与最小验证方法
- 推荐路线 + 立刻可做的第一步

## 反模式

- **不复述就展开**：理解错了，后面展开得再好也是白费
- **只讨论 happy path**：不谈失败与回滚，方案不可落地
- **路线之间没有实质差异**：换汤不换药，等于没有选择
- **不给最小验证**：所有路线都停留在纸面，无法决策
- **一次把所有问题都解决**：过早优化会导致想法在讨论阶段就死掉
- **把未验证的假设写成结论**：后期会以"你当初说可行"的形式反噬
