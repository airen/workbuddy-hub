# 代码审查

从安全、性能、错误处理和架构几个方面检查代码。可以指定优先查哪一类，也可以完整过一遍。

## 适用场景

- 合并前的常规审查
- 改动涉及敏感逻辑，想优先查安全
- 页面 / 接口变慢，想优先查性能
- 想让审查标准可复用（把常用模式固化成团队约定）

## 输入

- 变更内容（diff 或文件清单）
- 变更的意图（规格 / 任务描述）——不知道意图就无法判断"是否造对了东西"
- 指定模式：安全优先 / 性能优先 / 完整清单（未指定时按完整清单）

## 执行步骤

### 步骤 1 — 先读意图，再读代码

先读规格或任务描述，理解这次要做什么。**不知道意图的审查只能看到代码风格问题。**

### 步骤 2 — 按模式选择检查轴

| 模式 | 覆盖的轴 |
|---|---|
| 安全优先 | 安全 → 错误处理 → 其他 |
| 性能优先 | 性能 → 其他 |
| 完整清单 | 安全 → 性能 → 错误处理 → 架构 |

### 步骤 3 — 逐轴检查

**安全**
- 输入是否校验（类型、范围、长度、来源）
- 注入面：SQL、命令、模板、路径遍历
- 权限与越权：是否校验了归属，而不只是登录态
- 敏感数据：日志里有没有密钥 / 令牌 / 个人信息
- 依赖：新增依赖是否有已知风险

**性能**
- 循环里的数据库查询 / 网络请求（N+1）
- 重复计算、可缓存但没缓存的结果
- 前端渲染：不必要的重渲染、未拆包的大依赖
- 数据量：是否有无上限的查询或全量加载

**错误处理**
- 失败语义是否明确（抛错 / 返回错误 / 静默）
- 错误信息是否可诊断（有上下文，不含敏感信息）
- 资源是否释放（连接、文件句柄、定时器）
- 超时与重试：有没有退避，会不会雪崩

**架构**
- 模块边界是否清晰，依赖方向是否合理
- 有没有只有一层薄封装的模块
- 逻辑是否可测试（依赖能不能被替换）
- 重复逻辑是否该收敛

### 步骤 4 — 分级并给出具体改法

| 级别 | 含义 | 要求 |
|---|---|---|
| 阻断 | 会导致事故、漏洞或数据问题 | 必须带文件:位置 + 具体改法 |
| 必修 | 明确的技术债或隐患 | 带改法，原则上合并前修掉 |
| 可选 | 更好的写法 | 说明收益，不阻塞 |
| 吹毛求疵 | 风格偏好 | 一句话带过 |

**每条阻断和必修都要能直接照着改。**只说"这里有问题"的审查没有价值。

### 步骤 5 — 也说好话

具体指出做得对的地方（哪一个抽象切得好、哪一处错误处理周全）。好实践被指出才会被保留。

## 输出

- 模式与覆盖范围
- 分级发现清单（每条含位置、原因、改法）
- 值得保留的好实践
- 结论：能否合并 / 需要修完哪些才能合并

## 反模式

- **不读意图就审**：只能看到风格问题，看不到"造错了东西"
- **只有批评没有改法**：无法执行的意见等于没提
- **把所有问题都标成阻断**：分级失去意义，审查被忽略
- **只看代码不看测试**：测试缺失本身就是一个必修项
- **用个人偏好当标准**：风格问题交给格式化工具，不进审查意见
- **审查意见不区分"必须"和"更好"**：阻塞了本可合并的改动
