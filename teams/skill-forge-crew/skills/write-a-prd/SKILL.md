# 写产品需求文档

一份能拿来评审的 PRD。核心不是写满，是**把"不做什么"写清楚**。

## 适用场景

- 需求已澄清，需要一份书面规格
- 范围不断膨胀，需要一条明确的边界线
- 多人 / 多 Agent 协作，需要共享同一份事实基础
- 实现到一半发现方向分歧，需要回溯依据

## 输入

- 需求澄清的结论（来自 `requirement-interview`）
- 现有代码与文档（要改哪些系统）
- 已知约束（时间、技术、合规、依赖）

## 执行步骤

### 步骤 1 — 先读代码，再写文档

PRD 里"要改动的现有系统"这一节必须是读过代码之后写的。凭需求描述想象出来的改动面，八成是错的。

查清：涉及哪些模块、现有接口长什么样、有没有相似实现可以复用、数据落在哪。

### 步骤 2 — 写目标

一到三句话，说清**解决谁的什么问题、带来什么结果**。要能被验证，不要写"提升用户体验"这种无法判定的话。

### 步骤 3 — 写非目标（单独成节）

这一节最重要，也最常被跳过。显式列出：

- 这次不做的功能（哪怕它很合理）
- 这次不支持的场景
- 这次不解决的历史问题

> 范围膨胀的唯一解药，是开工前就把边界写下来。

### 步骤 4 — 写用户路径

按用户实际动作一步步写：从哪个入口进来 → 看到什么 → 做什么操作 → 得到什么结果 → 出错时看到什么。

每个路径都要写**失败分支**。只写成功路径的 PRD，实现出来必然漏异常处理。

### 步骤 5 — 写成功标准

可验证，不写"做好了"。例：

| 差 | 好 |
|---|---|
| 上传更快 | 95 分位的 10MB 文件上传耗时 ≤ 3 秒 |
| 用户更满意 | 上传任务放弃率从 12% 降到 5% 以下 |
| 系统更稳 | 上传失败重试成功率 ≥ 99%，无数据丢失 |

### 步骤 6 — 写现实限制

时间、人力、技术栈、合规、第三方依赖、必须兼容的旧版本——把约束明写，否则评审时会有人假设一个不存在的自由度。

### 步骤 7 — 写改动面

逐个列出要改的模块、接口、数据结构、配置，并标注是新增 / 修改 / 删除。有破坏性变更的单独标出。

## 输出格式

```
# PRD：<功能名>

## 背景与目标
## 非目标（本次不做）
## 用户路径（含失败分支）
## 成功标准（可验证）
## 现实限制
## 改动面（模块 / 接口 / 数据）
## 开放问题与待确认
```

## 反模式

- **没有非目标**：范围必然膨胀
- **只写成功路径**：异常处理在实现阶段才被发现，工期翻倍
- **成功标准不可验证**：做完了也说不清算不算做完
- **不读代码就写改动面**：改动面写错，计划全废
- **把技术方案塞进 PRD**：PRD 说"要什么"，方案说"怎么建"，混在一起会让需求被实现细节绑架
- **开放问题不列出**：藏着的问题会在评审时爆炸
