# Issue 分诊

处理待办问题，给每个 Issue 一份明确的任务说明：**调查范围是什么，不处理什么。**

## 适用场景

- 积压 Issue 需要清理
- 新 Issue 需要自动分类和打标签
- 要交给 Agent 处理，需要先把任务说明写清楚
- 需要按模块或人员分配任务

## 输入

- Issue 列表（标题、正文、标签、时间、关联信息）
- 模块归属规则（哪些路径属于哪个模块）
- 可用的标签体系

## 执行步骤

### 步骤 1 — 先判断是不是真问题

逐条判断并分类：

| 类型 | 处理 |
|---|---|
| 真缺陷 | 进入分诊流程 |
| 使用问题（不是 Bug） | 回复用法说明，转为文档任务或关闭 |
| 重复 Issue | 合并到原始 Issue，保留链接 |
| 信息不足 | 明确列出需要补充的信息，标记待补充 |
| 已修复 | 确认修复版本并关闭，注明在哪个版本修的 |
| 外部依赖导致 | 标注上游，说明本仓库能做什么 |

**不要把"使用问题"当缺陷分诊**，那会浪费整个排查预算。

### 步骤 2 — 写调查范围

对每个确认要处理的 Issue 写：

```
现象：<用户看到什么>
期望：<应该是什么>
调查范围：<从哪个模块 / 哪段路径开始查>
可能方向：<2～3 个假设，按可能性排序>
不查什么：<明确排除的方向及原因>
需要的信息：<复现步骤、环境、日志>
```

**"不查什么"和"查什么"一样重要。**没有排除项，调查会无限扩散。

### 步骤 3 — 归类与打标签

按两个维度打：

- 模块维度（属于哪个模块，按路径规则判断，不靠标题猜）
- 性质维度（缺陷 / 增强 / 文档 / 疑问 / 依赖）

同时标严重程度：阻断（不可用或数据风险）/ 高（主流程受影响）/ 中（有绕行方案）/ 低（体验问题）。

### 步骤 4 — 排优先级

排序依据：**严重程度 × 影响用户数 × 修复成本**。不要只看严重程度——一个阻断级但只影响一个人的问题，可能排在一个中等但影响所有人的问题之后。

### 步骤 5 — 分配

按模块归属分配。跨模块的 Issue 拆成多个，或指定一个主要负责人并列出协作者。

**判断不了的留给人工**，不要为了自动化而硬猜归属。

## 输出

- 分类结果（每条 Issue 的类型与处理动作）
- 待处理 Issue 的调查范围说明（含"不查什么"）
- 标签与优先级
- 归属分配，以及留给人工判断的清单

## 反模式

- **所有 Issue 都当缺陷处理**：使用问题、重复问题会挤占排查预算
- **不写"不查什么"**：调查无限扩散，一周查不完一个 Issue
- **靠标题猜模块**：必须按路径规则或代码归属判断
- **只按严重程度排序**：忽略影响面会导致排错顺序
- **硬猜归属**：猜错的分诊比不分诊更糟
- **分诊完不复盘**：同类问题反复出现，说明根因没被处理
