# 中文长文与技术社区发布交底

## §0 先说清楚这个技能为什么不省略

专家团原有的能力重心在**社媒短视频**（抖音/B站/小红书/快手）和**公众号图文**。这两条线的发布工具（`baoyu-post-to-*`、四个 `*-upload`、`self-media-wechat-publisher`）已经能跑。

但中文内容还有第三条赛道：**技术社区长文**（CSDN、掘金、知乎）。这条赛道有四个不一样的地方，直接套短视频那套会翻车：

1. **正文是 Markdown + 代码块**，不是封面九宫格。转换错一次，代码块全糊。
2. **默认产物是草稿，不是终稿**。这三站官方都不鼓励外部程序直接终发，草稿是唯一稳妥的自动落点。
3. **后台数据要主动抓**，不会推给你。发布动作和一周后的数据回收是两件事，中间隔着 7 天。
4. **知乎是个例外**——它目前没有可靠的自动发布方案，硬承诺等于骗人。

本技能负责把这四件事讲透，并给出每站的自动化水位线。**专家团负责写稿和判断，外部工具负责真正敲键盘。**

## §1 四站自动化水位线（动手前先看这张表）

这张表是本技能的核心。**水位线以上才敢承诺，以下必须降级为「我给你准备好，你去点」**。

| 平台 | 落草稿 | 自主终发 | 后台数据 | 成熟度 | 备注 |
|---|---|---|---|---|---|
| **CSDN** | ✅ 自动 | ❌ 不建议 | ✅ 自动 | 中 | 创作中心结构化程度尚可，改版频率一般 |
| **掘金** | ✅ 自动 | ❌ 自主放弃 | ✅ 自动 | 中 | 上游实现明确限定「只存草稿，不做终发」 |
| **微信公众号** | ✅ 已有能力 | ✅ 需确认 | ✅ 自动 | 中 | 发布见 `self-media-wechat-publisher`；本技能补**数据回收** |
| **知乎** | ⚠️ 不稳 | ❌ | ⚠️ 仅公开侧 | 低 | **没有成熟可靠的自动发文方案**，见 §5 |

> **诚实原则**：用户问「能不能自动发知乎」，回答是「目前不能，我可以把稿子整理成知乎格式，你手动发」。**不要为了显得全能而假装能发**——发出去一半卡住比直说不能更糟。

## §2 四条通行铁律（四站通用）

这四条是从成熟实现里提炼出来的公约数，本专家团在此之上统一执行标准。

### 铁律一：草稿优先，终发必须有授权

默认产物**一律是草稿箱**，不是已发布。

- 运行任何发布类命令前，必须先把「要发哪几站、各自是草稿还是终稿」列给用户看，**拿到明确回复才开始**。
- 不允许因为「用户之前说过一次」「成稿已经确认过了」就跳过这一步。这是不可逆动作。
- 唯一的例外是用户这次明确说了「直接发」，且指定了平台。

### 铁律二：认证靠文件，不靠账密

**永远不要向用户索要账号密码、短信验证码、登录二维码内容。**

正确做法是复用用户浏览器已有的登录态，导出成文件。查找顺序统一为：

1. 命令显式传入的 `--state` / `--cookie`
2. 工作区下的 `.media-manager/auth/<platform>/storageState.json`
3. 同目录的 `cookies.json`（降级方案）
4. 技能目录下的 `.auth/`（兼容旧路径）

**优先 `storageState.json`**，`cookies.json` 只作为兜底。

> **安全红线**：`storageState.json` 和 `cookies.json` 等同于明文账密。**绝不提交进 git**。写 `.gitignore`，写进技能文档，每次提到都要强调。

### 铁律三：产物落工作区，不落临时目录

所有中间产物（转换后的正文、抓回来的 JSON、配图）必须写进用户可见的工作区目录。

**不许写进 `/tmp` 或任何会被清理的位置**——重发一遍草稿是小事，草稿链接和数据包没了没法追溯才是大事。

### 铁律四：一次性配置不做第二遍

环境没问题就别重复跑：

- **只做一次**：装依赖、装浏览器内核、导出登录态
- **只在换机器或怀疑后台环境崩了时重跑**：环境自检
- **登录态失效才重跑**：登录校验

如果登录态已知有效，**不要先跑一遍依赖安装和登录检查再干活**，那是浪费时间。

## §3 CSDN 路径

### 能做什么

| 操作 | 命令 |
|---|---|
| 存草稿 | `media csdn post --file output/{slug}/article.md --draft` |
| 抓后台数据 | `media csdn analytics fetch` |
| 导出登录态 | `media csdn auth export` |
| 校验登录 | `media csdn auth check` |

### 关键约束

- **直接传原始 Markdown 文件**，不要在调用前先把 MD 转成 HTML。转早了代码块格式会崩。
- 编辑器改版导致选择器失效时，**用 `--headful` 跑一遍肉眼看**，别猜选择器。
- 页面上冒出新的必填项时，**停下来告诉用户哪个字段拿不到值**，不要自动填一个猜测值进去。

### 数据结构

CSDN 后台报告是三层结构，看懂这三层才知道怎么给结论：

```
report
├── range          {start, end}                   —— 统计区间
├── overview       articleCount / exposuresCount /
│                  diggCount / commentCount /
│                  viewCount / score /
│                  averageQuality / collectCount  —— 账号整体
└── articles[]     逐篇
    ├── summary    publishTime / exposuresCount /
    │              viewCount / commentCount /
    │              diggCount / favoriteCount /
    │              fansCount / qualityScore      —— 单篇累计
    └── recent7Days[]  按天展开同样一套指标        —— 近 7 日走势
```

**读法**：`overview` 看水位，`articles[].summary` 找出爆款，`recent7Days` 判断这篇是在涨还是在凉。**只看总数不看趋势，等于没看。**

## §4 掘金路径

### 能做什么

| 操作 | 命令 |
|---|---|
| 存草稿 | `media juejin post --file output/{slug}/article.md --draft` |
| 抓后台数据 | `media juejin analytics fetch` |
| 导出登录态 | `media juejin auth export` |
| 校验登录 | `media juejin auth check` |

### 与 CSDN 的三点差异

1. **数据面更宽**：除内容数据外还有**粉丝数据**，`--page content|follower|both` 可切换。做涨粉归因时这个必须有。
2. **发文可选字段更多**：`--title` / `--cover` / `--tags` / `--column` / `--visibility`。产出报告时要说清**哪些字段实际生效了、哪些没确认到**。
3. **主动放弃终发**：成熟实现在实现层面就把终发这条路封死了，只做草稿。这是刻意的克制，不是能力不足。

### 必报清单

发文后必须向用户报告：最终模式（draft）、实际用上的标题、可用的文章链接/ID、实际生效的标签/专栏/封面、**以及哪些可选字段没能在界面上确认到**。

## §5 知乎：这里要有心理准备

### 发布侧 —— 目前不靠谱，别承诺

翻遍成熟的自媒体工具链，**知乎的自动发文普遍缺失或极不稳定**。连专门的中文自媒体管理工具矩阵都没有把知乎的发布纳进去——这不是遗漏，是因为确实难做稳。

**本专家团对此的处理方式：**

- ❌ 不承诺自动发知乎
- ❌ 不用不可靠的第三方脚本去赌，发一半失败更难收场
- ✅ 负责把成稿**改成知乎适配形态**：知乎喜欢的行文节奏、开篇钩子、Markdown 兼容处理（尤其是代码块和 LaTeX）
- ✅ 交付一个「复制即发」的最终文本，用户手动粘贴

### 采集侧 —— 有可用的

虽然发不了，但**看别人的内容**是有成熟工具的：

| 工具 | 能做什么 | 许可 | 获取 |
|---|---|---|---|
| **MediaCrawler** | 关键词搜索 / 指定回答抓取 / 创作者主页批量，覆盖含知乎在内 7 个国内平台 | ⚠️ 需自行核实 | [NanmiCoder/MediaCrawler](https://github.com/NanmiCoder/MediaCrawler) |
| **zhihu-scraper** | 把单个回答/文章转成干净 Markdown，自动处理 LaTeX | ⚠️ 需自行核实 | [LoneKnightz/zhihu-scraper](https://github.com/LoneKnightz/zhihu-scraper) |

**用法定位**：这两个归入**选题情报与竞品研究**（`creator-ops-topic-scout`），不归发布。看竞品可以，发自己的不行。

> ⚠️ 采集工具务必遵守目标平台的 robots 与条款，仅用于公开内容的研究用途，不要拿去做账号养号和批量搬运。

## §6 微信公众号数据回收

微信公众号的**发布**能力专家团已经有了（`self-media-wechat-publisher`、`baoyu-post-to-wechat`）。本节补的是**发布之后那一环：把数据捞回来**。

### 背景

微信公众号后台的数据结构跟 CSDN/掘金不是一个物种：它是**内容分析 + 用户分析**双页，且 token 会过期。

### 怎么拿

```bash
media wechat analytics fetch
```

可选 `--page content|user|both`，加 `--start/--end` 限定区间。

### token 怎么破

这是公众号最容易踩的坑：

- ✅ **推荐**：让脚本从已登录的首页自动发现 token
- ⚠️ **仅调试用**：手动传 `--token`
- ❌ **不要用**：从别处复制来的旧 token——它基本必定过期，表现为跳回登录页

### 拿回来是什么

两套归一化的字段，对着看才有意义：

**内容侧**（`normalized.content`）
- `summary`：阅读 `read`、点赞 `like`、分享 `share`、收藏 `collection`、评论 `comment`
- `dailyTotals`：按天的走势行
- `articles`：文章列表，含 `refDate` / `title` / `totalReadUv` / `readUvRatio`

**用户侧**（`normalized.user`）
- `summary`：`newUser` / `cancelUser` / `netgainUser` / `cumulateUser`
- `dailyTotals`：按天的净增走势

**产物文件名格式**：`wechat-analytics-YYYYMMDD-HHMMSS.json` + 同名 `.md`。

> `readUvRatio` 是公众号最值得盯的指标——它反映读完率，比单纯的阅读数更能说明稿子质量。底下��数字上不去时先看完成率。`cancelUser` 追平或超过 `newUser` 时，说明这一轮内容选题把人赶跑了，该换了。

## §7 把数据变成结论

拿到 JSON 只是开始。专家团的活是把数字变成「下周该怎么写」。

### 三步法

1. **定基准**：`overview` 里的均值是什么水平，低于均值的篇目挑出来
2. **看走势**：用 `recent7Days` / `dailyTotals` 判断每篇是在爬坡还是在坠落——**同一篇文章，第 3 天还在涨说明被算法推了，当天见顶说明标题拉垮**
3. **出动作**：给出下一轮的具体选题调整，不要停在「数据表现良好」这种废话上

### 报告必须包含

- 明确的高低水位判断（哪篇好、哪篇差）
- 趋势方向（涨 / 平 / 凉）
- **下一步具体做什么**（换选题方向 / 换标题写法 / 换发布时间）
- 数据区间和可复现的命令，方便下次跑同样的查询

### 反模式

- ❌ 只报总数不报趋势
- ❌ 只夸不批
- ❌ 「建议持续优化内容质量」这种等于没说的话
- ❌ **把抓到的数字当成事实而不复核**——平台口径会变，异常值先怀疑脚本，再怀疑内容

## §8 安全边界（红线）

1. **不索取**账号密码、短信验证码、扫码密钥
2. **不实现**登录绕过、验证码破解
3. **不提交** `storageState.json` / `cookies.json` 到版本库
4. **不做**多账号批量、养号矩阵、搬运别人内容伪装原创
5. **不猜测**页面上拿不到值的必填字段——停下来问用户
6. **采集工具**只用于公开内容研究，遵守平台条款与 robots
