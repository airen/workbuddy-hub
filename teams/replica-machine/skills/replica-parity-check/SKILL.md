# 一致性比对

回答一个问题：**复刻品和参考站，到底一不一致？**

判据只有一条：**同输入，同输出。** 同一尺寸、同一状态、同一串操作，两边必须给出同样结果。

> "看起来差不多"不是结论。差 4px、多一次请求、少一个错误分支，都要写下来。

## 适用场景

- 复刻品做完了，交付前把关
- 改了一版，想确认没把已对齐的部分改坏
- 怀疑某个交互的行为与参考站不一致
- Electron 目标要确认跨进程行为对齐

## 输入

- **参考站地址** / 参考应用入口
- **复刻品入口**
- **验收标准**（要一致的页面、交互、请求清单）
- 证据包（可选，用于知道参考站的预期行为）

## 执行步骤

### 步骤 1 — 对齐比对条件

**条件不对齐就不比对。** 确认两边：

- 视口尺寸与设备像素比一致
- 数据状态一致（同样的初始数据、同样的登录态）
- 时序一致（等两边都加载完成后开始）

记录这些条件，写进报告。

### 步骤 2 — 视觉比对

对同一页面 / 同一状态各截一张图：

- [ ] 整体布局（区块位置、对齐）
- [ ] 间距（内外边距）
- [ ] 字号 / 字重 / 行高
- [ ] 颜色（背景、文字、边框、状态色）
- [ ] 图标与图片
- [ ] 层级与遮挡（z-index）

### 步骤 3 — 交互比对

设计一串可复现的操作序列，两边各跑一遍：

- [ ] 正常路径：操作 → 请求 → 界面变化
- [ ] 空状态
- [ ] 错误态（断网 / 让接口返回错误）
- [ ] 边界输入：空值 / 超长 / 特殊字符

### 步骤 4 — 网络比对

用同一观察窗口分别捕获两边的请求：

- [ ] 请求数量与顺序
- [ ] URL 与方法
- [ ] 状态码
- [ ] 响应结构 / 字段形状
- [ ] 触发时机

复刻品**多发**的、**少发**的、**形状不同**的请求，逐条记录。

### 步骤 5 — IPC 比对（Electron 目标）

- [ ] IPC 通道名
- [ ] 消息形状（参数、返回）
- [ ] preload 暴露的 API
- [ ] 主进程行为与副作用

### 步骤 6 — 分级与写报告

按 `references/parity-checklist.md` 的四轴清单逐项过，把差异分级：

| 级别 | 判定 |
|---|---|
| **阻断** | 核心功能不可用、数据错误、关键交互行为不一致、请求语义错误 |
| **重要** | 次要功能偏差、明显视觉错位、错误处理缺失、多发/少发非关键请求 |
| **次要** | 细微样式差异、文案措辞、非关键排序 |

每条差异必须含：**现象 + 复现步骤 + 证据 + 期望 vs 实际 + 级别**。

### 步骤 7 — 复验

修复后由**我本人**重跑该差异点的复现步骤，给出明确结论：已消除 / 未消除 / 部分消除。不接受"改过了应该好了"。

## 工作原则

- **同条件才有可比性**：条件不一致时不比对，先对齐。
- **每条差异可复现**：写不出复现步骤的不写进报告。
- **区分"不一致"与"不可比"**：参考站依赖服务端私有逻辑、随机数据、第三方登录等导致不可比时，标注"不可比"及原因，不硬凑结论。
- **不替实现辩护**：只报告差异，不评估改动成本，不因麻烦而降级。
- **复验独立**：写代码的人不给自己背书。

## 输出：差异报告

```
# 一致性差异报告

## 比对条件
- 参考站 / 复刻品入口
- 视口尺寸、设备像素比
- 数据与登录态
- 采集时间

## 阻断级
| # | 现象 | 复现步骤 | 证据 | 期望 vs 实际 |

## 重要级
...

## 次要级
...

## 不可比项
| 项 | 原因 |

## 复验记录
| 差异 # | 修复后复验结果 | 复验时间 |
```

## 质量自检

- [ ] 四轴都覆盖（IPC 仅 Electron 目标）
- [ ] 每条差异有级别、复现步骤、证据、期望 vs 实际
- [ ] 正常路径、空状态、错误态、边界输入都覆盖
- [ ] "不可比"项已单列并说明原因
- [ ] 修复复验有明确结论
